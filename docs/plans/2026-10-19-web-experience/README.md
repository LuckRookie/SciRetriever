## 背景与目标

**第一轮**（01，已完成）：修复连续阅读、栏宽、来源展示、洞察范围等可用性缺陷。

**第二轮反馈**：Owner 认为产品整体不够优雅，具体包括：
- 控件圆角不统一，很多框接近直角；
- 风格大体统一，但阅读、总结、全文等局部设计没跟上；
- 点击效果差距大，交互“硬邦邦”。

实测确认问题来自三方面：
- **设计体系缺失**：没有圆角、间距、焦点、动效变量；同类控件多处手写；状态不完整；字体未落地。
- **原生 DOM 写法的结构性代价**：
  - 迟到响应、状态不一致这类缺陷反复出现；
  - 进出场动画和布局过渡要自己造；
  - 整段重建 HTML 会丢失焦点和动画。
- **阅读与总结的展示没有经过设计。**

**第三轮决定**：Owner 在讨论后决定，**不考虑重写成本，Web 前端改用 React 重建**。行为组件、动画、数据请求、长列表都使用成熟的库，不再重复造轮子。

**本计划目标**：在不改变服务端合同与业务语义的前提下，用 React 加设计语言 v2 重建全部 Web 界面，达到“统一、安静、有手感、可信”的产品质量。然后切换为默认界面，删除旧前端，同时处理解析质量和引用网络两个内容层问题。

## 已确定的决定

ADR 0036 已接受；当前依赖和验证数据见 02 及依赖说明。

| 编号 | 决定 |
| --- | --- |
| D1 | Web 前端采用 **React 19 + TypeScript** 重建。并行开发期已结束，Owner已确认新版作为唯一正式界面；旧前端及其临时入口全部删除。 |
| D2 | 行为组件采用 **React Aria Components**（无样式）。菜单、对话框、下拉、提示的定位、焦点和键盘交互都使用它的内置能力，**不另外引入 Floating UI**。 |
| D3 | 动画采用 **Motion**。颜色、背景、按下、焦点用 CSS；进出场、布局让位、选中指示滑动、可打断动画用 Motion。**不引入其他动画库**。 |
| D4 | 服务端数据采用 **TanStack Query**，负责请求取消、去重、缓存和失效；长列表用 **TanStack Virtual**；结果表用 **TanStack Table**（无样式）。 |
| D5 | 样式使用**自有 CSS 加设计变量 v2**（G4 确认）。不使用 Tailwind、CSS-in-JS 或带样式的组件库。**CSP 不放宽**：仍为 `script-src 'self'`、`style-src 'self'`，不允许运行时注入 `<style>`。 |
| D6 | 开发与构建使用 **Vite**：开发时热更新，生产构建离线产物，由 `scripts/build-workbench-assets.mjs` 放入 `apps/server/dist/web`。02 的技术验证不通过时，退回 esbuild 加 JSX。 |
| D7 | 不引入路由库。以新版 `/` 入口与当前 `view`、`query`、`sort`、`literature`、`reader` 参数为准；撤销 `/next` 路由、旧 `workspace` 别名与旧偏好键回退/迁移。当前React偏好和业务固定来源合同保留。 |
| D8 | 阅读引擎保留为框架无关模块，由 React 组件通过 ref 包装：PDF.js 渲染、Markdown 与 KaTeX 渲染、续读传输（`apps/web/src/reading/`）。G3 的性能口径不得退化。 |
| D9 | **不改**服务端 API、读取合同、证据合同和业务语义。确需新增接口时按 ADR 0033 同步 CLI/MCP，并单独说明。 |
| D10 | 视觉上保留原型的布局、四主题、主色、18/20/17 px 字号、40 px 控件、证据荧光笔；组件层按设计语言 v2。`prototype.html` 字节不变。 |

## 不变量（所有块）

- 查询和浏览不生成新材料，也不触发模型或解析；加工操作都要显式确认。
- 旧 artifact、新 result、文档 ID 不混用；证据固定版本。
- 客户端偏好不成为文献事实。
- 迟到或被取消的响应不污染当前视图。
- 读取失败不回滚已加载的正文。
- 状态先改变，动画只是装饰。“减少动效”下所有状态立即完成。不对宽高、位置做布局动画，布局变化用 FLIP（transform）。
- 只维护新版界面和当前React偏好；不恢复旧入口、旧URL别名或旧偏好迁移。业务数据与证据兼容不属于本次撤销范围。
- 测试迁移不得删除或弱化业务断言（见 05 的测试迁移规则）。

## 执行流程

**单个页面的标准循环**（06–09 中每个页面都这样执行）：
1. 从功能对等清单中取出该页的能力条目，以及对应的旧测试文件。
2. 截取旧界面的现状，做出样稿（或按 G6 已确认的规则直接实施）。
3. 只用 04 的组件和 05 的数据层实现，不手写控件样式，不直接调用 `fetch`。
4. 按 05 的规则把旧测试迁移为新测试，断言的业务含义保持不变，并新增交互测试。
5. 截图四主题和 1440 / 1024 / 390 三种宽度，与样稿并排比对。
6. 跑一致性测试与审计脚本。
7. 在块文件中勾选，并更新功能对等清单中该页的状态。

**并行运行期（已结束）**：旧界面曾提供 `/`，React通过 `/next/` 同源共享登录和API。GB之后正式入口为React `/`；Owner随后明确取消全部前端兼容，因此旧入口、旧URL别名、旧偏好读取回退及迁移一并撤销。现仅构建React前端，业务schema与固定证据读取不变。

**审计数据**：计算样式审计脚本在以下节点各跑一次，与基线并列，用数据证明“统一”：
- 03 的旧界面基线；
- 04 的组件画廊；
- 06–09 的每个页面；
- 11 的最终结果。

**证据位置**：截图与日志放在已被忽略的 `sandbox/runs/2026-10-19-web-experience/` 下，分为 `audit/`、`design/`、`gallery/`、`pages/`、`final/` 等目录。
