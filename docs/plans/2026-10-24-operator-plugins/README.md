# 计划 16：知识加工平台与研究任务

类型：计划
负责：知识加工平台、预置算子与研究任务组合的执行、审阅点与交接
状态：Ready（2026-11-10 按 ADR 0059、ADR 0060 与修订后接受的 ADR 0044 重排；G-adr 已通过；01 可开工；尚无实现）

## 目标

把文献的文本（初稿或校订稿）加工成有类型、可核查的知识。人和 Agent 是并列的服务对象（[ADR 0059](../../architecture/decisions/0059-general-literature-knowledge-base.md) 第 2 节）：

- 人在 Web 上发起加工，读结果页面，从页面回到原文核对，导出带出处的结果；
- Agent 经 CLI 和 MCP 发起加工，按层读取结构化的结果，沿证据展开到原文；
- 两者经过同一组检查点，取用同一份结果；几万篇的批量加工由服务端并发完成。

具体要求：

- 研究任务能被自然承接：“比较这批论文在不同条件下的结果”“这批论文怎样回答某个问题”交付可核查的结果；研究问题和提取规范从逐篇阅读那一步就生效。
- 预置算子与形态覆盖总结、问答、提取、问题综合、记录比较、发表统计、主题维基、实体归一与关系图谱。
- 算子只依赖实际需要的材料：有初稿或校订稿就能加工正文，只有书目也能做摘要筛查；标签等库整理条件不阻断正文分析。
- 算子绝不自动执行：每次付费运行都经过选取、授权、估算与确认，花费与用时开始前可知，成本可控制。
- 每种产出类型同时交付三样：人读的页面、Agent 按层读取的结构、带出处的导出（规格 8.12）。人或 Agent 自制的声明式算子不用改执行、保存与界面机制。

优先交付两条用户路径：

1. **问答闭环**：人或 Agent 对一批论文提一个问题，得到带证据的回答与综合。由 [02](02-question-synthesis.md) 首先交付。
2. **学一个领域**：人从主题页读到单篇论文，再读到原文中的依据，并原路返回（需求用3）。由 [12](12-topic-pages.md) 首先交付。

## 背景与诊断

2026-10-24，Owner 转来 Codex 会话“审视 PDF 获取后的算子设计”的评价；Claude 独立审查，并与该会话（gpt-6-astra，max）讨论六轮（往来原文：本机 `sandbox/prompts/operator-design-review-*.md`）。双方一致认为结果怎样保存、怎样复用做得扎实，任务设计薄弱。已在代码中核实：

1. `knowledge-synthesis@2` 的逐篇步骤写死为 `summary` 概览、不带问题，用户问题只进入最后一次汇总；
2. 单篇输入一律要求 `READY`，而 `READY` 包含“必填元数据齐全”和“有标签”；
3. 持续阅读会话（读全文、看图、检索、回查）只有总结能用，执行器按 `p.id === "summary"` 放行，问答和提取只能切块单次调用；
4. 综合只输出带引用的文字，记录不能进入综合，ADR 0037 承诺的表格没有实现；
5. 综合本身不记录读取，有成员不完整时整份被记成 `none`，`require-all` 不满足时返回空结果；
6. `summary` 的问题模式与 `labels` 是两个重叠的问答，`labels` 又与标签词表撞名；
7. 快照逐篇处理是串行循环；快照成员上限 10000 篇。

2026-11-10 的事实（ADR 0060 背景）：库里 35,227 篇书目，926 篇有全文，3 篇完成建档。按旧规定（只读 `READY` 文献的校订稿），平台只能在 3 篇上运行。因此按需材料门槛（04）排在问答闭环之前，并按 ADR 0060 读取初稿；估算现在只有 token 用量的历史，没有单元用时的记录。

讨论中的初发现，各块都不得偏离：执行与保存成熟、任务设计薄弱；问题决定逐篇读什么；库管理不阻断正文分析；维持少量明确机制，不做任意依赖图、配方语言或插件平台；以上述比较任务为判断标准。

演变：

- 2026-10-24：Owner 决定保留算子并插件化，底层平台加总结、问答、提取三个内置算子。
- 2026-10-26：第四轮定案，暂只做三种产出类型与两个固定组合。
- 2026-10-28：第五轮定案选取与固定流程；Owner 决定“做全，做完再看效果”，第六轮把问题形式化：封闭的七种产出类型、五种预置执行形态、类型到视图的封闭注册表。Owner 同意第六轮定案，并同意预算采用软上限（只停止派发新单元，不截断正在阅读的单篇）与“各块验工程、成套验效果”的验收节奏。
- 2026-11-10：产品重新定位为人和 Agent 并列的通用文献知识库（ADR 0059）；全文分初稿与校订稿两级（ADR 0060）；ADR 0044 按两者修订后接受。计划据此重排，见“进度”。

## 验收节奏

- **各块验工程**：退出条件用合成 fixture 与 fake 模型证明机制、合同与界面行为；审阅点 A–C 看截图与行为说明。
- **成套验效果**：真实论文上的质量、成本与可用性，在 11 用一批真实文献把全部组合跑通后统一评估（G-real、G-lib）。块内的真实小样本只用于发现明显问题，不作为效果结论。
- **基准与效果检查点**：效果不等到 11 才第一次看。
  - 开工前建立基准：Owner 选定 10–20 篇真实校订稿与 2–3 个研究问题（至少一个是“比较这批论文在不同条件下的结果”一类的记录比较）；论文最好来自至少两个差别明显的学科，便于 11 的 11.3 复用。总设计师 把论文冻结成快照（G-lib），起草期望答案与期望记录，Owner 核对后作为后续各次对比的同一把尺子。基准的文献与期望答案只存本机 `sandbox/benchmarks/plan16/`，不进仓库。
  - E0（01 之后）：`summary@3` 与 `summary@2` 在基准上对比，只用于发现会话迁移的退化。
  - E1a（02 之后）：问题综合在基准上对照期望答案。读不准时先退回 01–02 改会话与问答，不开工 12。
  - E1b（03 之后）：记录比较在基准上对照期望记录。读不准时先退回 03（必要时 01），不开工 05、08、09、10。
  - 04、06、07、13 不依赖阅读质量，不受 E1a、E1b 约束。
  - 每次对比的方法：同一基准快照，算子升版本后重跑；总设计师 用 `sandbox/` 脚本导出两版结果逐篇逐条对照，结合结果中已有的覆盖、逐值核对状态、未定比例与用量；人工把条目标为对、错、不确定，错因归为漏读、误读、证据不符、格式四类，再决定改哪一层。这些脚本是评估工具，不进产品；某项做法验证有效后，再按派活规则交实施者落实。
  - 基准运行每次单独授权；E0、E1a、E1b 的结论只陈述基准样本。
- 某块工程验收不通过，不进入依赖它的块；效果评估发现问题，交 总设计师 判断退回哪一块。
- 未获 G-real、G-lib 授权时，计划只能标为“工程完成、效果待验”，不能宣称成套验收完成。

## 范围与非目标

范围：规格第 8 节的全部内容，即合同与结果外壳、七种产出类型（分块交付）、公共阅读会话、`summary@3`、`qa@1`、`records@3`、按需材料门槛与文本等级、运行流程与选取、估算与单元用时、预算与授权、快照拆分与跨快照的覆盖合计、汇总与命名组合、发表统计、主题分组与维基页面集、实体归一、关系图谱、声明式算子、视图注册表、分层读取、带出处的导出、机器接口、对应 Web 页面与指南。

非目标：

- 不做任意依赖图、配方语言、自动循环、外部代码插件或用户代码沙箱；
- 不做通用产出形态扩展协议或插件自带界面；七种之外的产出类型须另经 ADR；
- 不做全量两两成对、仅按名称的实体合并（规格 8.15）；
- 不做单位换算、实验等价判定或领域合并规则（归下游）；
- 不读补充材料（首版只读正文）；
- 不改写、迁移或重算任何历史结果；
- 不形成初稿，不改初稿的标注与默认文本规则（计划 21）；不改建档流程、标签词表与 `READY` 的判定本身（只是不再用它做算子门槛）；
- 不建设长期 Agent 账户配额系统。

## 不变量

- 任何付费运行都不会自动发起：没有常驻规则，版本事件与阅读只标记过时；授权在第一笔花费之前。
- 人和 Agent 发起的运行经过同一组检查点，得到同一份结果；任一方发起的结果另一方都能取用。
- 历史结果在每一块完成时都仍可读、可导出、可作为证据，不依赖活动注册表；旧排队任务按原版本完成或终止。
- 执行器不按算子 id 分支；插件不提供校验代码或界面代码。
- 每个条目都能沿证据链回到证据根；空值有原因；“声明范围内未得出答案”不写成“论文未报告”。
- 每份结果记录每篇输入读的文本等级；依据初稿的结论不冒充依据校订稿。
- 覆盖与判断分开记录：不把部分读取报成完整，不把未定报成排除，不把候选报成已确认。
- 运行不静默截断；超出容量时明确报缺口；预算停止时如实报告未处理单元。
- 测试只用合成 fixture 与 fake 模型，不连接正式库，不调用真实 Provider、模型或 MinerU；真实模型须 G-real，正式库须 G-lib。
- 测试只因选择器或文案变化而改写，断言目的不变。

### 排序依据

问答闭环与主题页面最早在哪里交付，由下面这些依赖决定。

能拆开的依赖，已经拆开：

- 原 04 中依赖 02 的 Task（按结果筛选、已有结果与常备产物、刷新与复核）移到新块 13，04 因此只依赖 01，可以排在 02 之前。
- 主题页面只需要逐篇问答、汇总与派生：论文页规范用 `qa` 的 `text` 答案，不需要 `records`，因此新块 12 不依赖 03。
- 分组提议在 06 之前按 02 的方式由所有者逐次确认，06 之后计入账本，因此 12 不依赖 06。
- E1 拆成 E1a（问答）与 E1b（记录比较）：12 只等问答的效果检查，不等记录比较。
- 原 08 的维基拆成 12（论文页、主题页、页面集）与 08（其余页面类型、增量更新）。

不能拆开的依赖：

- 02 依赖 01：`qa@1` 跑在公共阅读会话上，结果用新合同。
- 02 依赖 04 退出 A：摘要筛查要求快照收入只有书目的文献并冻结它们的元数据（4.4）；结果的覆盖要如实报告缺材料（4.2）；不按材料准入，库里只有 3 篇能被加工。
- 04 的初稿部分依赖计划 21：初稿的版本、核对依据、默认文本与读取合同都由计划 21 交付。计划 21 之前问答闭环只在校订稿上成立。
- 12 依赖 02：问答、汇总、运行流程、结果页外框、分层读取与导出都在 02。
- 12 依赖 07 的 7.2：页面清单的组装是派生，派生执行器在 07。
- 12 依赖 E1a：这是 Owner 定下的效果门槛（不在读不准的问答上铺开页面），须 G-real、G-lib 授权，不是技术依赖。
- 万篇规模依赖 06：大批量运行在账本与软上限之前不开放；拆分与覆盖合计依赖 04 的快照与 07 的派生。
- 05 依赖 03：声明式算子的三种产出类型要先由内置算子验证。
- 08 依赖 03：方法页与论断页的规范基于 `records`。
