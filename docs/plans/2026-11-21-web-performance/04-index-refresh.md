# 04 · 搜索索引只处理变化

类型：计划（结果块）
负责：大批量写入期间，搜索索引能跟上写入，不再长期占满一个 CPU
状态：Pending（等 D2）

## 原因

- 每次刷新先调用 `scanChanges`（`apps/server/src/storage/sqlite/retrieval-engine.ts`），把全库每篇文献的“当前版本”与“已索引版本”全部读出来逐篇比对，找出变化的文献，再处理它们。18.8 万篇时光比对就约 11 s。
- 写入不停，刷新就一轮接一轮；4174 里一个线程长期 100% CPU 就是它。修订号相差 215 万，不代表有那么多篇没进索引。
- 前端 `IndexLine` 在索引落后期间每 2 s 读一次状态（读的是状态文件，本身不重）。

性质：设计问题（D2）。找变化靠全量比对，而不是写入时记下的变更。

## Outcome

- 刷新的耗时与变化的篇数成正比，与库的总篇数无关。
- 持续写入期间，索引落后保持在 01.3 定下的范围内。
- 搜索结果与全量重建的结果一致（现有的 `verify` 仍是全量检查，作为维护操作保留）。

## 进入条件

D2 的决定。记录变更多半要加表，需要迁移，随 10.3 上线；不需要迁移的减负（例如写入高峰时把刷新间隔拉长、合并刷新请求）可以先做。

## 责任边界

- 后端。规格：[查询技术篇](../../architecture/technical/06-retrieval-context.md)的索引一节。

## Tasks

D2 决定后补齐。至少包括：实现、与全量重建的一致性测试、二十万篇合成库上边写边刷新的测试、迁移（若需要）。

## 退出条件

10.1 复测中，CLI 入库期间索引落后在目标范围内，4174 没有长期满载的线程。
