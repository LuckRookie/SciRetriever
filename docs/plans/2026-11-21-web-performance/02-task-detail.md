# 02 · 运行中任务的详情

类型：计划（结果块）
负责：任务详情页刷新时不再把这个任务的全部来源记录重读一遍
状态：Pending

## 原因

- 详情接口每次都调用 `taskSourceResults`（`apps/server/src/application/source-statistics.ts`），把这个任务的全部来源记录按每页 1000 条读完，再在内存里汇总成按来源的几行合计。Suzuki 任务有 17 万多条，一次约 19 s。
- 任务运行时，详情页每 2 s 刷新一次（`apps/web/src/app/features/tasks/Tasks.tsx` 的任务详情查询）。诊断里写的 5 s 是外壳任务列表的刷新间隔。
- 这些读取和其他 Web 读请求排在同一个工作线程上（见计划 README 的“共同机制”）。

性质：缺陷。结果只是合计，没有理由每次从头算；刷新间隔比查询本身还短。

## Outcome

- 运行中大任务的详情接口耗时与来源记录的条数无关（目标见 01.3；在目标定下前，以“17 万条时 1 s 以内”作为临时口径）。
- 返回的合计与现在逐条重算的结果完全一致。
- 页面刷新不会叠起请求：上一次没返回时不发下一次；查询变慢时刷新间隔随之拉长。

## 进入条件

G-dispatch。不需要迁移。

## 责任边界

- 后端：02.1、02.2。前端：02.3。
- 不改：来源统计页（全库、按时间范围）的口径；任务详情的返回结构。

## Tasks

- [ ] **02.1 增量合计**：在服务进程内按任务缓存合计与已读到的记录位置，下次只读新增的记录；记录被删除或快照不连续时整读一次重建。说明：若实施者查明有更简单、同样正确的办法（例如在写入时已有可用的合计），在汇报里说明并采用。
- [ ] **02.2 测试**：合成一个十万条来源记录的任务，断言第二次读取只读新增部分、合计与整读一致；任务结束后合计不变；并发写入下合计不丢不重。
- [ ] **02.3 刷新节奏**：任务详情与任务列表的刷新在请求未返回时不重发，间隔按上次耗时拉长（例如不小于上次耗时的 2 倍），任务结束后停止。
