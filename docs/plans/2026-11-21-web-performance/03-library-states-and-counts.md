# 03 · 文献状态与全库计数

类型：计划（结果块）
负责：全库计数与按状态筛选在二十万篇、有写入时也能很快出来
状态：Pending（等 D1）

## 原因

- 计数 SQL 对每篇文献调用自定义函数 `sr_status`（`apps/server/src/storage/sqlite/library-page.ts` 的 `libraryCounts`）。函数取的是内存里的状态缓存 `LibraryStateCache`（`library-state-cache.ts`）。
- 缓存在两次读取之间有不超过 64 篇变化时只补算这几篇；超过 64 篇，或变更记录缺失时，把全库 18.8 万篇的状态在 JS 里重算一遍。
- CLI 每秒入库约 2.7 篇，两次读取之间几乎总超过 64 篇，所以写入期间每次计数都要整库重算。诊断用 CLI 测的 7.3 s 是冷启动，正好是一次整库重算。
- 外壳一打开就读计数；按状态筛选和“暂无 PDF”筛选也要这个缓存。

性质：设计问题（D1）。状态是“每次从全量数据推算”的投影，这个做法到二十万篇、持续写入时撑不住。

## Outcome

- 全库计数、按状态筛选的耗时达到 01.3 的目标；与现在的结果一致。
- 写入期间计数不再触发整库重算。

## 进入条件

D1 的决定。若决定把状态存进库里，需要迁移，随 10.3 上线；不需要迁移的减负（例如补算阈值随批量调整、按变更记录分批补算）可以先做。
