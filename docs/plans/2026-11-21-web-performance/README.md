# 计划 26：二十万篇下的 Web 性能

类型：计划
负责：文献库接近二十万篇、同时有大批量写入时，Web 的计数、任务详情、搜索索引、读请求排队与打开 PDF 的耗时；以及长时间引用扩展的断点续跑与来源冷却
状态：In progress（2026-11-21 计划编写完成；设计问题 D1–D7 待与 Owner 讨论；实施未开始）

## 目标

Owner 2026-11-21：“当数据库变多之后，现在已经快接近20w了。整个使用体验变得非常差，非常卡。除此之外还有一点是打开PDF的时候也有点慢，这部分一定要进行优化。web端是我们的门面，是重中之重，各项使用方面一定要优化。”

完成后：在约二十万篇、并有一个引用扩展任务持续写入的正式库上，Web 的常用操作达到 D7 定下的目标耗时；有一组可重复运行的性能检查，以后的改动不会悄悄退回去。

## 来源与已知事实

- 现场诊断：`sandbox/reports/2026-11-21-web-performance-at-188k/README.md`（执行会话 2026-11-21 只读测量：187,565 篇，catalog 4.8 GB，WAL 557 MB，同时有 CLI 引用扩展每秒入库约 2.7 篇）。
- 总设计师 2026-11-21 对照代码查出的原因写在各块的“原因”一节。
- 万篇规模的上一次测量：[计划 25 的 20.8](../2026-11-16-before-processing/20-scale-mechanics-check.md)（一万篇、无并发写入时三次读取 373 / 155 / 119 ms）。那次检查没有覆盖“边写边读”和十万篇以上。

**共同机制（推断，待 01 实测确认）**：4174 的 Web 读请求由一个 SQLite 工作线程依次处理（`apps/server/src/storage/sqlite/worker.ts` 的 `new Worker`）。全库计数（03）与运行中任务的详情（02）都要读全库或整个任务，在写入期间反复执行；翻页、打开 PDF 等短请求排在它们后面。搜索索引的刷新（04）有自己的工作线程，但它的全量比对让一个 CPU 长期满载，并和其他读请求一起把 WAL 撑大。

## 与正在运行的引用扩展的关系

执行会话（local_d7744f16）在 4174 之外用 CLI 跑 Suzuki 1995 的两层前向引用扩展（`processing-2b51707b…`），使用构建目录 `candidate-56d843ab549c`，2026-11-21 估计还要 2 到 4 天。

- 改代码、提交、不带迁移的 4174 部署不影响它；每次部署前仍先问执行会话，部署单写明不得删除或重建它的构建目录。
- 带 schema 迁移的部署必须先由执行会话结束它的进程。按现状，结束后续跑会从种子重来（见 08）。
- 因此：**不需要迁移的改动先做先上线；需要迁移的改动（可能来自 D1、D2、D5）合成一次迁移**，等 Suzuki 任务跑完，或 Owner 决定先停它。

## 不变量

- 计数、筛选与搜索的结果和现在一致；只改快慢，不改含义。已有测试里的结果断言不放宽。
- 已接纳的数据不丢失；中断后能继续（[计划 25 的不变量](../2026-11-16-before-processing/README.md#不变量)照旧）。
- 打开 PDF 仍然只显示与记录一致的文件；D4 若放宽“先校验后显示”，必须写明校验失败时页面怎么办。
- 部署不碰执行会话的进程、构建目录与 catalog。
