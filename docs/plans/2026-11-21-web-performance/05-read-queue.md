# 05 · 读请求排队与 WAL

类型：计划（结果块）
负责：短请求（翻页、打开一篇、读 PDF）不被长操作挡住；WAL 能收缩
状态：Pending（等 D3；02–04 之后复测再定范围）

## 原因

- Web 的读请求由一个 SQLite 工作线程依次处理（`apps/server/src/storage/sqlite/worker.ts`）。一个 7 s 的计数或 19 s 的任务详情在跑时，其他请求都要等。
- WAL 涨到 557 MB 不收缩：长时间的读（02、03、04 的全量读取）加上两个进程同时写，checkpoint 一直做不完。

性质：排队是设计问题（D3）；WAL 是 02–04 的结果，先不单独处理。

## Outcome

- 01.3 目标中的短请求，在有长请求同时进行时仍在目标内。
- 没有写入高峰时，WAL 能回到较小的大小。

## 进入条件

D3 的决定；02–04 上线后用 01 的方法复测，若排队已不明显，本块可以缩小或经 Owner 取消。

## 责任边界

- 后端。

## Tasks

D3 决定后补齐。候选方向（供讨论）：增加只读工作线程；按请求类型分开排队；给长请求设上限、分段执行。WAL：确认 checkpoint 设置，必要时在空闲时执行一次 `TRUNCATE`。

## 退出条件

10.1 复测中，长请求进行时短请求仍在目标内；WAL 在空闲后收缩。
