# 12 · 引用扩展从断点续跑

类型：计划（结果块）
负责：长时间的引用扩展中断后从中断处接着跑；扩展规模不受内存限制
状态：Done（待部署）

## 现状

- 待查队列（frontier）与已查记录（visited）只在内存里（`apps/server/src/entry/discovery.ts`）。
- 中断后续跑会从种子重新开始：不丢数据、不重复入库，但已花的时间要重花一遍。执行会话已核实：含能综述任务续跑后，种子在 2026-11-20 07:01Z 被重新查询。
- 两层前向扩展的待查队列可以有几十万到几百万项，放在内存里会随规模涨。

性质：设计问题（B9）。

## Outcome

- 中断（停服、重启、手动中断）后续跑，从保存的进度接着跑；已查过的文献不再查询。
- 待查队列与已查记录在库里，内存占用与扩展规模无关。
- 保存进度不影响已有的“不丢数据、不重复入库”。

## 进入条件

B9 的决定。若库里已有的每篇查询记录足以还原“已查过哪些”，可能不需要新表；否则加表，上线方式同 04。

## 责任边界

- 后端。规格：[任务协调 5.2](../../architecture/technical/02-task-coordination.md#52-并发中断与恢复)。

## Tasks

- [x] **12.1 查证**：现有记录能否还原已查集合与待查队列，写明结论。
- [x] **12.2 进度**：做法见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 6 节第 9 条。每查完一篇，在写入其结果的同一事务里记下“已查”并更新待查队列（12.1 查明现有记录够用时复用，否则按 11 的方式加表）。
- [x] **12.3 续跑**：续跑从保存的待查队列开始，不再从种子重来。
- [x] **12.4 测试**：在若干位置中断后续跑，断言不重复查询、结果与一次跑完一致；百万项待查队列时进程内存不增长。

## 进度

- 2026-11-22：12.1–12.4 完成（后端实施者，一轮）。12.1 的结论：10.4 的 `citation-write-checkpoint` 加上任务的种子足以还原队列，不加表，结构与指纹不变。做法写进[任务协调 5.2](../../architecture/technical/02-task-coordination.md#52-并发中断与恢复)。在一篇查到一半、刚记下“已查”、一层刚结束三处中断后续跑：只有第一种多查当时那一篇，其余与一次跑完的调用序列相同，业务表逐字段相同。百万项待查队列：重放 12.6 s，RSS 126 MiB（1 万项时 99 MiB）。总设计师复跑见提交说明，`pnpm build` 通过。报告 `sandbox/reports/2026-11-22-discovery-resume/REPORT.md`。
- 正在跑的 Suzuki 任务由旧版本开始，没有检查点；换到新版本后续跑会从种子重来一轮（与现在相同）。所以部署要等它跑完，不要中途切换。
- 残余：续跑的重放耗时与该任务的检查点条数成正比（百万项 12.6 s），只在启动时发生。扩展结束时的最终发布仍是一个事务，百万条结果时持有写许可多久没有实测，归 14.2。

## 退出条件

合成来源上的引用扩展在中断后续跑，查询次数与一次跑完相同。
