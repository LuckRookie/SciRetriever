# 计划 26：千万篇规模的文献库与 Web

类型：计划
负责：让文献库在百万到千万篇、并有持续大批量写入时仍然好用：规模目标与原则；状态、计数、翻页、搜索、读请求、打开 PDF、入库吞吐、迁移方式；长时间引用扩展的断点续跑与来源冷却
状态：In progress（2026-11-21 计划编写完成；立意 A1–A3 与设计问题 B1–B11 已定；ADR 0065 待 Owner 审定；实施等 G-dispatch；实施未开始）

## 目标

Owner 2026-11-21：

- “当数据库变多之后，现在已经快接近20w了。整个使用体验变得非常差，非常卡。除此之外还有一点是打开PDF的时候也有点慢，这部分一定要进行优化。web端是我们的门面，是重中之重，各项使用方面一定要优化。”
- “立意的时候不要只想着20w，之后我们会有更多的数据呢？别忘了我们数据库是要为了大批量的文献数据所设计的，以后说不定会有很多，百万千万都不一定。所以这部分的优化一定要设计好。”

因此本计划不以“二十万篇时够快”为目标，而是**让常用操作的耗时不随库的总篇数增长**，并在百万、千万篇的合成库上验证。[需求](../../architecture/requirements.md)现在写的是“文献库以万篇起步并持续增长”，规模目标要随 A1 改写。

## 来源与已知事实

- 现场诊断：`sandbox/reports/2026-11-21-web-performance-at-188k/README.md`（执行会话 2026-11-21 只读测量：187,565 篇，catalog 4.8 GB，WAL 557 MB，同时有 CLI 引用扩展每秒入库约 2.7 篇）。
- 总设计师 2026-11-21 对照代码查出的原因写在各块的“现状”一节。
- 上一次规模测量：[计划 25 的 20.8](../2026-11-16-before-processing/20-scale-mechanics-check.md)，一万篇、无并发写入，三次读取 373 / 155 / 119 ms。它没有覆盖边写边读，也没有覆盖十万篇以上。

**现状的共同问题**：好几处做法的耗时或内存与全库篇数成正比，在万篇时看不出来，到二十万篇加上持续写入就卡了，到百万、千万篇会完全不可用：

| 做法                                                 | 与总篇数的关系               | 块  |
| ---------------------------------------------------- | ---------------------------- | --- |
| 文献状态每次在内存里由全量数据推算，整库投影常驻内存 | 时间、内存都是 O(N)          | 04  |
| 计数、分面、列表总数每次扫过整个筛选结果             | O(结果数)，不筛选时就是 O(N) | 05  |
| 部分排序先把全部匹配行取出再排序，再翻页             | O(结果数)                    | 06  |
| 搜索索引每次刷新把全库的版本逐篇比对                 | O(N) 每次刷新                | 07  |
| 运行中任务的详情每次重读任务的全部来源记录           | O(任务记录数)                | 03  |
| 所有 Web 读请求排在一个工作线程上                    | 任何一个长请求挡住全部短请求 | 08  |
| 引用扩展的待查队列与已查记录只在内存                 | 内存 O(扩展规模)，中断即丢   | 12  |
| schema 迁移停服、整库离线改写                        | 停服时间 O(N)                | 11  |
| 入库每条约 0.4 s CPU、每秒 2 到 3 条                 | 一千万篇要一个多月           | 10  |

## 与正在运行的引用扩展的关系

执行会话（local_d7744f16）在 4174 之外用 CLI 跑 Suzuki 1995 的两层前向引用扩展（`processing-2b51707b…`），使用构建目录 `candidate-56d843ab549c`，2026-11-21 估计还要 2 到 4 天。

- 改代码、提交、不带迁移的 4174 部署不影响它；每次部署前仍先问执行会话，部署单写明不得删除或重建它的构建目录。
- 带 schema 迁移的部署必须先由执行会话结束它的进程；按现状，结束后续跑会从种子重来（见 12）。
- 因此：不需要迁移的改动先做先上线；需要迁移的改动合成一次迁移（14.3），等 Suzuki 任务跑完，或 Owner 决定先停它。B8 定下以后，往后的迁移不再需要停任务。

## 不变量

- 计数、筛选与搜索的含义不变；B2、B4 若引入“一万以上”或“只取前若干条”，界面必须如实说明，不把截断的数当准确数。
- 已接纳的数据不丢失；中断后能继续（[计划 25 的不变量](../2026-11-16-before-processing/README.md#不变量)照旧）。
- 打开 PDF 仍然只显示与记录一致的文件；B6 若放宽“先校验后显示”，必须写明校验失败时页面怎么办。
- 部署不碰执行会话的进程、构建目录与 catalog。
