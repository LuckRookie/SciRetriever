# 08 · 读请求分道与耗时上限

类型：计划（结果块）
负责：短请求不被长请求挡住；每类请求有耗时上限；WAL 能收缩
状态：Pending（等 B5）

## 现状

- Web 的读请求由一个 SQLite 工作线程依次处理（`apps/server/src/storage/sqlite/worker.ts`）。一个 7 s 的计数或 19 s 的任务详情在跑时，翻页、打开 PDF 都要等。
- WAL 涨到 557 MB 不收缩：长时间的读加上两个进程同时写，checkpoint 一直做不完。

性质：排队是设计问题（B5）。04–07 去掉长请求以后排队会减轻，但只要将来有一个请求变慢，所有请求仍会一起变慢；分道与上限是兜底。

## Outcome

- 短请求与长请求分开排队（例如另开只读工作线程跑长请求）。
- 每类请求的耗时上限写进规格；超过上限的请求在日志与性能检查中报出，作为缺陷处理。
- 没有写入高峰时，WAL 能回到较小的大小。

## 进入条件

B5 的决定。不需要迁移。

## 责任边界

- 后端。

## Tasks

B5 决定后补齐。至少包括：请求分类、分道实现、长请求进行时短请求耗时的测试、checkpoint 设置的确认与空闲时收缩。

## 退出条件

14.2 中长请求进行时短请求仍在目标内；WAL 在空闲后收缩。
