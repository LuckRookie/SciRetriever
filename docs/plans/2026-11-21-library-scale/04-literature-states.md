# 04 · 文献状态写入时维护

类型：计划（结果块）
负责：文献状态不再每次由全量数据推算，也不再把整库的状态投影放在内存里
状态：Ready（设计已定，等 G-dispatch）

## 现状

- 计数与按状态筛选对每篇文献调用自定义函数 `sr_status`（`apps/server/src/storage/sqlite/library-page.ts`），函数取的是内存里的整库状态投影 `LibraryStateCache`（`library-state-cache.ts`）。
- 两次读取之间变化不超过 64 篇时只补算这几篇；超过就把全库状态在 JS 里重算一遍。CLI 每秒入库约 2.7 篇，写入期间几乎每次都整库重算。诊断用 CLI 测的 7.3 s 是冷启动，正好是一次整库重算。
- 投影常驻 4174 的进程内存，大小与总篇数成正比。

性质：设计问题（B1），违反 A2 的“耗时与内存不随总篇数增长”。提高 64 的上限只能缓解：计数 SQL 仍要对每篇调用一次 JS 函数。

## Outcome

- 状态随写入在同一事务里维护，存在库里，有索引；按状态筛选是普通的索引查询。
- 状态与现有推算逐篇一致；推算依赖的配置（标签上限、建档方式）改变时，状态在后台按批重算，期间界面如实显示“正在更新”。
- 进程内不再有整库投影。

## 进入条件

B1 的决定（已定，见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 5 节）。需要加表加列，按 11 的方式（或在 11 定下前并入 14.3）上线。

## Tasks

做法见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 5 节第 1 条。

- [ ] **4.1 维护点清单**：列出所有会改变文献状态或缺失步骤的写入（入库、PDF 接纳、解析、建档、校对、撤回、标签、设置变更等），与 `deriveCurrentState` 的输入逐项对上。
- [ ] **4.2 存储与维护**：状态与缺失步骤存成列或表并建索引；4.1 的每个写入在同一事务里更新它。按 11 的方式加表、回填。
- [ ] **4.3 设置变更**：标签上限、建档方式改变时在后台按批重算；期间计数与筛选返回“正在更新”的标记，前端显示。
- [ ] **4.4 去掉整库投影**：`sr_status`、`sr_missing` 与 `LibraryStateCache` 改为读存储的状态，进程内不再有整库投影。
- [ ] **4.5 测试**：与现有推算逐篇比对的一致性测试（含并发写入、撤回）；百万篇合成库上按状态筛选的耗时与进程内存，和一万篇相比。

## 退出条件

14.2 的规模检查中，按状态筛选的耗时与内存不随总篇数增长。
