# 04 · 文献状态写入时维护

类型：计划（结果块）
负责：文献状态与“是否收进来”在写入时维护、存在库里；Agent 按状态取出待处理的一批，人的列表默认只显示收进来的文献；进程内不再有整库的状态投影
状态：Done（待部署）

## 现状

- 计数与按状态筛选对每篇文献调用自定义函数 `sr_status`（`apps/server/src/storage/sqlite/library-page.ts`），函数取的是内存里的整库状态投影 `LibraryStateCache`（`library-state-cache.ts`）。
- 两次读取之间变化不超过 64 篇时只补算这几篇；超过就把全库状态在 JS 里重算一遍。CLI 每秒入库约 2.7 篇，写入期间几乎每次都整库重算。诊断用 CLI 测的 7.3 s 是冷启动，正好是一次整库重算。
- 投影常驻 4174 的进程内存，大小与总篇数成正比。

性质：设计问题（B1），违反 A2 的“耗时与内存不随总篇数增长”。提高 64 的上限只能缓解：计数 SQL 仍要对每篇调用一次 JS 函数。

## Outcome

- 状态随写入在同一事务里维护，存在库里，有索引；按状态筛选、按状态取出待处理的一批是普通的索引查询。
- 每篇文献记下是否收进来（[ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 2 节）：被明确选用过就是收进来的，只经由发现进入的不是；在选用发生的同一事务里写入，有索引。
- 状态与现有推算逐篇一致；推算依赖的配置（标签上限、建档方式）改变时，状态在后台按批重算，期间界面如实显示“正在更新”。
- 进程内不再有整库投影。

## 进入条件

B1、C2 的决定（已定，见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 6 节）。需要加表加列，按 11 的方式（或在 11 定下前并入 14.3）上线。

## 责任边界

- 后端。规格：[版本化存储](../../architecture/technical/07-versioned-storage.md)、[查询技术篇 2.1.8](../../architecture/technical/06-retrieval-context.md#218-文献库计数与全文取得情况)。

## Tasks

做法见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 6 节第 1 条。

- [x] **4.1 维护点清单**：列出所有会改变文献状态或缺失步骤的写入（入库、PDF 接纳、解析、建档、校对、撤回、标签、设置变更等），与 `deriveCurrentState` 的输入逐项对上；再列出构成“选用”的写入（导入、浏览时收藏、加标签、放进集合、打开阅读、提供或要求全文、发起加工），查清每种写入现在是否已留下可以回填的记录。
- [x] **4.2 存储与维护**：状态、缺失步骤与“是否收进来”存成列或表并建索引；4.1 的每个写入在同一事务里更新它。按 11 的方式加表；已有文献按 4.1 查到的记录回填，查不到选用记录的按只被发现处理，并在报告里写明各有多少篇。
- [x] **4.3 设置变更**：标签上限、建档方式改变时在后台按批重算；期间计数与筛选返回“正在更新”的标记，前端显示。
- [x] **4.4 去掉整库投影**：`sr_status`、`sr_missing` 与 `LibraryStateCache` 改为读存储的状态，进程内不再有整库投影。
- [x] **4.5 列表默认范围**：文献库列表、CLI 与 MCP 的列表默认只列收进来的文献，可以显式改为全部；搜索照旧覆盖全库，结果里标明哪些是只被发现的。合同、页面规格与命令说明同步。
- [x] **4.6 测试**：与现有推算逐篇比对的一致性测试（含并发写入、撤回）；每种选用写入后文献变为收进来的；百万篇合成库上按状态取一批、按状态筛选的耗时与进程内存，和一万篇相比。
