# 11 · 不停服的迁移方式

类型：计划（结果块）
负责：schema 变化不再需要停服、整库离线改写
状态：In progress（11.1–11.4 完成；11.5 回填让行实施中）

## 现状

现在的 schema 迁移（v12–v19 的迁移脚本）都是停服、备份、离线整库改写。停服时间随库的大小增长；一千万篇（按每篇 25 KB 约 250 GB）会要几个小时，并且每次都要先停正在跑的长任务。

性质：设计问题（B8）。

## Outcome

- 迁移的规则写进[版本化存储](../../architecture/technical/07-versioned-storage.md)：只加表、加列、加索引；需要的数据在后台按批回填，回填期间旧路径照常工作；回填完成后才切换读取。
- 不能这样做的变化（例如改列含义）登记为例外，写明停服时间的估计，并经 Owner 同意。
- 04、05、07、12 需要的结构变化尽量按这个方式上线。

## 进入条件

B8 的决定（已定，见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 6 节）。

## 责任边界

- 后端；规格由总设计师改写。

## Tasks

做法见 [ADR 0065](../../architecture/decisions/0065-scale-rules.md) 第 6 节第 8 条与第 3 节第 5 条。

- [x] **11.1 规格**：迁移规则写进版本化存储：加表、加列、加索引；后台回填；回填完成后切换读取；例外的登记与审批。
- [x] **11.2 旧版本兼容**：旧版本打开带有新增表的库时照常工作；查明现有的 schema 指纹检查哪里会拒绝打开，按规则放宽，并有测试。
- [x] **11.3 回填框架**：按批回填、记录进度、中断后继续，回填期间读写一致。
- [x] **11.4 测试**：百万篇合成库上回填的耗时与对前台请求的影响；回填中途中断再继续。
- [ ] **11.5 回填让行**：前台有写入在等时回填不取下一批，单批持有写许可有上限；1m 回填期间入库不低于每秒 90 篇、短读 P95 不变差。

## 退出条件

一次实际的结构变化（例如 04 的状态列）按新方式在合成库上完成，前台请求在回填期间达到目标。
