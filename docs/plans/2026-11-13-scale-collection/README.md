# 计划 23：万篇规模的收集与验收

类型：计划
负责：需求收2“全文取得情况”的可见性与收4“万篇规模”的机制验收、真实运行与后续
状态：Pending（2026-11-13 计划编写完成；未开工；技术可行性未验证；功能未交付）

## 目标

[需求](../../architecture/requirements.md)的“收”要求文献库以万篇起步并持续增长（[收4](../../architecture/requirements.md#收4-规模与持续积累)），并能看到一个范围内全文的取得情况（[收2](../../architecture/requirements.md#收2-取得全文)）。2026-11-10 对 Owner 正式库的只读计数：35,227 篇书目，926 篇有 PDF，3 篇完成建档（[ADR 0059](../../architecture/decisions/0059-general-literature-knowledge-base.md)“背景”）。成规模的收集从未真正跑过。

本计划做四件事：

1. **收2 看得见**：对任意范围（全库、文件夹、入库批次、一次发现、保存的筛选），人和 Agent 都能看到三个数：多少篇已取得全文，多少篇还没有，其中多少篇已试完自动途径。
2. **机制验收**：用合成数据和本机的假来源，让至少一万篇文献走过入库、去重、获取、中断后继续、局部失败与库内查询，记录时长、吞吐、内存与磁盘（收4 验收行）。不联网，不需要授权。
3. **真实运行**：经 Owner 逐项授权，在他选定的范围、用他允许的来源取得全文，测出覆盖、失败分类、吞吐与“试完”的篇数，交 Owner 判断。
4. **从数字到后续**：把测出的缺陷变成后续任务或新的决定；收尾。

## 现状：收2 还缺什么

- **没有“全文取得情况”这三个数本身。** 计数按状态给出。“已取得全文”要由调用方把 `ASSET_READY`、`ARCHIVING`、`ARCHIVE_FAILED`、`READY` 加起来，`EXCLUDED` 怎样算没有规定；“还没有”是 `UNREVIEWED`；“已试完”是 `unavailable_pdf`。Web 的快速筛选“有 PDF”只是 `ASSET_READY` 一种状态，已建档的文献不在其中，所以 Web 上看不到“已取得多少”。
- **计数的单位没有规定。** 计数按具体版本（`Literature`）给出（[查询技术篇 2.2.1](../../architecture/technical/06-retrieval-context.md#221-libraryquery-与结果单位)）。收4 写“同一篇文献有多个版本时，默认只需要其中一个达到目标”：预印本没有 PDF、正式版有 PDF 的，现在算一篇已取得、一篇未取得。
- **计数合同不在规格里。** `LibraryCounts` 只在代码里，查询技术篇没有它的字段与含义。
- **按出版社的覆盖没有入口。** 来源统计按来源，不按出版社。收2 不要求按出版社显示；真实运行的评估要按出版社统计，用评估脚本在副本上算（05），是否做成产品功能由 06 交总设计师判断。
- **规模上没有验证过。** 计数的 SQL 对每行计算状态，在三万五千篇上的耗时没有测过。

## 范围与非目标

范围：全文取得情况的规格、读取与 Web 显示；万篇机制验收的测试与数据生成；一次经授权的真实获取运行与评估；后续任务与新决定的整理；收尾。

非目标：

- 上一节表中归其他计划的内容；
- 新的 PDF 来源、获取层级或浏览器能力；
- 按测出的数字自动调整获取顺序（来源统计只供人判断）；
- 为了“通过”设定吞吐、覆盖率的阈值。只有下面的不变量是硬性条件。

## 不变量

所有块、所有运行都必须保持（这些是硬性条件，违反即为缺陷）：

- **已接纳的数据不丢失**：已接纳的书目、来源记录、PDF 与关系，不因中断、重复运行、局部失败或另一来源失败而被删除或替换（需求可4、收2）。
- **中断后能继续**：再次运行从缺失的部分继续，不重做仍然有效的部分（收4）。
- **查询不触发扩充**：计数、筛选、读取和任何只读操作都不联网、不调用模型、不创建任务（规1）。
- **临时错误不算试完**：网络、权限、配置、存储错误与使用者中断不产生自动获取耗尽事实（收2 验收行）。
- **一个范围、一次发起**：获取只在使用者明确发起时进行，范围在提交时固定（规2、ADR 0052）。
- 合成测试不连接真实服务；真实运行只用 Owner 授权的来源与范围。

### 为什么这样分

- **01 单独一块、由总设计师负责**：三个数的定义（尤其版本与 `EXCLUDED`）、计数合同和机制验收的口径都不在规格里，实施者不能自己定。
- **02 与 03 分开**：02 交付后 Agent 与 CLI 就能读到三个数，可以单独验收；03 改文献库页面，排布要先进页面规格。
- **04 单独一块**：它只用合成数据和假来源，不需要任何授权，能独立证明“万篇的机制成立”；它也是 05 的前提。
- **05 单独一块**：它碰 Owner 的真实库和真实来源，每一步都要单独授权，产出的是数字而不是代码。
- **06 单独一块**：数字出来之后，哪些是缺陷、哪些要新决定，由总设计师判断，不在运行中顺手改。
- **07 收尾**：文档、全量与部署汇合。

## 计划级验证与完成标准

- 02–04、06 的退出条件都满足；05 至少完成一次经授权的运行并交出报告（Owner 也可以决定不做真实运行，在 05 记下依据，计划仍可收尾）。
- 不变量在 04 的机制验收与 05 的真实运行中都有直接证据。
- 收4 验收行要求记录的数据、时长、吞吐、内存、磁盘和外部调用花费，在 04（合成）与 05（真实）中都有数字。
- 开发中只跑定向测试；收尾跑一次全量（HARNESS 5.4、6）。04 的万篇测试不进入全量（见 04）。

不能由局部证据推出的结论：

- 合成数据上的吞吐与内存，不说明真实来源上的吞吐（真实来源受网络、限流与浏览器制约）。
- 一次真实运行的覆盖率，不说明其他范围、其他时间的覆盖率。
