# 计划 28：导入与 PDF

类型：计划
负责：使用者把文献放进文献库的各条途径和与 PDF 有关的环节：按 DOI 或标题添加、只导入 PDF 时的书目、PDF 工具合一、Agent 的入口（MCP 与 Skill）、解析全文的耗时、书目文件的格式、Zotero 导入（扩展与 Agent 两条路）；以及计划 25 留下的真实获取运行、真实核对与收尾
状态：Ready（2026-11-25 计划编写完成，尚未开工；同日并入计划 25 未完成的 14–17、21–24；Owner 说还要补充内容）

## 目标

Owner 2026-11-25：第一位外部使用者只导入 PDF，323 篇全部以文件名入库。他的判断是“这部分要好好做，要不然用户连数据都导入不进来”。当天已补上的三样（读不出的原因可见、识别书目、构建自带 MuPDF 并在启动时把关）见 [ADR 0066](../../architecture/decisions/0066-complete-program-or-failed-build.md) 与[文献与材料 8.4](../../architecture/technical/03-literature-materials.md#84-书目待补)。本计划做剩下的。

Owner 同日提出五点，并同意按下面的顺序做（原话：“可以，先写计划吧”）：

1. 两套 PDF 工具（MuPDF 与 `pdfinfo`、`pdftotext`）用一套行不行。
2. PDF 导入后怎样拿到合理的元数据；解析全文时元数据还会再更新一次。
3. 支持给定标题或 DOI 来获取文献，适合少量导入，直接进文献库。
4. 一批任务里有多个 PDF 要解析时，能不能并行加速。
5. “以后都是 Agents 时代，这些导入最好都提供 MCP 和 Skill。”

## 已定的方向

- 导入的结构不变：各条途径都先成为批次，预览、认篇、查重、确认后入库（[ADR 0063](../../architecture/decisions/0063-unified-intake.md)）。新途径复用这套机制，不另造。
- 使用者点名的文献进文献库（[ADR 0067](../../architecture/decisions/0067-library-and-candidates.md) 第 3 节）。按 DOI 或标题添加属于点名。
- 导入时不调用模型。导入的目标是让使用者在列表里认得出这篇文献；补全在解析全文时进行。
- 先量后改：认出率、两套工具的一致性、解析全文的耗时，都先在真实数据上量出数字，再决定改什么。
- 每条导入途径同时交付页面入口、MCP 工具（及 CLI）与 Skill 说明。
- 不为一个读法或一项功能加第二份数据；提出结构变化之前先核对现有的表和索引能不能回答，并在正式库上只读量过。

## 仍需验证的前提

- PDF 自带的作者、期刊、年份有多可靠（块 02）。
- MuPDF 与 `pdfinfo`、`pdftotext` 对同一批 PDF 的判断是否一致（块 03）。
- 解析全文的时间主要花在哪一步（块 05）。代码里一批任务默认同时处理 4 篇、每篇同时校订 3 页；配置项 `max_concurrency` 与它是不是同一个开关，没有核对。
- 现有的 Skill 与 MCP 覆盖到哪里（块 04）。只核对过文件存在，没有通读。
