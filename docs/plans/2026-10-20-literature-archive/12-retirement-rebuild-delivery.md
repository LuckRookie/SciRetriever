# 12 旧路径退役、真实库重建与交付

状态：Pending。

- 执行者：代码退役与重建工具由 worker 负责；用户文档与收尾由文档执行者负责；GB 和 GR 由 Owner 确认。

**Outcome**：

1. 旧路径全部退役，生产代码中不再存在：
   - 两阶段总结与元数据流程；
   - `LiteratureContent` 的生产；
   - `CONTENT_READY` 状态；
   - 单一当前 `ParserResult` 的阅读路径；
   - `markdown-utf8-v1` 文档的生产。
2. 真实库在隔离副本上完成以下工作：
   - schema 迁移；
   - 按旧库模式重建；
   - 抽样核对。

   Owner 验收后切换到正式库。
3. 以下文档都已改为描述当前行为：
   - README；
   - 用户指南；
   - 配置手册；
   - CLI/MCP 说明；
   - MinerU 注意事项；
   - 技术文档中的“实施中”标注。
4. `pnpm full` 通过，便携安装包离线验证通过，计划状态为 Completed。

**进入条件**：
- 01–11 全部完成；
- 12.1、12.2 需要 GB；
- 12.3–12.5 需要 GR。

**责任边界**：
- 本块覆盖全仓库的退役清理；
- 真实库操作只在 Owner 授权的副本和切换窗口内进行。

- [ ] **12.2 退役旧解析与文档路径**（需要 GB）

  - `vlm-engine` profile 不再发布 `ParserResult`（3.6）。
  - `markdown-utf8-v1` 不再生成新文档。
  - 已有的旧文档版本：
    - 如果仍被有效证据引用，保持只读；

  - 文档读取入口只保留 v1/v2 判别读取，不再保留旧的生产路径。
- [ ] **12.3 隔离副本重建**（需要 GR）

  1. 按现有做法复制真实库，参考“Web 大库读取与可靠性修复”计划中的隔离快照方式，包括 catalog 与 FileStore。副本放在 Owner 指定的位置。
  2. 在副本上执行 7.3 的 catalog 迁移，以及 03–10 新增子系统的迁移。
  3. 先抽样：选择 Owner 指定数量的文献，按旧库模式建档（9.8），并生成重建报告：
     - 就绪数与失败数；
     - 失败原因分布；
     - 校订分类统计；
     - 需要重新解析的部分数与 GPU 时间；
     - 疑点、处置与存疑统计，矫正与用时核对的成本；
     - 模型调用次数与 token 数；
     - 词表规模与整理操作的数量。
  4. 由 Owner 抽查以下内容：
     - 若干篇文献的校订稿（对照 PDF）；
     - 元数据冲突；
     - 标签与词表。

     抽查通过后，对副本中的全部文献执行建档。
  5. 生成全量重建报告。处理问题队列，或者把问题队列列为已知遗留，提交 Owner。
- [ ] **12.4 切换**（需要 GR）

  - 按 Owner 确认的方式切换，可以选择：
    - 用重建后的副本替换正式库；
    - 在正式库上重放迁移与建档。
  - 切换前后都要完成：备份、完整性检查（现有的 operator 完整检查）、服务重启验证。
  - 切换失败时，按备份回退，并记录原因。
- [ ] **12.5 真实验收**（需要 GR）

  在正式库上按以下顺序完成一次真实流程：

  1. 新获取一篇带补充材料的文献；
  2. 分别显式启动解析与建档，直至 `READY`；
  3. 运行一个单篇算子；
  4. 生成快照；
  5. 运行一个多篇算子；
  6. 修改一个区块；
  7. 确认相关结果被标为过时。

  验收结果脱敏后记录在本块。

## 集成与影响

- 删除旧数据不可逆，只能在 GB 之后执行，而且要先在副本上执行。
- 切换期间服务不可用，时间窗口由 Owner 安排。

## 验证

- 12.1、12.2：
  - 在全仓库中搜索被删除的符号和状态值，确认没有残留；

## 恢复与交接

- 12.4 切换失败时，用备份回退，正式库保持旧状态，不进行部分切换。
- 残余风险写入 ADR 0037 的后果部分，以及根 README。
