# 08｜验收矩阵、打包与切换

## 1. 证据等级

当前仓库的Full包含严格类型、全部unittest、wheel构建和内容检查；本次文档任务未运行这些检查。迁移期间旧分支继续使用旧Harness，TS门禁在明确修订后替换工具，但不能弱化用户结果、安全和数据完整性的验收目的。[R03](10-sources.md#r03)

建议TS `quick`包含lint/format/typecheck；`full`再包含单元、合同、真实浏览器离线集成、数据差分、构建、包内容和安装后冒烟。具体脚本由迁移任务建立；此处不是已有命令说明。真实站点验证独立显式运行，不放入默认CI。

## 3. Fixture 构建

使用本地受控HTTP/HTTPS服务，生成具有明确DOI/标题/引用的合成PDF。用实际Chromium执行点击、JS blob、iframe、下载和SW，不mock掉要验证的事件顺序。测试网络白名单只存在于独立fixture环境。

同一fixture可以覆盖延迟、重定向、下载文件名与内容不一致、失效cookie、网络断开等变体。延迟由受控事件/闸门触发，避免固定sleep造成偶然通过。所有crash点要记录最终DB/spool/asset三者状态。

有效旧测试迁移到新运行时；直接复现已知缺陷的测试先证明旧逻辑存在相应风险，再用修正合同检验新实现。不可通过减少case或只测happy path让新套件变绿。

## 4. 性能与成功率

首先收集：动作排队/执行p50/p95、首帧延迟、输入回显延迟、WS积压、event-loop延迟、DB排队、内存峰值、候选保存时长、孤儿数与恢复次数。帧率/超时/预算是待校准的配置，不把一个拍脑袋常数固化为所有机器通用门禁。

真实站点样本仅在用户明确授权后运行，记录候选总数、人工在同出口可下载数、Agent触发信号数、完整保存数、交接数、身份通过数和最终成功数。失败目标不从分母删除；手动可下载且Agent失败单列。

不把某家验证挑战能否通过作为可以强制实现的固定CI断言；工程责任是可靠操作、准确归因、按政策放弃和不丢文件。不能承诺换TS或升级浏览器就提高站点放行率。

## 5. 打包策略

首选平台发行目录/压缩包：启动器、固定Node运行时、编译后的server、web静态资源、必要native模块和资源manifest。浏览器二进制采用经许可的随包或首次受控下载/缓存方式，校验hash与版本；不能运行时自动漂移到latest。[W18](10-sources.md#w18)

发布前冻结支持矩阵。至少优先验证用户当前Linux服务器环境和选定桌面平台；macOS/Windows/ARM支持只能在通过矩阵后声明，不依据npm可安装就宣布支持。Node原生依赖和PDF引擎的可选字体/渲染模块纳入包扫描。

不要求最终用户安装Node工具链、Python、Rust/GCC或VNC。无桌面Linux的headed Chromium仍需显示与系统库：可复用现有Xvfb，或提供受支持的自动环境准备/自包含运行镜像；容器属于可选发行形式，不声称零系统前提。[W14](10-sources.md#w14)

SEA单可执行可后续评估，但不是首发硬目标；native addon、浏览器与动态资源路径不一定自然内嵌。发布可用性优先于“只有一个二进制文件”。[W18](10-sources.md#w18)

## 6. 最终切换条件

全部活动模块有去向；核心差分通过；有意行为变化有批准记录；v2升级在副本上演练；文档/配置/公开命令一致；受支持平台安装后全流程通过；没有生产Python后门、裸调试端口或静默绕过网络边界。

切换由明确release与维护流程执行。先备份并暂停旧服务，关闭Profile，再迁移和启动新服务；失败按恢复演练处理。回滚影响真实新数据时停止自动覆盖，保留证据并进行前向修复/增量恢复。
