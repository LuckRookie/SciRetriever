# SciRetriever 活动实施计划规范

本目录保存需要跨阶段执行、跨会话恢复、共享合同变更、持久化变更或独立授权范围的活动计划。
计划把已经确定的方向组织成可执行、可验证、可恢复的结果，不替代需求、架构、Accepted ADR、技术合同或源码。
普通局部修改不必创建正式计划。所有计划继续受根 [HARNESS](../../HARNESS.md) 和
[AGENTS](../../AGENTS.md) 的工作树保护、权限、验证和交付规则约束；计划本身不授予真实数据、系统配置或 Git 操作权限。

## 1. 计划与其他文档的职责

| 文档                      | 负责什么                                         | 不负责什么                   |
| ------------------------- | ------------------------------------------------ | ---------------------------- |
| requirements              | 产品目标、范围和验收方向                         | 不维护施工任务与测试日志     |
| design / technical        | 模块责任、事实所有权、目标对象图和技术合同       | 不把设计目标表示为已经实现   |
| Accepted ADR              | 长期架构选择及其后果                             | 不维护逐项实施进度           |
| contracts、源码与直接测试 | 当前可执行的数据和行为合同                       | 不替代产品决策或实施顺序     |
| plan                      | 把已确定方向变成可验证结果的依赖、行动和恢复安排 | 不成为第二套架构或运行数据库 |
| README / guide / API      | 实际安装、配置和调用方式                         | 不把未交付能力写成当前用法   |

计划可引用上述事实。方向变化时应回到相应 owner 文档修正，不能长期保留两份相反的真相。
长期选择需要 ADR 时，把决策同步作为明确 Task；实施计划中的建议不能自行覆盖 Accepted ADR。

## 2. 什么时候需要正式计划

适用情形包括公共 API/配置/合同变化，状态、身份、恢复或文件采用边界变化，跨模块与跨会话工作，
需要多项证据汇合，或者涉及真实服务、用户数据、安装交接等独立操作范围。

一次连续工作单元就能安全完成并验证的局部修改，直接在源码和测试中处理。
需要正式计划时，不能只列方案和原则；必须让下一位执行者知道从哪项 Task 开始、如何验证、失败后停在哪里。

## 3. 目录和结果块

每个活动计划使用独立目录：

```text
docs/plans/YYYY-MM-DD-<slug>/
├── README.md
├── 01-<result>.md
├── 02-<result>.md
└── ...
```

根 README 是计划控制面，编号文件是结果块。**结果块按可独立验收和交接的能力划分，不按模块、代码文件或人员机械拆分。**
块数由实际结果和依赖决定；不要求固定几个阶段或文件，也不为了格式保留无意义步骤。
编号便于引用，不代表所有块必须严格线性执行。

活动计划使用扁平编号 Markdown 文件。调查、评审处置、证据和恢复记录写进其所属块；跨块决定写在根 README。
不另建无人负责的 `research.md`、`review.md`、`evidence.md` 来分散控制信息。
原始日志、截图、PDF、临时数据库和测试产物留在系统临时目录；计划只记录脱敏结论及证据定位。

## 4. 根 README 的最低内容

根 README 保留计划层面信息，具体编排可按任务调整：

- 目标、已确定方向、适用真相源和仍需验证的前提；
- 当前授权、未覆盖动作与必要 Human Gate；
- 范围、非目标和所有块必须保持的不变量；
- 结果块的输出、实际依赖、状态及集成关系；
- 主要风险及其负责块；
- 计划级验证口径、完成标准和不能由局部证据推导的结论；
- 当前进度、最近证据、恢复点和下一安全动作；
- 变更记录、最终交接、取消或替代安排。

根 README 不复制所有 Tasks，也不成为源码设计、终端日志和历史讨论的总汇。
对于实施尚未开始的计划，明确区分“计划编写完成”“技术可行性已验证”“功能已交付”。

## 5. 结果块的最低内容

每个结果块必须交代：

- **Outcome**：完成后可观察、可检验的结果；
- **进入条件**：前置合同、输入、数据、授权和证据；
- **责任边界**：本块拥有及触达的模块、生产者和消费者；
- **Tasks**：有稳定编号、按真实依赖排序的具体工作；
- **集成与影响**：调用方、配置、数据、公共接口及用户行为；
- **验证**：真实命令、直接断言、失败注入与未覆盖范围；
- **退出条件**：后续块可以依赖的事实；
- **恢复与交接**：失败保留什么、退回哪里、交给谁什么结果。

这些是最低信息要求，不是要求所有块具有相同长度或同样多的 Task。
Task 采用稳定编号和 checkbox，例如 `2.3`。每项写清动作、输出和验收；不能只有“实现调度器”“补充测试”等笼统动词。
跨块只依赖其中一个 Task 时应写出 Task ID，不要求等待无关工作，也不把部分证据写成整块完成。

完成 Task 时记录执行时 revision/patch、实际命令、结果、证据位置和残余风险。
没有实现证据不能勾选；只完成文档或 fake 测试不能勾选真实 Browser 路径。

## 6. 依赖、实施与审查

默认由一个 Primary owner 在同一工作区顺序整合。产品的 Agent worker 并发不等于开发过程的多执行者并行。
实际委派遵守本会话授权：只有共享合同稳定、修改范围清楚、存在汇合点时才安排多个实施者；“任务很多”不是理由。
已经明确授权的范围不重复询问，计划也不能凭工具可用性扩大授权。

每个结果块至少进行一次主执行者的 exact-diff、调用方和定向验证检查；跨块汇合后做集中集成审查。
发现具体失败、风险或不确定结论时，再增加针对性的专项复核，不为每个 Task 机械重复固定轮数。
原有工作树必须保护；不得把“恢复基线”解释为丢弃尚未归属的改动。

## 7. 授权边界与 Human Gate

计划应明确相关动作已经获得的授权和仍未覆盖的范围，尤其是：

- 破坏受支持的公共合同、配置格式、数据库或历史资产；
- 访问真实 Provider、模型、用户数据或其他外部系统；
- 修改系统 DNS、用户 Profile、凭据或运行环境；
- Git commit、merge、push、PR、发布、用户数据迁移或现场切换；
- 超出已确定方向的新产品或架构选择。

具体要求以用户指令和 HARNESS 为准。不存在相关动作的块不人为增加审批；已有授权继续有效。
计划里的授权仅覆盖原本允许的动作，不能由写入一个表格变成新的许可。

## 8. 验证与恢复

验证要针对本次风险，说明公共合同和错误语义、取消与迟到事件、文件/资源/进程责任、
配置和数据兼容、生产对象图以及需要时的安装交接如何得到证明。
命令必须来自本仓库真实入口，不复制其他项目的工具或测试数量。

代码切片使用相关 Vitest 反馈，交付默认必须通过 `pnpm full`；真实 Browser/Provider 测试与离线 Harness 分开记录。
文档修改检查链接、术语、命令事实、Markdown 结构和 diff。未运行检查及原因必须写明，
任何历史 Full、第三方评审或单次真实成功都不能代替当前改动的验收。

恢复时先读本规范、HARNESS、计划根 README 和当前结果块，核对 branch、worktree、HEAD、baseline、
最近证据和用户改动。只继续当前 Task 或下一安全动作，不从记忆猜测完成状态。
状态通常为 Pending、In progress、Partial、Completed、Blocked、Superseded 或 Cancelled；根计划可用 Ready 表示可开工。
Partial 必须指出具体完成的 Task 与剩余退出条件，不能用模糊的“基本完成”代替。

## 9. 完成、取消与清理

所有结果块退出条件、计划级验收、集中审查及实际需要的授权条件闭环后，计划才标为 Completed。
完成、取消或被替代时更新最终 revision、残余风险、恢复方式和替代链接；已证明的行为与长期决定同步到其真相源。
历史按 SciRetriever 现有归档和 Git 约定处理，不引入另一套 archive 规则。

本规范不新增固定文件数检查或机械门禁。合格计划的判断依据是结果、责任、依赖、证据和恢复是否具体可执行。
