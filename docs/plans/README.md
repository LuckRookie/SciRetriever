# 活动实施计划

本目录保存需要跨阶段执行和恢复的活动 Change Plan。计划负责把已经获准的方向组织成可执行、可验证、可恢复的工作，不定义产品需求、架构合同或已经发布的行为。

## 1. 权威边界

- 产品范围和验收以 `docs/architecture/requirements.md` 为准；
- 长期设计选择以 Accepted ADR 为准；
- 模块责任和目标对象图以 architecture design/technical 文档为准；
- 当前行为以 README、用户指南、源码和测试为准；
- 计划只引用上述事实，不复制出第二套需求、架构或完成结论；
- 复选框只表示计划执行证据闭环，不能替代源码、测试、Harness 或发布事实。

## 2. 目录形态

每个计划使用独立目录，目录名采用 `YYYY-MM-DD-<slug>`：

```text
docs/plans/
  README.md
  YYYY-MM-DD-plan-name/
    README.md
    01-first-change-unit.md
    02-second-change-unit.md
    ...
    NN-verification-and-handoff.md
```

`README.md` 是计划控制面，回答“为什么做、做到什么、按什么顺序、全局约束是什么、失败后从哪里继续”。编号文件是执行面，每个文件只承载一个可以独立说明结果和验收的大块。块数和名称按实际依赖决定，不套固定数量；验证与交接必须有明确归属，复杂计划通常单列最后一块。

不建立只有形式意义的空文件，也不把所有细节重新复制回根 README。若某计划确实需要额外的迁移矩阵、样本清单或证据索引，可以增加命名明确的附件文件，但其 owner、用途和退出条件必须在根 README 中说明。

## 3. 计划 README 的必备组件

每个计划根 README 必须包含：

1. **身份与状态**：Run ID、创建日期、Primary owner、baseline revision、执行模式、当前状态；
2. **目标观察**：完成后用户或系统能够观察到的结果，而不是文件操作清单；
3. **授权与真相源**：用户决定、适用 requirement/ADR/design 链接及计划不能改变的边界；
4. **事实、假设与开放问题**：已经核实的 baseline、仍需验证的假设、会改变方向的未决问题；
5. **范围与非目标**：本次必须完成和明确不扩张的内容；
6. **全局验收条件**：整个计划完成时必须同时成立的结果；
7. **分块地图**：每块的结果、文件、依赖、当前状态和交接关系；
8. **跨块合同**：所有块都必须保持的数据、接口、行为、安全和兼容性约束；
9. **影响矩阵**：公开接口、配置、数据/schema、依赖、文档、打包与运行对象图是否变化；
10. **风险与转化信号**：主要风险、观察指标，以及何时必须回到调查、设计或用户决策；
11. **验证与证据策略**：从直接测试到 Full Harness、安装包、语义审查的顺序和证据归属；
12. **授权门**：真实外部访问、数据迁移、Git、发布或破坏性动作所需的明确授权；
13. **执行方式**：Primary owner、顺序/并行策略、Task 执行循环、集成点和变更路由；
14. **执行审查**：计划就绪、块进入、切片、块退出、集成和最终交付分别由谁审查什么；
15. **进度规则**：Task、Block 和 Plan 的勾选/状态更新条件；
16. **恢复与续作协议**：失败信号、最近恢复点、恢复方法、跨会话继续时首先读取的内容；
17. **变更记录与最终交接**：计划本身为何调整、完成后留下什么、未完成事项如何处置。

计划 README 可以简洁，但不能省略这些语义。没有内容的项目应写 `无` 及原因，不能悄悄消失。

## 4. 每个大块文件的必备组件

每个编号大块文件必须包含：

1. **块身份**：状态、Task 范围、前置块、下游块和恢复点；
2. **块结果**：完成本块后新增的可验证能力或已经消除的风险；
3. **进入条件**：开始本块前必须成立的合同、对象图或验证；
4. **责任与改动面**：owner、文件/模块、生产者、消费者及受保护的用户工作；
5. **需要保持的行为**：本块不能破坏的既有结果；
6. **Tasks**：每项使用 checkbox、稳定 ID、动作、验收和必要依赖；
7. **执行方式与集成点**：本块采用的顺序、可并行单元、Task 循环和与上下游汇合的位置；
8. **审查门**：进入、切片、退出时审查的对象、阻断条件和 finding 路由；
9. **接口/数据/依赖影响**：本块实际改变什么、不改变什么；
10. **验证与证据**：直接测试、静态检查、集成检查及证据记录位置；
11. **退出条件**：何时可以将块标为 Completed 并进入下游；
12. **完成证据**：执行后填写真实命令、结果和残余风险；
13. **失败与恢复**：本块失败时停止在哪里、如何回到最近通过状态；
14. **下游交接**：下一块可以依赖的稳定合同，不传递临时实现细节。

## 5. Task 与状态语义

Task 应按结果切分，而不是按“阅读文件”“写代码”“跑一下测试”等活动切分。推荐格式：

```markdown
- [ ] **ABC12 — 实现角色绑定的单次执行。** Runtime 根据 role 选择 model，
  在外部 I/O 前验证 capability，并把一个 provider-neutral call 转为一次 adapter 调用。
  - 依赖：ABC09、ABC11。
  - 验收：角色错配与 capability 缺口均在 fake adapter 调用计数仍为零时稳定失败。
```

状态统一使用：

- `Pending`：前置条件尚未满足或尚未开始；
- `In progress`：当前正在集成且尚未通过退出条件；
- `Completed`：Tasks、直接测试、必要文档和退出条件全部闭环；
- `Blocked`：存在必须由用户授权、外部状态或新设计决定解除的阻断，并明确记录阻断事实；
- `Superseded`：由新计划替代，必须链接替代计划并停止更新旧复选框；
- `Cancelled`：明确终止，记录已完成事实和未实施范围。

只有实现、直接测试和对应验收证据同时成立时才能勾选 Task。根 README 的块状态从块文件汇总，但不维护另一套独立 Task 计数。Plan 只有所有全局验收与最后交接闭环后才能标为 Completed。

## 6. 执行方式

每项计划只有一个逻辑 Primary owner。Primary owner 负责事实、设计、全局计划、用户工作保护、集成、证据、审查和最终交接；即使某些 Task 由其它执行者完成，局部成功也不能替代集成成功。

根 README 必须声明执行模式：

- **single-session**：一个 Primary owner 在一个连续会话内完成；
- **cross-session**：通过计划状态和恢复协议跨会话继续；
- **worker-assisted**：在获得人类明确批准后，由边界稳定、文件不重叠、可独立验收的多个执行单元协作；
- **independently-reviewed**：在 Primary review 之外增加独立判断。

模式可以组合，但每次变化必须写入计划变更记录。默认使用一个 Primary owner 串行执行，不为了形式增加执行者或并行度。任何实现单元的并行执行都是 `HUMAN GATE`：只有人类明确批准当前计划中写明的并行范围后才能启用；“开始”“继续”“尽快完成”等普通执行授权不等于并行授权，也不能从工具可用性或任务可拆分性推断同意。

执行顺序遵循真实依赖：

1. Block 进入条件和前置审查通过；
2. 对当前 Task 做精确预检，核实 owner、调用方、受保护改动和直接测试；
3. 完成一个最小但完整的能力切片，包括实现、直接测试和必要文档；
4. 运行低成本直接检查；
5. 审查该切片的 diff、合同、错误路径、范围和证据；
6. finding 解决后记录完成证据并勾选 Task；
7. Block 全部 Task 完成后执行块级集成和退出审查；
8. 只有退出条件通过，才把稳定合同交给下游 Block。

并行默认关闭。只有满足以下全部条件时才允许并行：

- 人类已经明确批准本次并行执行及其具体范围；
- 单元之间没有未稳定的共享接口或数据格式；
- 文件/模块 owner 不重叠；
- 每个单元有独立验收和恢复点；
- 根计划声明汇合点、集成顺序和最终 owner；
- 并行不会绕过用户授权或增加真实外部动作。

并行批准必须记录在计划授权门和变更记录中，并至少说明并行的 Blocks/Tasks、各自 owner 或执行单元、文件范围、共享合同、汇合点和停止条件。批准只覆盖记录的范围；新增并行单元、扩大文件范围或改变共享合同必须重新取得人类同意。批准被撤回时不再启动新并行单元，Primary owner 应让已开始工作到达安全检查点后统一集成或停止。

这个 Human Gate 约束同时推进的实现、迁移或其它会改变项目状态的执行单元。为了降低等待时间而批量发起的独立只读检查、文件读取或无状态诊断，不形成多个实施 owner，不属于计划级并行执行；它们仍必须遵守安全、资源和外部访问授权。

执行证据改变 owner、接口、数据、风险、验收或授权边界时，立即停止按旧计划推进，返回调查、设计或用户决策；不能在下游 Task 中堆兼容层或例外掩盖计划失效。

## 7. 执行审查

执行审查与测试分开。测试提供机械或行为证据；审查判断目标、所有权、结构、风险、证据和交付是否一致。每个计划至少设置以下审查门：

| Gate | 时点 | 必查内容 | 未通过处理 |
| --- | --- | --- | --- |
| R0 Plan readiness | 开始首个实现 Block 前 | 目标、授权、真相源、事实/假设、依赖、验收、风险、验证、恢复及并行授权状态是否完整 | 返回计划/设计，不开始实现 |
| R1 Block entry | 每块开始前 | 前置块证据、owner、受保护工作、接口、测试入口、外部授权及并行 Human Gate 是否仍有效 | 保持 Pending，修复前置或更新计划 |
| R2 Slice review | 每个能力切片完成后 | diff 是否满足 Task、错误路径/测试/文档是否闭环、是否越界或夹带改动 | 普通 finding 当场修复；实质 finding 路由回 owner |
| R3 Block exit | 每块结束前 | 全部 Tasks、直接测试、接口一致性、下游合同、残余风险和恢复点 | 不勾选 Block，回到未闭环 Task |
| R4 Integration review | 多个依赖分支汇合时 | 组合对象图、共享状态、配置、数据、错误和测试是否仍一致 | 回到产生冲突的 Block，不在汇合处做长期补丁 |
| R5 Final delivery | Full 后交付前 | 原始目标、计划差异、集成 diff、架构、UX、兼容性、安全、证据、文档、打包和发布状态 | finding 解决、路由或明确接受为残余风险后才能交付 |

审查至少覆盖这些视角：

- 用户结果和全局验收；
- 计划遵从性及计划变化是否有依据；
- 模块 owner、依赖方向、公共面和共享状态；
- 数据、兼容性、错误语义、安全和 UX；
- 测试是否保护结果、合同、不变量和失败，而非偶然内部细节；
- 文档、配置、打包、依赖、凭据和任务范围；
- 验证证据、未覆盖范围、残余风险和 Git/发布状态。

finding 分为：

- **blocking**：违反需求、Accepted ADR、数据/安全/授权边界或适用门禁，必须停止推进；
- **material**：改变 owner、接口、数据、风险或验收，必须路由回调查/设计/对应 Block；
- **ordinary**：当前 Block 内可直接修复并重新验证；
- **accepted residual risk**：因外部状态或未授权真实验证无法消除，必须在交接中准确说明，不能冒充完成证据。

Primary owner 必须审查集成结果。公共合同、安全/隐私、持久数据、核心架构、广泛迁移、Harness 变化或用户明确要求时，应考虑独立 reviewer；独立 reviewer 只给出 finding，Primary owner 仍负责解决、重新验证和最终交接。审查结果写入对应 Block 的完成证据或正式 review artifact，不创建无人消费的流水账。

## 8. 计划演进、证据与归档

- 局部可逆的执行选择记录在计划变更表；改变产品范围、长期架构或公开合同的决定必须回到 requirement/ADR，不能由计划自行授权；
- 原始终端日志、真实数据、凭据、截图、PDF、构建产物和缓存不进入计划目录；计划只记录可复现命令、结果摘要和正式证据链接；
- 事实变化导致顺序、范围或 owner 改变时，先更新根 README 的事实/风险/分块地图，再更新受影响块，不机械重写全部文件；
- 完成、取消或被替代的计划从活动目录移出。具有长期审计价值时进入 `docs/archive/` 并明确“非当前真相源”；没有长期价值时删除；
- 归档或删除计划前，确保所有仍然有效的产品、架构、使用和验证事实已经进入各自权威文档。

新计划至少创建根 README、一个实施块和一个验证/交接块。根 README 使用以下顺序：

```text

目标观察
授权与真相源
事实 / 假设 / 开放问题
范围与非目标
全局验收条件
分块地图与依赖
跨块合同
影响矩阵
风险与转化信号
验证与证据策略
授权门
执行方式与集成点
执行审查
进度规则
恢复与续作
计划变更记录
最终交接
```

编号块文件使用以下顺序：

```text
块身份

```
