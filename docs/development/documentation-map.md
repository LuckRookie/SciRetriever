## 同步规则

1. 公开入口、模块 API、配置、schema、序列化格式或默认值变化时，代码和测试同步，README 与当前用户指南更新已实现行为。只有理想产品合同本身变化时才修改 architecture。
2. `Literature` 身份、当前 metadata revision 令牌、内容 artifact 和 schema version 必须始终使用不同术语和所有权。多个不可变 MetadataObservation 长期保存，每个 Literature 只有一份当前 LiteratureMetadata，旧统一元数据不形成 revision 历史。
3. 内容只保留一份与当前 PDF 和 metadata revision 对齐的 current LiteratureContent；成功替换清理旧 content support，失败保留旧结果。不存在平行分析、标签结果、两阶段 provenance 列表或 `DocumentPackage` 占位。
4. 理想能力只在 architecture 定义；未实现能力不得进入当前命令示例或 accepted config。
5. ADR 0005 的 `DocumentPackage` 2.0 已撤销；未来完整快照或其它公开边界变化必须重新确认消费方并新增 ADR。受支持数据或公开合同发生变化时，由 owner 明确迁移、弃用和兼容门禁。
6. 活动提案放在 `docs/proposals/`，需要跨阶段恢复的活动执行计划放在 `docs/plans/`；确认方向、完成、拒绝或被替代后的提案、评估和进度记录进入 archive。这些材料不属于产品或架构真相源，也不参与当前代码文档同步。
7. provider 或访问方法变化不得绕过 ADR 0012/0015/0016 的 provider/channel/host 进程内共享准入、官方 API quota policy、Browser 一个固定身份 Profile/共享 CloakBrowser context、不同 risk group 并行/同组限速串行、per-hop PublisherAccessProfile guard、challenge dependency、runtime/circuit 和单次 operation limits；不得用统一固定数字冒充所有 Provider 政策，不得把动态 plan/route hint/queue/限速/runtime/challenge 状态持久化为文献事实，也不得绕过 secure transport、有限 timeout、validation、immutable storage 和 redaction。Chromium 自己管理的认证状态可以只留在 owner-only Profile 中，但不能进入配置、status、日志或文献数据库。
8. 每个输入 Asset 在 Catalog 中最多保留一个当前 ParserResult 关系。重解析只有在新结果完整生成、验证并发布后才能原子替换该关系；失败必须保留旧结果。不可变文件不得原地覆盖，旧解析字节不形成数据库历史，只能进入无 Catalog 记录的可回收缓存。
9. Parser 的公共产物只包含输入 Asset 身份与 hash、页数、规范化 Markdown artifact、Markdown 实际引用资源、结果 hash 和 parser provenance。Artifact 同时保存媒体类型和字节大小。MinerU JSON、GROBID TEI、block、bbox、逐段 source locator 及其它 parser 私有输出不得进入当前公共合同或长期 Catalog。
10. LiteratureContent 的章节和子章节正文统一使用 Markdown 字符串；固定缺失值为“未提供”。内容 hash、UTF-8 Markdown 字节 hash 和单一 Analysis provenance 不得混写，且 ParserResult/LiteratureContent 的可重建性不能降低来源元数据和原始 PDF 的保存优先级。
11. 新功能必须明确读取哪些当前文献数据库事实、形成哪些新事实、由哪个业务模块拥有其含义并如何保留 provenance。收集、导入、处理、查询和导出不得建立平行结果集合或第二真相源；重跑与恢复重新读取 current facts，不恢复旧外部调用或内存现场。
12. 持久化 DiscoveryRun 和进程内数据库补全必须分别表达外部发现和当前范围补全；当前合同不得建立 Collection、membership、CollectionSelector 或 BatchRun。`sources.metadata.limit` 分别按每个 Source 在整个 Run 的过滤前原始 item 计数，Metadata 不做领域语义过滤；不得恢复共享总量、强制 CollectionRun 流水线、运行中动态吸收目标、逐篇全 Provider 自动补查，或让系统/Parser/LLM 失败触发版本回退。缺 PDF 目标只在当前内存中组成有界 cohort，严格执行 Public → API → Browser admission，不能把队列或计划变成持久批次状态。
13. 有效的处理型 Entry 操作只形成 Discovery、数据库补全、手动 PDF、导入或导出五类非持久化 Report，并只共享正常结束、受控中断、操作级失败三种 ReportEnd。Report 不建立通用 envelope、ReportId、时间、自由 details、日志数组或第二套 counts；selector、目标、候选、普通失败、统计和 Report 不进入 Catalog，硬崩溃只依赖已提交 current facts 恢复。
14. 自动 PDF 获取耗尽只在全部适用 routes 正常结束且没有 deferred、action-required 或未解决 failure 后保存 LiteratureId；新 observation、成功主 PDF 或明确重试清除。临时错误、`429`/quota 和 Browser 登录/MFA/challenge 不建立该事实，`needs_manual_pdf` 不增加 Literature 状态。
15. 手动 PDF 必须绑定具体 Literature，复制到内部 staging 后复用同一基本检查；不增加 AcquisitionPath 或自动结果分支，不保存用户绝对路径，不移动、修改或删除用户原文件，并在成功时清除自动获取耗尽事实。
16. 核心 Catalog schema 按标量列、重复子表、明确 FK 和 ArtifactStore 映射，不用完整 Pydantic JSON、通用 `extra/details`、selected IDs JSON 或 vendor response 代替精确结构。
17. Logging 变化必须同步检查设计文档、总体技术文档、Logging、Entry、Acquisition 与 Network 技术文档：目标生产模块只通过 `logging.api` 获取项目 logger，Bootstrap 只通过该 API 触发一次生产 stderr 配置；正常/Debug 可以显示安全 tier/route/group/action，Report 从 typed result/failure 独立形成，stdout 不被日志污染，外部 adapter 在进入 LogRecord 前完成脱敏。Cookie、profile 内容、完整 URL、selector、签名 locator 和页面对象在两种模式都不得进入日志；不得绕过 Logging 模块私自配置 Handler，也不得建立公共事件合同、持久日志、Observer 或 EventBus。
18. Library 读取变化必须同步检查 Model、Literature、Entry 与 Storage：Search/Detail/Reference 页面都是同一 read-only snapshot 的临时投影；references/cited-by 共用权威 Reference，Provider count 不混入。Artifact 只从 Detail 中既有 Asset/ArtifactRef 进入 verified reader，Model 不执行 I/O；用户文件导出默认拒绝覆盖并原子发布，内部路径、stream、目标路径、副本和结果不持久化或进入处理 Report。
19. CLI 命令根固定为 `sciretriever`，命令树为 `discover topic/citations`、`complete`、`literature search/show/references/cited-by`、`import metadata/pdf`、`export metadata/pdf/content`，以及裸 `config` 交互管理器和 `config status/test`。CLI 不得恢复 `config set/remove`、`exchange`/`bibliography`/`artifact` 或内部模块一级命令；README、指南、配置示例和 `project.scripts` 只描述已实现并通过安装后离线测试的当前行为。
20. Provider、Source 默认或访问方式变化必须同步检查 ADR 0014/0015/0022、Configuration、Metadata、Acquisition、Network、Provider Notes、Profile 准入矩阵与工具中立性声明：Metadata 产品能力与 Publication/Access Provider、Access Platform 身份分开；领域发现按 Auto/Custom effective selection + production + readiness 选择，原文按强证据形成 Resolution/Plan。Provider secret 只进入固定 owner-only 凭据文件和当前 adapter 内存，Key 不改变 Source enablement，Browser profile/Cookie 不进入该文件；`config status/test` 不形成数据库事实，Harness/CI/离线验收不读取真实凭据/profile 或连接真实服务。
21. Identifier canonicalization、Provider 字段身份归类或 Literature 身份比较发生变化时，必须同步检查 ADR 0002、架构原则、Design、Model、Metadata、Literature、Storage 和直接 fixture/测试。不得让 adapter 私自形成不同 DOI/arXiv 规则、把 Provider record ID 塞入文献 identifiers、用模糊文本覆盖稳定冲突，或让 Storage 唯一约束替代 Literature 业务决定。
22. Agents 变化必须同步检查 ADR 0008/0017/0019/0021、Agents/Analysis/Acquisition/Configuration/Network/Logging/Bootstrap：Configuration 拥有 Model Provider 与 `provider/model` Model 注册表，Model 只保存 reasoning/image，Analyze/Browser 直接选择完整 Model；消费模块派生 strict output、tool/image 合同与调用限制，Agents 拥有 provider-neutral capability、无状态一次调用 Runtime 与按 Model Provider 共享装配的协议 adapter，消费模块拥有 prompt/workflow/schema/tool 含义/结果验收；自动模型目录读取必须保持有界、非持久并经过 Network，失败或无安全结果才进入 Manual，不能成为 capability 真相；不得恢复 Service/Profile/Preset/Entry 配置层、增加 task-level model/reasoning/capability override，恢复 Analysis 私有 provider、Session/history/累计作业预算，把 Browser/Literature 业务枚举放入 Agents，让 Agent 取得 Page/CDP/Cookie/任意 URL/JavaScript，或持久化 prompt/response/screenshot/reasoning。
23. CloakBrowser、Profile identity 或 challenge 变化必须同步检查 ADR 0015/0016/0017、Configuration、Network、Acquisition、Entry、Logging、Provider Notes 和现场核实门：唯一生产 runtime、固定 seed/native persona、一个 process/context、原始出口、CONNECT/Network guard、显式 binary 生命周期、受限 challenge dependency、统一 Observation/动作与页面分类必须一起验证；不得保留 stock fallback、随机身份、环境代理、全局 Cloudflare origin 放行，把 Challenge 恢复为默认终态或专属生命周期/circuit，引入外部 solver/token 注入，或自动处理登录/MFA。
