# 元数据名称治理与 PDF API 路由提案

> 2026-10-11：用户结束讨论并授权实施。以下保留讨论时的建议与证据，后续进度以[实施计划](../2026-10-11-metadata-governance-pdf-routing/README.md)为准；目标合同同步到 ADR 0014/0015/0023，归档不表示功能已经交付。

本提案记录元数据名称差异、AI 辅助数据库维护以及文献到原文服务的连接方式。用户已同意先记录“程序处理已知情况、AI 辅助治理未知名称”的方向，并认可五层获取的整体思路。2026-10-11 按用户要求，由三个 Agent 从软件预检、预算调度和反例审查角度讨论 Browser 入口成本；用户随后明确以接近人的观察与操作、控制时间成本为主，调用和动作次数采用宽松防失控上限。具体数据合同、治理结果如何接纳、预算数值、故障回退及实现仍待定稿。本文不授权实施，不表示相关能力已经交付，也不兼任实施计划。

## 问题与目标

SciRetriever 面向长期、大规模文献积累。同一篇文献可能从多个供应商获得，而期刊和出版社的名称存在缩写、标点、语言、品牌及历史写法差异。当前统一了字段结构，但字段含义尚未全部归一。

本轮需要分别解决两个问题：

1. 保留来源信息的同时，如何识别表示同一实体的名称，并使处理结果可以复用。
2. 下载时如何根据文章的元数据和访问线索，连接到适用的授权全文 API。

用户明确：元数据入库后不必立即下载 PDF。AI 治理可以作为异步数据库维护的一环；不要求仅靠程序穷举所有名称，也不接受为了全面覆盖而建设过大的治理体系。

## 当前基础与边界

以下描述来自 2026-10-10 工作树源码阅读，不代表新的设计已经实现。

| 当前事实 | 影响 |
| --- | --- |
| [`LiteratureMetadata`](../../../packages/contracts/src/index.ts) 中的 `venue` 和 `publisher` 是可空字符串，没有专门的规范化出版社 ID 或期刊 ISSN 字段 | 统一字段不等于统一实体身份 |
| [来源投影](../../../apps/server/src/literature/metadata-rules.ts)按来源优先级选择当前字段，同时保留已接纳的来源记录 | 当前解决采用哪个值，尚未实现名称别名的统一解析 |
| [Provider 目录](../../../apps/server/src/providers/README.md)已有 `elsevier`、`wiley` 等稳定 ID，以及服务、站点、标识符、凭据和访问政策定义 | 可以复用现有目录，不必创建第二套服务注册体系 |

| 当前自动获取顺序为公开来源、授权 API、Browser | API 优先是本轮提出的策略变化，尚未修改实现或 Accepted ADR |

名称、元数据供应商、出版归属和原文访问服务分别表达。Scopus 返回一篇 Wiley 文章，不构成 Elsevier 全文服务覆盖它的证据；期刊也可能转移出版或托管平台。聚合原文服务可以跨出版社提供材料。

## 名称治理：已同意记录的方向

- 常见且含义明确的情况使用程序规则；AI 辅助识别未知名称、缩写及需要上下文的描述。
- 治理可以异步执行，不成为元数据入库或每次 PDF 下载的必经模型调用。
- 来源记录保留供应商提供的名称；治理结果应可追溯、可纠正，不覆盖已有来源事实。
- 可靠的归类结果应当复用，减少对同一名称的重复模型调用。
- 未知或冲突保持明确，不强行归类，也不阻止其他本来适用的下载路径。

### 建议的最小工作方式

1. 从指定文献范围汇总不同出版社名称，统计已识别、未知、冲突，以及各自涉及的文献数量。
2. 对大小写、空白等确定性差异做规则处理；已知别名使用共享映射。映射就近维护，不在各元数据适配器中复制。
3. 将未识别名称及必要的文章网址、标识符等上下文交给 AI，并提供已有候选内部 ID，允许返回未知或冲突。
4. 根据证据检查模型建议，接纳可复用映射；同名但含义依赖上下文时，不推广为无条件全局别名。
5. 后续获取任务消费已确认结果，并继续结合文章级访问证据判断服务适用性。

这些是实现建议，尚未冻结字段、入口或接纳条件。模型的自报置信度不能独自成为接纳依据。治理至少应能解释输入、上下文依据、结果及规则或模型来源；具体持久化与纠正方式待设计。

首次可以是显式运行的批量维护操作，复用现有 Agents 能力；尚未决定增加常驻任务、自动定时调度、独立治理服务或新的数据库表。

### 期刊名称的范围

期刊全名和缩写的归一可以使用可信 ISSN、电子 ISSN、ISSN-L 等身份依据，但当前尚未设计这些字段的接入和存储。完整期刊目录及出版转移历史不作为首次 PDF 路由改进的前置条件。

名称识别、服务适用性与当前文章下载权限是三个不同结论。AI 可以辅助语义归类；当前托管、API 覆盖与实际授权仍需要相应事实或服务响应。

## PDF API 连接：继续讨论，尚未定稿

用户希望将文献元数据中的期刊、出版社与对应 API 连接起来。本轮进一步提出：先下载元数据供应商给出的 PDF 直链，剩余文献依次尝试出版社专用 API、通用 API、公共网站和 Browser。以下记录该排序建议及审核意见；尚未修改当前生产合同。

后续讨论围绕一条具体的数据流展开：

```text
文献标准元数据 + 来源记录 + 治理结果 + 文章访问线索
  -> 识别候选原文服务及依据
  -> 检查服务支持的文章标识和必要配置
  -> 形成可执行 API 请求
  -> 取得统一 PDF 候选或明确结果
  -> 按已确定的获取策略继续处理
```

需要确定：

- 规范化出版社 ID 如何连接现有 Provider/service ID，如何表达一个文章可能有多个可用原文服务。
- 期刊归属仅作候选线索还是需要可复用映射；如何避免要求每本期刊预先登记才能下载。
- 现有文章 URL、PII 等证据如何优先使用；证据不足时怎样补充 DOI 落地信息，冲突如何呈现。
- 名称治理结果的接纳条件，以及什么结果可以用于 API 适用性判断。
- 五层顺序的具体来源归类，以及正常无全文、凭据失败、限流和临时服务故障各自如何处理。

当前 [ADR 0014](../../architecture/decisions/0014-capability-scoped-providers-and-local-credentials.md)和 [ADR 0015](../../architecture/decisions/0015-publisher-aware-tiered-pdf-acquisition.md)要求证据驱动的原文路由，并保留公共来源优先的三级顺序。单独 publisher 字符串或 DOI 前缀不独自启用内容 API。拟议的路由与排序变化若获确认，应先同步对应长期合同，再实施，不能把本提案当作已经生效的行为。

## 五层获取顺序的审核建议

用户提出的顺序合理：先消费已有文件线索，再使用明确适用的服务，最后进入交互成本较高的 Browser。建议按当前文献仍缺 PDF 的情况逐层推进：

```text
已有 PDF 直链
  -> 出版社专用 API
  -> 跨出版社的聚合 / 开放获取 API
  -> 公共网站的 HTTP / 页面规则获取
  -> Browser Agent
```

这些是同一套获取流程的执行层，不要求新增五个核心模块或五套下载器。

| 层 | 消费的信息与职责 | 示例及边界 |
| --- | --- | --- |
| 已有 PDF 直链 | 消费各来源已经提供的正文文件线索，直接请求字节 | 元数据中的 PDF URL；建议将 arXiv ID、PMCID 可确定构造的公开 PDF 地址也归入该层，以保留廉价路径优先 |
| 出版社专用 API | 根据文章级访问证据与内部服务定义，调用适用的全文产品 | Elsevier Article API、Wiley TDM；出版社名称帮助提出候选，具体文章定位与服务覆盖仍需确认 |
| 通用 API | 使用覆盖多家出版社的聚合或开放获取服务查找、取得原文 | CORE、Unpaywall；前者可能需要凭据，后者主要返回开放获取位置，均不保证覆盖任意文章 |
| 公共网站 | 对配置中启用的站点执行有界 HTTP 跳转、静态页面解析和文件获取 | Sci-Hub 等站点、适用的文章落地页；正常未命中或独立来源不可用不等于机构无权访问 |
| Browser | 对剩余可运行目标，使用现有机构网络与浏览器会话交互获取 | 复用通用 Agent 和统一文件接纳，不在此增加逐出版社页面脚本 |

API 是否需要凭据与获取优先级分别表达。当前 `public / authorized-api` 分类不足以单独承载新顺序：Unpaywall 当前属于 public，CORE 属于 authorized-api，但拟议顺序把它们都放在通用 API 层。源码能力目录、配置顺序及有界 cohort 调度如何同步调整，留给实施设计，不通过是否有 API key 推断层级。

### 直链发现与文件有效性分别判断

`.pdf` 后缀可以作为轻量候选信号，但不能成为唯一条件或成功标准：

- 应解析 URL 后检查 `pathname`，忽略大小写；`paper.PDF` 和 `paper.pdf?download=1` 都可以是候选。
- 没有 `.pdf` 后缀的 `/download/123` 或 `/pdf/文章标识` 也可能返回 PDF。供应商明确提供的 PDF 字段或媒体类型可以直接形成候选，不要求后缀匹配。
- `.pdf` 地址可能返回登录页、验证页或错误 HTML。实际 HTTP 响应、文件字节和已有 PDF 读取检查决定能否接纳，不能只看地址或 Content-Type。
- 查询参数按已支持的网络规则保留；不能为了匹配后缀删除下载所需参数。阅读器 fragment 按现有规则处理。
- 已知需要凭据的官方 API 地址继续交给所属适配器，不能因它看起来像 PDF 而作为匿名直链请求。
- 明确标为补充材料或其它版本的线索不应仅凭 `.pdf` 后缀当成目标主 PDF；这属于候选选择，不恢复正文 DOI / 标题的下载验收门。

具体建议是把“元数据适配器明确给出的 PDF 线索”与“受支持资产线索中具有 PDF 路径后缀的地址”作为候选来源，再统一下载和验证。未知网页地址保留为页面入口，不因无法判定后缀就丢弃，也不无界扫描元数据中所有 URL。

### 层级之间的文件与线索传递

任何一层新取得明确 PDF locator 后，立即通过对应下载机制获取文件，不重新排队到第一层，也不继续完成其它来源的查询。普通文件地址复用共享下载器；需要凭据、会话或专用协议的文件继续由原适配器或 Browser 获取。只有有效 PDF 正式发布后，才结束该文献的后续获取。

同一操作内复用已经获得的 DOI 落地地址、服务标识和候选结果，避免同一 URL 在不同来源下反复请求。为确认 API 归属而解析 DOI 地址是定位工作，可以发生在 API 调用前；这不等于提前执行公共网站的全部下载策略。已经可以直接下载的文件不必先完成名称治理或出版社识别。

### “失败后继续”的范围

五层箭头表示允许继续的结果，并不把全部错误转换成正常未命中：

- 不适用或正常查无全文，继续下一层；有效文件已下载但本地发布失败时保留候选并修复发布，不重复下载。
- 某个站点不可用，保留来源级失败及允许的独立回退；不能据此宣称文献没有版权或所有路径均已正常耗尽。
- 限流、Retry-After、凭据、取消、安全与本地存储故障保留各自的停止或延期语义。具体 API 故障如何回退仍待确认，不因改排序自动放宽现有边界，也不通过同一服务的其它入口绕过限流。
- 未识别出版社时跳过尚不适用的专用 API 判断，继续其它有依据的路线；不强制等待 AI 治理完成。

## Browser 入口预检与预算：2026-10-11 多 Agent 审阅

用户指出，多个备用入口若分别启动 Browser Agent，会增加单篇文献的预算；建议先由软件检查 URL，再把有必要的工作交给 Browser Agent。审核接受减少无效模型调用的目标，同时区分链接检查、文件验证、网页交互与文章授权，避免把 HTTP 请求成功设为 Browser 的必要条件。

### 审阅分工与主要意见

本轮三个 Agent 独立阅读源码后相互质疑，主 Agent 汇总并回查证据。以下为本轮建议，未作为已接受设计实施。

| 视角 | 主要发现与建议 |
| --- | --- |
| 软件预检与数据流 | 复用前四层已有请求结果，不增加常态 HEAD/GET 预检流水线；PDF 下载端点与文章落地页分别保留，前者失效不丢弃后者 |
| 预算与调度 | 一篇文章的逻辑 Browser 任务共享累计时钟、模型调用和动作额度；不能循环调用完整 delivery，为每个候选重新取得预算 |
| 专门挑刺 | HTTP 403/challenge 不证明浏览器不可访问，HEAD/200 不证明是正确 PDF；模型接管后自动后台换页可能使动作过时；候选准备也必须有时间和网络边界 |

对此前“坏入口后依次换备用”的建议补充必要约束：如果每次换入口都重新调用完整 `deliver()`，当前工厂会创建新的文章 clock，可能放大预算。入口恢复应由程序在同一逻辑文章任务内完成，不能借换入口重新开始整套 Agent。

### 当前已经具备的基础

- [Entry](../../../apps/server/src/entry/pdf-acquisition.ts)当前对单次获取升级一次 Browser，并非已经按 URL 循环调用 Agent；多候选入口尚未实现。
- [文章执行器](../../../apps/server/src/browser/article-flow.ts)先开页、观察和检查在途候选，再派发模型请求；打开页面直接捕获到 PDF 时可以零模型调用，前提是 Browser 路线本身已配置且就绪。
- [文章时钟](../../../apps/server/src/browser/article-session.ts)已有累计活跃时间、实际模型派发次数、动作计数与冷却；默认 300 秒、50 次模型调用、100 次 Agent 动作。初始开页和观察计入活跃时间，平台/模型排队、下载与本地发布按各自生命周期处理。
- 同一执行器的下载失败恢复已经保留用量；新建执行器则不能假定自动共享原预算。物理页面或 runtime session 是否需要重建，与逻辑文章任务是否重置预算分别考虑。

“一次 Browser 任务”“一次网页导航”和“一次模型请求”分别计量。一篇文献只进入一次逻辑 Browser 流程，仍可能需要多轮观察与模型动作；预检能避免明显无效的决策，不能保证每篇文章只用一次模型请求或一定节省固定比例。

### 用户确认的预算取向：重视时间成本，保留充分操作空间

2026-10-11 用户进一步明确：Browser Agent 应尽量像人一样观察和操作，同时避免死循环；操作预算应比较充裕，主要关注时间成本。由此调整提案的优化重点：减少不必要的等待和重复工作，保证有效交互有继续执行的空间，不把最低模型调用数作为首要目标。

“像人一样工作”在本提案中体现为：根据当前页面反馈选择下一步，给异步页面足够反应时间，重新观察后再决定，避免在没有新反馈时反复点击同一个控件。已有 5 秒节奏与平台访问政策继续保留；本次讨论不通过缩短间隔来提高吞吐。

| 控制对象 | 建议职责 |
| --- | --- |
| 文章操作时间 | 主要的资源控制；观察页面是否在推进，同时保留最终时间边界，避免一个目标长期占用处理资源 |
| 模型调用数、Agent 动作数 | 充裕的防失控上限，不应在正常操作仍在推进时成为频繁触发的主要失败原因；换入口、重建页面不重置计数 |
| 无进展重复 | 根据有意义的页面反馈、重复动作、导航循环和实际下载进展判断；优先等待与重新观察，持续无效才结束并保留原因 |
| 下载时间 | 沿用独立的传输进度、无新增字节超时及总时限；下载已经开始时让出模型 worker，不套用页面点击预算中断正常的大文件传输 |
| 排队与端到端耗时 | 区分平台冷却、模型排队、实际推理、网页响应、下载与本地处理；即使排队不消耗活跃预算，仍计入用户实际等待时间与保留会话寿命 |

当前 300 秒、50 次模型调用、100 次动作仅是已实现的默认值，不因在提案中引用而冻结为最终新参数。本轮不直接承诺新的数字或自动无限续期；后续用代表性样本检查什么边界先触发，再决定是否放宽具体数值。应保留一份共享预算，次数上限采用宽松设置，实际控制重点放在时间和无进展循环。

进展判断不等于截图像素或 URL 每次变化：广告、动画和加载指示器变化不能使总时限不断续期。反过来，页面短时不变、下载仍有字节增加或验证仍在处理，也不能立即判成死循环。首期复用已有观察、动作反馈与下载事件，不建设覆盖所有出版社的“页面进展识别器”。

模型选择以完成真实页面任务的成功率与耗时为依据，优先评估成本合适的视觉模型，不预设必须使用昂贵模型。图像输入能力是前提；正确定位、稳定返回可执行动作以及使用反馈的能力仍需验证，不能把“支持看图”直接等同于已经胜任全部站点。复用现有图像输入与动作决策合同，不另设模型评审调用。

后续验收增加正常长流程、短时页面不变但随后成功、真正重复点击/循环导航，以及大文件持续下载等对照样本。关注下载成功率、单篇实际耗时、各阶段耗时和停止原因；模型次数用于解释成本及发现异常，不单独作为优化是否成功的证明。这些是拟议验收方向，本轮未调整运行参数或开展新的真实测试。

### 建议的最小流程

```text
前四层尝试下载，并保留本次已取得的文件和访问结果
  ├─ 已取得有效 PDF -> 发布；不启动 Browser
  └─ 尚缺 PDF
       -> 软件整理有依据的文章入口，复用已有结果、去重与排序
       -> 为本篇文章建立一份累计预算
       -> 在实际 Browser 环境中开页、等待、观察（暂不调用模型）
            ├─ 已触发下载 -> 进入既有下载/验证队列
            ├─ 明确当前入口失败且有备用 -> 在剩余预算内由程序恢复入口
            └─ 需要交互或程序不能确定 -> 将当前页面交给模型
                 -> 后续按既有动作、下载与恢复流程继续
```

软件检查是路线准备，不是对文章身份或下载权限的“认证”。已有 PDF 直链应尽量一次 GET 完成下载和验证，不先 HEAD，再 GET 检查，最后让 Browser 重下。下载中的流或已取得的有效候选继续由原 owner 完成；本地发布失败不重新抓取文件。

进入 Browser 前，软件可以检查 URL 结构、已知线索角色与版本、已登记 API 地址、重复候选及当前操作中已观察到的失败。已知需要凭据的 URL 留给原适配器。下载端点与文章落地页分别保留，PDF 端点失效不意味着 DOI 或文章页面也失效。

普通 HTTP 的结果只描述该访问方式与本次尝试。404 可降低该候选优先级，但不能跨传输、跨会话永久宣布死链；403、验证页、动态 JS、连接异常均不单独证明 Browser 无法访问。无需新增一轮匿名请求来证明 Browser 值得尝试。200 HTML 也不证明页面就是目标文章，模型仍可利用目标元数据观察；有效但错误的 PDF 继续标记身份未验证，留给解析阶段检验。

有来源依据且获准使用的入口，可以进入浏览器的零模型准备阶段。浏览器网络与页面开销仍真实存在；这里只延迟模型调用，不承诺零成本。现有站点首页探测不能替代文章入口准备，也不能因此证明文章全文可用。

### 自动恢复的边界

首版建议只在首次模型请求派发前，支持程序识别的明确导航失败及有界备用入口恢复。未知页面、验证页等需要判断的情况进入模型；不增加复杂的通用网页正确性分类器。模型接管后继续既有会话恢复，不在模型背后自动切换入口。

- 恢复前先确认并结算真实在途捕获；若已经下载，不再同时打开备用入口。
- 换页面、换入口或必要的物理重建都继承同一文章任务的累计预算与失败记录，不再次获得 300 秒/50 次/100 动作。复用现有 clock 与生命周期机制，不新建平行预算系统。
- 自动开页、观察、页面等待占用活跃预算；排队时间仍按现有规则排除。零模型阶段不能无限候选导航，也不能全部放进 `exclude()`。
- 首次导航后的自动恢复遵守既有操作节奏、平台准入与冷却。30 秒冷却针对平台网络活动结束后的资格释放，不是每个资源请求固定等待 30 秒。跨平台由现有 scheduler 交接，不能裸调用导航绕过准入。
- 页面变化继续更新 generation/revision 并使旧动作失效；取消后不启动备用，只有记录过的有限候选可以尝试。
- 在当前操作内记录已尝试入口及实际到达的地址，避免文章地址与 DOI 相互跳回造成循环；保留有意义的 query，不把不同查询参数粗暴合并。运行态定位信息遵循现有 URL/凭据边界，不新增长期 URL 健康表。

### 最小反例与后续验收场景

| 场景 | 预期结果 |
| --- | --- |
| 获准的一次性或签名直链首次 GET 返回 PDF | 使用这次字节发布，不为检查重复消费地址或丢弃文件再由 Browser 下载；定位信息继续遵守现有凭据与日志边界 |
| HEAD 拒绝或结果与 GET 不同 | 不把 HEAD 成功作为门槛；不增加必经 HEAD 探测 |
| 普通 HTTP 返回 403/验证页，实际 Browser 可交互 | 不因预检误拒 Browser；在真实页面上由模型处理需要交互的部分 |
| 同一个地址普通 HTTP 返回 404，实际 Browser 会话可正常访问 | 不把一次 HTTP 失败缓存为跨传输的永久坏链，不因此禁止 Browser |
| PDF 端点 404，文章落地页或 DOI 可用 | 保留文章入口；对失效端点的结果不扩散为整篇失败 |
| Browser 首入口明确失败，备用入口可用 | 首个模型调用前完成有界恢复，不重建整篇预算、不绕过平台准入 |
| 入口准备期间 PDF 下载已经开始 | 进入原下载队列，零额外模型调用，不同时恢复到其它入口 |
| 200 HTML 指向无关页，或下载到另一篇有效 PDF | 不声称 HTTP 成功证明文章身份；保留目标元数据观察与解析阶段身份检验 |
| 备用入口重定向回已失败入口，或出现真实限流 | 防循环并保留停止/延期原因，不靠新 URL 或 session 重置预算/绕过限流 |
| 正常流程需要较多交互，或验证页短时不变后继续推进 | 宽松次数上限不随意截断有效工作；在总时间边界内允许正常等待和重新观察 |
| 广告动画持续变化但反复点击同一控件没有反馈 | 不把无关变化当成进展，不反复续期，按无进展与总时间边界结束 |
| 前一页面模型响应或网络回调晚到 | 不影响后继页面，预算与捕获仍归原逻辑文章任务 |

上述多数是待实现方案的验收要求，不是新功能测试已通过的声明。主 Agent 本轮运行两个现有测试文件中的 7 个定向离线用例，确认累计预算、5 秒冷却、已有候选停止决策、模型实际派发计数及同页恢复保留用量；7 个通过、74 个未选中。该检查不证明多候选入口预检已经实现，也没有进行真实出版社或模型调用。

## 范围控制与后续评估

首期关注已有服务可使用的名称归类与文章定位，暂不建设全球出版社关系库、全期刊目录或历史版权系统。AI 治理也不承担恢复丢弃字段、编造缺失 DOI、证明订阅权限或修改已有文献身份的责任。

进入实施前应先用授权范围内的数据量化：未知名称有多少、涉及多少篇文章、多少确实影响 API 路由。再选取有代表性的样本比较程序规则与 AI 建议的正确性、未知率和误归类情况。数据库统计和真实模型调用尚未在本轮执行。

方案定稿后再确认必要合同、所有权与兼容影响，并按任务实际范围编写计划。本提案不提前固定实施阶段数量。
