## 本轮交互证据（2026-10-19）

Owner 对已展示的 Motion 手感反馈为「目前就挺好的，加了motion之后手感好多了」，随后确认当前版本整体定稿。G7据此沿用已试用参数，不重新要求用户逐项确认；没有伪造12项逐一选值或录屏记录。此确认不等于每一条业务页面的性能已经达标。12 项 A/B/C 对照及参数导出由 `view=lab` 与 `components-gallery.test.ts` 覆盖；组件的菜单、Dialog、Tabs、Popover、Toast、Drawer、Disclosure 使用共同的 CSS/React Aria/Motion 路径。普通虚拟行、路由、PDF 翻页、正文追加、栏宽拖动与数字变化不添加布局动画。

`next-motion.test.ts` 在正式生产资源和合成库上对普通/减少动效双跑：10 轮筛选展开/收起、20 次信息栏状态切换、Dialog 键盘关闭与焦点回归；PerformanceObserver 记录 long task，MutationObserver 记录 PDF canvas 插入，pointerdown 后下一帧记录调度延迟。它验证稳定状态和有界渲染，不把共享 CI 主机的毫秒级计时变成新的通用门禁（遵循 HARNESS）。

首轮并行测试样本：筛选出现一个 52 ms long task，减少动效样本为一个 50 ms；信息栏两种模式均未记录 long task；下一帧延迟约 21–53 ms；20 次信息栏变更的 canvas 插入分别为 0 与 9。这个样本证明没有随动画逐帧重建 PDF，但不能声称所有交互都不存在超过 50 ms 的任务。数据在 ignored `sandbox/runs/2026-10-19-web-experience/pages/react-motion-*-concurrent.json`。后续单独运行样本另存 `react-motion-*.json`，保留首轮证据。单独复测两种模式均无 long task，下一帧最大延迟分别为 49.2 / 38.8 ms，canvas 新增为 0 / 6；这些结果仍限定于本机合成两行库和一页 PDF。

反馈时序还需要区分：下一帧调度时长不等于请求完成时长。提交中的 `aria-busy`、失败保留草稿、成功入口和焦点回归由各页与共享组件直接测试验证；没有可靠服务器进度时不生成百分比。全站两种模式的最终测试数与结果由 11 汇总。

### 最终测量与减少动效修正

原120个样本（12交互×2模式×5次）均保留。原Dialog探针只观察role=dialog外壳，未覆盖子级动画文字，不能把该行冒称文字出现时间；随后改为观察真实标题h2，菜单与Dialog分别记录瞬时点击目标出现、触发器反馈和独立持续按下反馈，三者不互相替代。修正目标后的减少动效仍有超过100ms的文字出现样本。

减少动效原用0.01ms CSS动画/过渡，仍触发React Aria进入动画结束时的同步状态更新。改为实际animation:none和transition:none，系统偏好及应用内减少动效都生效；Motion已有duration=0路径保持。相同两类弹层×5次定向A/B：修正后的10个真实内容样本全部低于59ms、无long task；持续按下结果单列，不用它替换内容时延。没有重跑筛选成功样本，原120及修正探针的before数据均保留。

正式生产版反复筛选与信息栏开合的两种模式样本均无long task，PDF不随动画逐帧重建。测量记录首次满足可视样式/裁剪条件的rAF，包含观测开销，不等同物理显示器延时或普适性能保证。

连续导航的早期失败源于Playwright CDP请求拦截改变卸载keepalive：不用route、禁止非本机DNS并审计所有origin的25次对照均真实释放连接，active保持1；最终120样本122次attach/detach配对，结束active为0。生产连接上限和鉴权不变。
