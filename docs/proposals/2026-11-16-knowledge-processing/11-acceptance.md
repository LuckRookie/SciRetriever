# 11 · 验收、文档与交接

类型：计划（结果块）
负责：计划 16 的全量验证、需求场景验收、文档同步、成套效果评估与部署
状态：Pending

## Outcome

1. Full 通过，或失败已修复并按 HARNESS 5.4 与第 6 节记录；
2. 需求第 7 节验收表中由本计划负责的场景，在合成数据与 fake 模型上逐条通过，包括规4 的两个学科与炼4 的万篇规模；
3. 规格第 8 节已实现的部分并入第 2、6、7 节的现行描述；指南与实现一致；
4. 若获 G-real、G-lib 授权，有阅读层测试集评估（E-read）、成套效果评估、两个学科的真实流程与真实规模的运行，结论只陈述所评估的样本；未获授权时计划标为“工程完成、效果待验”；
5. 若获 G-deploy 授权，4174 部署并完成只读冒烟。

## 进入条件

01–10、12、13、14 退出，或 Owner 决定的子集已退出并在根 README 进度中记录范围。11.10 例外：14 退出 A 后即可进行，不等其它块。04 的退出 B 与计划 21 的进度相关：计划 21 未交付时，本块按退出 A 验收，并在结论中写明初稿路径未验收。

## 责任边界

worker：Full、场景验收的测试与运行、部署、真实服务步骤的执行；总设计师：文档并入、指南、效果评估方案与结论、审阅与验收。

- [ ] **11.3 规4：两个学科的完整流程**〔worker 运行，总设计师 核对〕
  - 材料：两个差别明显的学科的合成文献，例如一个以实验和数据表为主的学科，一个以论证为主、没有“方法”“结果”章节的学科；两组都含只有书目、只有初稿〔计划 21〕、有校订稿的文献。
  - 流程：在同一个库里，对两组分别走完本计划负责的“炼”与“用”：摘要筛查、问题综合、记录比较（两组用各自的记录定义）、发表统计、主题页面、实体归一与关系（两组用各自的实体类型集合），以及 Web 阅读、Agent 分层读取与带出处的导出。“收”与“读”由各自的计划验收；这里只要求两组文献已经在库里，并能被读取。
  - 阅读层：两组都走 `reading-layers`；同一份核心提示词与同一张补丁表管两组。
  - 判据：两组之间不改任何代码、配置、内置规范或产品规则；只改调用方自己定义的问题、记录定义与实体类型集合。需要为某一个学科改规则的地方，记为失败并交 总设计师 判断退回哪一块。
  - 真实版本：Owner 指定两个学科的真实文献与预算，在正式库的隔离副本上重走一遍，须 G-real、G-lib。阅读层的部分以 11.10 的结论为准。
- [ ] **11.4 炼4：万篇规模**〔worker 运行，总设计师 核对〕
  - 材料：至少 25,000 篇合成文献（只有书目、只有初稿〔计划 21〕、有校订稿的混合），fake 模型按固定规则返回用量与延时。
  - 流程：
    1. 选取全部文献，按 06 的 6.7 拆成每份不超过 10000 篇的快照；
    2. 先在小样本上运行一次，形成同口径的单元用量与用时历史；
    3. 对各份快照估算：每份一行加合计，花费与用时都给出区间；
    4. 逐份确认并运行逐篇 `qa`；运行中途停止进程，再恢复；
    5. 以全部清单为输入做一次汇总，另做一次“覆盖合计”。
  - 判据：
    - 估算在开始前给出，区间依据写明样本数；与实际用量的偏差记录在案；
    - 恢复后不重做已完成的单元（fake 模型的调用计数证明）；
    - 汇总与覆盖合计逐份列出并合计到全部选取；故意少输入一份时，该份整份显示为未覆盖；
    - 记录所用数据、时长、吞吐、内存、磁盘与 fake 调用次数。
  - 真实版本：万篇规模的真实运行花费大，只在 Owner 授权的范围与预算内进行，须 G-real、G-lib；未授权时只报告合成规模的结果。

- [ ] **11.10 阅读层测试集评估（E-read）**〔总设计师写方案与判定，worker 执行；须 G-real、G-lib〕
  - 依据：规格 8.16“测试集”。它决定核心提示词与补丁表的取舍，也是需求规4 在阅读层的验收。14 退出 A 后即可进行，核心或补丁每次改动后再做一次。
  - 材料：
    - 机制：14 的合成测试集（`tests/fixtures/`），在每次改动前先跑通，只证明程序可判定的各项；
    - 效果：Owner 选定真实资料，组成须满足规格 8.16：研究论文、综述、学位论文、手册、人写的笔记各至少一份；来自至少两个差别明显的学科；初稿与校订稿都有〔计划 21〕；至少一份按章处理的长资料，至少一份没有章节标题的资料。资料不在库里时，由 Owner 提供，放进正式库的隔离副本。
  - 期望：总设计师为每份资料起草期望（要点、每条要点的依据、应写“原文未给出”的栏目），Owner 核对。资料与期望只存本机 `sandbox/benchmarks/plan16-reading/`，不进仓库。
  - 比较：
    - 程序判定：原句与数字的逐字核对通过率；机器写的句子是否都有引用；分组是否都是资料自己的标题；各栏条数是否在上限内；“原文未给出”与期望是否一致；
    - 人工判定：要点与依据逐条标为对、错、不确定，错因归为漏读、误读、证据不符、格式；
    - 按资料类型（`publication_form`、`article_kind`）分组报告，并报告长资料阈值（14 的 14.5）是否合适。
  - 改动的判定：
    - 某一类型的资料反复出现同一类错误，而核心不变时其它类型都正确，总设计师才提议补丁：写明失败案例（案例 ID、加补丁前的结果 ID、哪里不对），在同一测试集上新旧两版逐份重跑；
    - 只有目标类型变好、其它类型不变差，补丁才写入补丁表；补丁升级 `key-points` 的版本，影响以后全部运行，由 Owner 确认后合入；
    - 改核心或阈值用同一判定；不通过的改动不保留。
  - 结论交 Owner；E-read 通过前，10 的 10.5a 不开工；阅读页计划可以按工程结果开工，效果结论随后补上。
