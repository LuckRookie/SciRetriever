## 1. 讨论结论与产品定位

用户明确：Web 主要用于控制、查看 Agent 工作和提交任务，希望 AI 能接入并代为提交任务。文献库内容也需要方便查看，虽然不是重点，仍须认真设计。用户随后同意“工作台、任务、文献库、设置”的划分，要求先记录提案，讨论充分后再据此编写 plans。

由此确定：**SciRetriever Web 是以 Agent 执行为中心的人类工作台，围绕提交任务、观察执行、控制过程、检查结果组织体验。** 文献阅读是完整的配套能力，产品投入优先服务任务执行与人类协作，不以完整文献管理软件的功能广度为竞争目标。

前一轮曾建议以文献与阅读结果作为首页重点；本次讨论已调整为 Agent 工作台优先。后续设计以本节记录的用户选择为依据。

### 已确认的方向

- 默认首页用于了解 Agent 正在做什么、哪些事项需要人介入、已经得到哪些结果。
- 一级入口为工作台、任务、文献库、设置。
- 支持人类提交和控制任务，并把 AI 接入、代为提交任务纳入正式设计。
- 文献库承担查找材料、查看元数据、阅读原文及已有知识产物的配套责任，保持良好的可用性。
- 先讨论产品与交互提案，再形成实施计划；本轮只记录讨论。

### 尚未确认的建议

后文有关首页布局、Browser 入口层级、任务详情、首次交付顺序及视觉风格均为具体设计建议。用户对整体划分的认可，不等于已经选定前端框架、Agent 接入协议、任务字段或全部交互细节。

## 2. 与现有产品和架构的关系

本提案承接[产品需求](../architecture/requirements.md)、[ADR 0026：科研 Agent 知识组件与人类协作](../architecture/decisions/0026-agent-knowledge-and-human-collaboration.md)与[ADR 0028：查询和扩充分离](../architecture/decisions/0028-query-and-expansion-separation.md)。

上层科研 Agent 理解科研意图、编排任务；SciRetriever 负责文献材料与知识产物的获取、处理、完整性和可追溯性。Web 展示事实、提交意图，继续使用同一套应用能力，不形成另一套文献库或任务业务规则。

以下边界继续适用：

- 查询已有文献与显式发现、下载、解析、分析分别表达。查看页面、打开结果或发现材料缺口不会自动创建任务。
- Agent 可以代用户发起已明确授权的具体任务；普通研究问题不自动构成扩库授权。组合执行须明确步骤、范围和停止边界，任务内无需逐篇重复确认。
- 人类与 Agent 共享文献、任务结果和应用语义；前端不自行推导权限、接纳 PDF 或修改业务事实。
- 页面接管绑定具体 Browser 会话，同一会话只有一个动作控制者；交还后重新观察，过期动作不继续执行。
- 任务失败或取消不撤销已经提交的有效材料；界面须同时呈现有效结果和未完成部分。
- 已确认的 PDF 文件验收与文章身份未验证规则保持不变，原文或结果查看不重新引入下载阶段的身份阻断。

设计收敛后，把新的长期决定同步到相应需求或 ADR，再由 plans 组织实施。本提案不直接更改公开 API、数据库或现有配置合同。

## 4. 信息结构

| 一级入口 | 用户目的 | 主要内容 |
| --- | --- | --- |
| **工作台，默认首页** | 看系统现在在做什么，及时处理问题 | 活动任务、当前步骤、需要介入的事项、最近完成结果，按需呈现 Browser 会话 |
| **任务** | 提交、查找和管理一次工作 | 新建入口、队列与历史、任务详情，人类和外部 Agent 提交的任务统一查看 |
| **文献库** | 检查和使用已有材料与结果 | 搜索筛选、元数据详情、PDF、可读正文、已有分析和来源证据 |
| **设置** | 管理系统运行条件 | 文献来源、模型、Browser、解析服务与运行参数，显示配置状态、显式测试和生效反馈 |

工作台侧重当前活动和需要处理的事项；任务页侧重完整队列、历史和单项详情。两处引用同一任务，避免产生相互独立的状态或重复的操作逻辑。

**Browser 入口建议**：主要从任务或具体文章进入观看和接管；首页提供活动会话的快捷入口。是否还需要独立的多会话总览、会话缩略图如何展示，留待原型讨论，不先新增第五个一级菜单。

## 5. 核心页面与交互建议

### 工作台首页

首页优先回答三件事：

1. **现在在做什么**：活动任务、当前阶段、处理范围和进度；Browser 会话只是其中一种执行表现。
2. **有什么需要我处理**：需要指导、接管或修正配置的事项，附直接进入目标任务的入口。
3. **已经得到什么**：新增元数据、已保存 PDF、已生成知识结果，能直接打开对应材料或结果集合。

展示真实执行信息，例如“正在搜索三个来源”“正在等待站点冷却”“正在接收 PDF”。模型思考、页面等待、文件传输和排队应按可观察事实区分；不把推测、内部思维或虚构百分比当成进度。详细日志可展开，不占据首页主体。

尚无任务时提供清楚的提交和接入入口。断连、空闲、任务失败、等待人工处理应有不同表达，不能都显示为空列表或泛化的“加载中”。具体布局和信息密度通过原型确定。

### 任务提交与详情

人工表单与外部 Agent 接入共用应用用例。提交时让用户或调用方明确目标、范围、执行操作和边界；具体字段、默认值与组合任务表达尚待设计，不在本提案中冻结 wire schema。

任务详情建议包含：

| 区域 | 展示与交互 |
| --- | --- |
| 任务目标 | 提交来源、目标和文献范围、允许执行的操作、停止边界 |
| 当前进度 | 已完成部分、正在进行的步骤、各目标处理情况与等待原因 |
| 实时执行 | 当前 Browser 会话，或搜索、下载、解析、分析的执行反馈 |
| 人工控制 | 按实际能力提供取消、指导、接管等操作，明确影响整个任务、单篇文献还是某个会话 |
| 结果与问题 | 成功材料、部分成功、失败原因、可执行的下一步，以及结果阅读入口 |

任务操作与 Browser 动作不是同一层级。暂停 Agent 页面动作、取消任务和停止文件传输不能用一个模糊按钮代替；哪些能力可用、何时生效、已经提交的结果如何保留，需在后续设计中逐项核实。重试也必须明确对象及是否会重复已有工作。

任务状态刷新应保留用户正在查看的文献和滚动位置。切换页面不应在视觉上造成任务消失；关闭页面后任务是否继续运行，则须依据最终运行生命周期合同表达，当前不作新承诺。

### Browser 观看与介入

建议以“会话选择、当前页面、操作与指导”组织观看界面，让文章标题、任务归属和控制者保持可见。并行工作时，用户能够切换观察目标，清楚区分正在操作页面的会话和正在后台下载的文章。

自然语言指导与向网页输入文字采用不同入口。指导需要返回实际受理或消费状态；点击接管后必须显示控制权是否已经取得，交还后应反馈 Agent 已重新观察并继续工作。截图或连接中断时显示画面状态，避免把旧画面呈现为实时状态。

多会话总览的密度、是否提供画中画、如何提示其他会话需要介入，仍待讨论。长期录像、历史回放不因实时观看需求而自动纳入范围。

### 文献库和设置

文献库须做好搜索筛选、长标题和摘要排版、PDF/正文/分析结果打开、来源与证据展开，以及从任务结果进入后返回原任务。PDF 已保存、正文未解析、尚无分析分别表达；用户查看缺口时可选择后续操作，但读取本身不触发加工。完整文献管理、笔记系统和 Zotero 深度集成不列为本次设计重点。

设置按已有配置责任组织。文献来源就近管理适用能力、参数和凭据；模型和解析服务保留各自入口。保存成功、当前运行是否已生效、是否需要重新组装应易于理解。具体表单仍需盘点现有支持范围，不能只提供外观而没有实际调用。

## 6. AI 接入和任务编排

目标使用路径是：用户向自己的科研 Agent 说明并授权具体任务，Agent 调用 SciRetriever 提交，Web 查看和控制同一任务，调用方取得状态与结果后继续自己的科研工作。

建议人类与 Agent 共用稳定任务身份、状态、控制规则和结果引用；界面展示提交来源与具体目标。“外部科研 Agent”“SciRetriever 内部模型”“Browser 会话”应在需要时区分，不把它们都称作一个含义不明的 Agent。

接入协议（例如 MCP 或其他正式 API）、身份与权限、重复提交处理、进度获取、取消及结果读取合同均待设计。优先复用现有 Entry、Application 和 durable jobs 能力，并核实哪些用例尚未进入统一任务入口；不预先引入新的编排引擎或第二套任务存储。

**建议的首次交付取向**是外部 Agent 接入与人工结构化表单。Web 内自然语言提交可作为后续选项：它需要进一步确定由谁理解意图、如何形成操作范围、如何沿用用户授权。用户尚未确认这两类入口的交付顺序，也未决定是否需要内置对话 Agent。

## 7. 视觉与前端组织建议

视觉需要适合长时间观察、控制与阅读。可评估延续现有暖白、墨绿方向，统一字体层级、间距、状态、按钮和焦点；任务列表保持适度密度，Browser 画面及阅读区保留充足空间。色彩、主题、桌面与窄屏布局尚未定稿。

原型优先用长标题、多任务、部分失败、无任务、连接中断和多会话等内容检验。状态不只依赖颜色，关键操作须具备清楚标签、键盘访问和及时反馈。具体视觉验收与响应式支持范围在交互收敛后确定。

前端建议按工作台、任务、Browser、文献库、设置组织功能，导航与基础组件共享，让人可以从目录理解职责。是否采用新的框架、组件库、路由或状态管理工具，先评估现有实现和交互复杂度；本提案不预定技术栈或目录迁移方案。

## 8. 用于后续原型讨论的场景

以“化学合成”为示例主题，构造明确授权的文献收集场景：外部 Agent 提交有界发现任务，元数据接纳后按已授权的独立下载操作推进，多个来源和 Browser 会话工作，其中一篇需要人工帮助，最后从结果打开材料。若采用组合提交，必须在提交时明确包含发现和下载，不能仅由主题自动推导。

原型需要让评审者走通：查看任务目标 → 理解并行进度 → 定位需要帮助的文章 → 指导或接管 → 交还 → 查看成功和失败结果 → 打开文献 → 返回任务。

这是一条待验证的体验场景，不是新增的固定业务流水线；已有材料的解析或分析任务也应能独立进入工作台。原型使用合成数据，不因编写提案启动真实 Provider、模型或用户数据操作。

## 9. 待继续讨论的问题

| 问题 | 需要确定的内容 |
| --- | --- |
| 首页与任务详情 | 活动任务、待介入事项、会话画面的优先级和空间分配 |
| 任务提交 | 首次支持的任务类型、范围选择、组合操作表达、默认边界及人工表单 |
| AI 接入 | 首先服务哪些调用方、接入协议、状态和结果合同；Web 内自然语言入口是否纳入首期 |
| 控制语义 | 任务与会话各自支持哪些控制；暂停、取消、重试、接管的生效点和反馈 |
| 运行生命周期 | 启动方式、关闭 Web 后的任务存续、断连重连、进程重启后的可恢复范围 |
| 使用与访问 | 先面向本机还是远程访问，单人或多观看者范围及相应控制边界 |
| 视觉与适配 | 风格、主题、信息密度、窄屏主要支持观看还是完整操作 |
| 文献库完成标准 | 首次必须具备的查找、阅读、来源证据与任务结果衔接体验 |
| 前端实现 | 现有入口的复用与整理、组件边界、框架选择和兼容影响 |

建议下一轮先讨论工作台首页和任务详情的布局与关键操作，再通过场景原型检查。问题按实际依赖逐步收敛，不要求一次回答全部问题，也不提前固定实施阶段数量。

## 10. 提案如何进入实施计划

当核心页面和使用路径、首次交付范围、任务/Agent 接入边界及主要生命周期问题足够明确后，整理对应的产品或架构决定，再依据[计划规范](../plans/README.md)编写实施计划。

计划应以可独立验收的结果组织任务，覆盖所需应用合同、生产接线、前端交互与验证。尚未决定且不影响首期的事项明确留后；不能用一个页面原型代替生产能力完成证明，也不把提案中的所有建议自动变成首期必做项。
