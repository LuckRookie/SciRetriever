# 可信全文、文献档案与算子

> 状态：草案，**不授权实施**。
>
> 2026-10-19 讨论中，Owner 已确认[第 2 节](#2-已确认的规则)列出的规则；各问题的答复与待确认项见[第 9 节](#9-问题与答复)。
>
> 本文回答三个问题：
> 1. 一篇文献在进入算子之前，应该处于什么状态；
> 2. 怎样得到可信的全文；
> 3. 单篇算子和多篇算子怎样使用这个状态。
>
> 涉及的现有决定见[第 8 节](#8-与现有决定的关系)，其中 ADR 0010 需要修订。
>
> 本文中的“算子”即 [ADR 0034](../../architecture/decisions/0034-unified-processors-and-results.md) 中的“处理器”。

## 1. 背景

### 1.1 为什么算子显得像脚本

ADR 0034 已经确定了文献级和集合级两类处理器，以及基于版本、规范和输入的复用机制。

讨论中 Owner 反馈：算子“和写一个脚本没什么区别”。原因在于，现有设计集中在执行机制上，而这些机制脚本同样能做到。算子真正区别于脚本的地方有三点：

- 记得以前处理过什么，可以增量更新；
- 每条结果都能指回原文；
- 人工修正不会在重跑时被覆盖。

这三点有一个共同前提：算子读到的文本必须可信，并且每篇文献在进入算子之前都处于同一种明确的状态。本提案先定义这个状态，再定义算子怎样使用它。

### 1.2 解析结果不能直接作为可信源头

2026-07-24 做过一次本地解析对比测试，覆盖 4 篇论文、共 49 页，比较了 MinerU 3.4.4 的 4 种模式和 Docling。测试结果保存在本地目录 `literature/parsed/parser_comparison/`，不随仓库分发。

测试发现：每种模式单独使用都会出错。但 **pipeline（读取 PDF 文字层）和 VLM（识别页面图像）出错的位置几乎不重叠**。

| 文档与位置 | pipeline | VLM | 正确方 |
| --- | --- | --- | --- |
| CJEM2024296 摘要中的热分解温度 | `151.41 ℃` | `151.41%` | pipeline |
| CJEM2024296 引言中的“229 ℃” | `2 2 9 ‰` | `229 °C` | VLM |
| CJEM2024296 引言中的化合物名 K₂BDFOF | `K BDFOF`（下标丢失） | `K_{2}BDFOF` | VLM |
| CJEM2024296 引用信息中的“偕二硝基” | 正确 | `倍二硝基` | pipeline |
| s42256 首页的出版日期 | `xx xx xxxx`（沿用了过期的文字层） | `01 July 2025` | VLM |
| d1ra00651g 中的 fi、fl、ft 连字 | 47 个私用区字符 | 正确 | VLM |
| 标题层级 | 一级、二级区分清楚 | 全部是一级 | pipeline |

另外两点观察：
- hybrid 的两档都漏掉了 CJEM2024296 引言中的一段文字；
- Docling 处理双栏论文时，阅读顺序不稳定。

两种 MinerU 模式都输出带页码和坐标的区块，而且每页的区块数几乎相同。例如 CJEM2024296 第 1 页，pipeline 有 24 块，VLM 有 25 块，其余各页大多完全一致。因此，两边的区块可以用程序对齐。

### 1.3 当前合同

**[ADR 0010](../../architecture/decisions/0010-parser-neutral-markdown-current-result.md)** 规定：
- 每个资产只保留一个当前 `ParserResult`；
- Parser 的私有输出（包括区块和坐标）在解析后清理；
- 如果要同时保存或合并多套 Parser 结果，需要新的 ADR。

**MinerU 适配**目前固定使用 `vlm-engine`，见 [MinerU 注意事项](../../notes/mineru.md)。

**[文档与证据](../../architecture/technical/04-document-evidence.md)**：
- 已有 `utf8-segment-v1` 文本片段定位；
- 页码和区域定位尚未实现；
- Parser 的私有坐标不能直接当作公共定位，必须由文档与证据模块验证后，按它自己的版本化方案发布。

**[ADR 0008](../../architecture/decisions/0008-summarized-markdown-literature-content.md) 与 0026**：每篇文献的总结型 Markdown 原本同时承担三件事，即近似校订、元数据确定和后续打标签。

## 2. 已确认的规则

以下规则由 Owner 于 2026-10-19 确认。

1. **建档先于算子。** 一篇文献必须先完成建档，进入“就绪”状态，才能被算子选中。
2. **建档内容固定。** 建档包括校订稿、结构、元数据、参考文献和标签，按这个顺序完成。
3. **校订采用两份识别。** 用 MinerU pipeline 和 VLM 各解析一次，程序对齐比较，只把分歧区块交给仲裁。
4. **不设“不可信区块”，也不设质量阈值。** 每个区块都必须有一个确定的结果；仲裁结果没有通过硬校验时，这篇文献建档失败，转人工处理。
5. **补充材料与正文属于同一份档案，但分成不同部分。** 每个部分各自解析、各自校订；没有补充材料的文献照常建档。
6. **总结移出建档，改为普通单篇算子。** 它可以默认对所有文献运行。
7. **标签自然增长，粒度为领域级。** 每篇文献的标签不超过总数上限（初值 6），按重要性排序，不强求填满；不设固定维度；先吸附已有标签，找不到才创建；回溯手动执行；整理全自动执行，可撤销。见 4.5。
8. **算子只能从校订稿读取内容。** 筛选范围由元数据和标签决定。
9. **算子分为单篇和多篇两类。** 单篇算子的定义是固定的，结果可以复用。
10. **单篇算子之间暂不互相依赖。** 单篇算子只读该文献的校订稿、结构、元数据和标签。
11. **多篇算子先逐篇读取，再汇总。** 逐篇读取由一个声明好的单篇算子完成，结果可以复用；汇总只基于这些单篇结果。
12. **多篇算子的输入是快照，输出带引用。** 输出可以是 Markdown 报告或结构化表格。快照变化后，结果标记为“已过时”，由人决定何时重新生成。
13. **现有文献重新建档，从已有的解析 Markdown 开始**，见 4.7。

## 3. 文献档案

### 3.1 组成

| 组成 | 内容 | 算子是否可读 |
| --- | --- | --- |
| 身份 | 文献 ID、DOI、各部分 PDF 的 hash | 可读 |
| 原件 | 正文 PDF；补充材料 PDF（可选，可以有多个） | 不可读 |
| 原始解析 | 每个部分各有 pipeline 和 VLM 两份区块列表 | 不可读 |
| **校订稿** | 每个部分一份区块列表。每个区块包含页码区域、类型、最终文字和来源标注；Markdown 由区块列表渲染生成 | **可读，是唯一的内容来源** |
| 结构 | 每个部分的章节及其角色，例如摘要、引言、实验、结果、结论、参考文献；图表清单和图注 | 可读 |
| 元数据 | 题名、作者、期刊、日期、DOI、语言、出版形式、文章性质、作者关键词等。每个字段记录来源，冲突字段做标记，人工确认的字段锁定 | 可读 |
| 参考文献 | 有序列表；如果能对应到库内文献，就建立关联 | 可读 |
| 标签 | 领域级主题关键词，按重要性排序，不超过总数上限；从自然增长的词表中吸附或创建；记录词表版本、模型和打标理由 | 只用于筛选 |

原件和原始解析只供建档和人工追查使用，算子不能读取。

### 3.2 部分

- 一份档案至少包含一个**正文部分**，可以有零到多个**补充材料部分**。
- 每个部分独立解析、独立校订，各自拥有页码和区域定位，因此不会出现“第 3 页是哪个文件”的歧义。
- 补充材料常常比正文晚获取。新增补充材料只会增加一个部分，不会改变正文部分的版本。

## 4. 建档

建档按以下顺序进行：

```
校订稿 → 结构 → 元数据 → 参考文献 → 标签
```

建档是内置流程，不是算子。每篇文献都要经过同样的流程。

### 4.1 校订稿

对每个部分执行以下步骤：

1. **两份独立识别**：用 MinerU pipeline 和 MinerU VLM 分别解析，保留两边的区块列表，包括页码、坐标、类型和文字。
2. **规则清理**：用确定性规则处理，不调用模型。包括：
   - 去掉页眉、页脚和页码；
   - 合并跨行或跨页断开的段落，以及断词连字符；
   - 识别参考文献区。
3. **区块对齐**：按页码和坐标重叠配对区块，并列出只在一边出现的区块。
4. **归一化后比较**：
   - 先统一写法上的差异，例如 `‑` 与 `-`、`（` 与 `(`、中文字之间的多余空格、`1 0 ^ { \circ }` 与 `10^{\circ}`；
   - 再比较数字、单位、化学式和词语。
5. **分流处理**：

   | 比较结果 | 处理方式 | 来源标注 |
   | --- | --- | --- |
   | 内容一致 | 直接采用。文字取 VLM 的写法，标题层级取 pipeline 的 | 两边一致 |
   | 只有写法差异 | 按规则统一 | 两边一致 |
   | 数字、单位或文字存在实质分歧 | 交给仲裁 | 仲裁 |
   | 只有一边有该区块 | 交给仲裁 | 仲裁 |
   | 一边含有私用区字符等可确定识别的缺陷 | 采用另一边 | 采用 pipeline 或采用 VLM |

6. **仲裁**：
   - 输入：该区块在 PDF 上的截图，加上两个候选文本；
   - 输出：选 A、选 B，或者给出修正，并说明理由；
   - 每次只处理一个区块，不重写整篇。
7. **硬校验**：
   - 仲裁结果中的数字、单位和化学式，必须至少在一个候选中出现；
   - 改动不能超出该区块。

   不通过硬校验时，这篇文献**建档失败**，列出需要人工处理的区块。
8. **图片区块**：复杂的反应式图、谱图等，作为图片区块并附图注处理。这属于区块类型，不涉及可信与否的判断。

来源标注只如实记录文字是怎么得到的，不代表可信度判断。

通用视觉 Agent 的全页识别可以作为可选的第三份来源，只在两边都无法对齐的版面上使用。是否引入，等原型统计后再决定。

### 4.2 结构

对每个部分标出：
- 章节及其角色，包括摘要、引言、实验、结果、讨论、结论、参考文献，以及补充材料中的各节；
- 图表清单和图注。

算子可以只读取指定角色的章节。例如提取实验条件时只读“实验”部分，不读引言，避免把引言中引用的他人数据误当成本文结果。

### 4.3 元数据

- 来源包括出版商、Crossref 等权威接口，以及校订稿。
- **按字段确定优先级**：
  - 题名、作者、期刊、DOI 等书目字段，优先采用权威来源；
  - 权威来源缺失时（例如没有 DOI 的中文期刊），采用校订稿中的信息。
- 每个字段都记录来源。来源之间有冲突时做标记，不静默覆盖。
- 人工确认过的字段会被锁定，之后重新建档也不会覆盖。

#### 出版形式与文章性质

现有元数据只有一个自由文本字段 `document_type`，用来记录文献类型。各数据源写入的值来自不同的体系，例如：
- OpenAlex 写入 `article`、`review`；
- arXiv 写入 `preprint`；
- RIS 导入写入 `journal-article`、`book-chapter`；
- 部分数据源留空。

这个字段把“发表载体”和“文章性质”混在了一起。Owner 于 2026-10-19 确认，将它拆成两个固定枚举字段：

| 字段 | 回答的问题 | 取值 | 以谁为准 |
| --- | --- | --- | --- |
| 出版形式 | 文献以什么载体发表 | 期刊论文、会议论文、书籍或书籍章节、学位论文、专利、技术报告或标准、数据集 | 优先采用权威来源（Crossref、OpenAlex、出版商）。只有权威来源缺失时，才采用校订稿 |
| 文章性质 | 在同一种载体中，这篇文章属于哪一类 | 研究论文、综述、快报或通讯、观点或评论、勘误或社论 | 以 Agent 依据校订稿的判断为准，因为数据源的这一项经常不准。数据源的值只作为参考，与判断不一致时标记冲突 |

- 预印本不作为出版形式。它属于现有的 `version_role` 字段（published / accepted-manuscript / preprint）：期刊论文的预印本，出版形式仍然是期刊论文。
- 两个字段都是固定枚举，不是标签，不占标签名额。开放性的说法（例如 benchmark）仍然作为标签。
- 现有 `document_type` 的取值，在重新建档时映射到这两个字段，作为数据源的参考值。映射表在实施时确定。
- 元数据中已有的 `keywords`（作者关键词）原样保留，作为打标签时判断粒度的首要参考（4.5.1）。

### 4.4 参考文献

从正文部分的“参考文献”章节解析出有序列表。如果某条参考文献能对应到库内文献，就建立关联。

### 4.5 标签

2026-10-19 Owner 确认：
- 不预设词表，标签自然增长；
- 标签只描述领域级的主题；细分主题只有在它是全文主导主题时才作为标签；
- 每篇文献的标签设总数上限，不要求填满；
- 不设固定维度；
- 回溯手动执行；
- 词表整理全自动执行，可以撤销；
- 主要化合物可以作为标签。

#### 4.5.1 标签描述什么

标签是一篇文献的主题关键词。它可以是：
- 领域，例如含能材料、起爆药、机器学习；
- 方法或工作类型，例如化学合成、理论计算；
- 文章性质，例如 benchmark；
- 主要化合物，见 4.5.4。

标签不按维度分类，因为固定维度无法覆盖所有情况。例如方法学对比文章需要的“benchmark”，既不属于研究对象，也不属于领域或出版形式、文章性质。

**粒度规则**：标签取文章自己会用作主要关键词的那一层。作者关键词是判断粒度的首要参考。细分主题只有在它是全文主导主题时才作为标签。例如“绿色起爆药”只用于以“绿色”为核心论点的文章；其他起爆药文章打“起爆药”即可。

以下内容**不做标签**：
- 具体数值和实验条件，这些由算子提取；
- 试剂、溶剂，以及其他次要化合物；
- 出版形式和文章性质。它们是必填元数据（4.3），不占标签名额。

#### 4.5.2 数量与顺序

- 每篇文献至少 1 个标签，最多不超过上限。上限是配置项，初值为 6，不要求填满。
- 标签按对本文的重要性排序，第一个是**主标签**。

筛选分为两档：
- “主标签是起爆药”：只选出以起爆药为主题的文献；
- “带有起爆药标签”：包含所有涉及起爆药的文献。

#### 4.5.3 打标流程：先检索，再吸附，最后才创建

1. **写出主题**：Agent 根据正文部分的题名、摘要、作者关键词、引言和结论，按 4.5.1 的粒度规则写出本文的主题，并排好顺序，数量不超过上限。
2. **检索候选**：系统按名称、同义词和定义，在词表中检索与每个主题最相近的若干已有标签，连同它们的定义一起交给 Agent。
3. **优先吸附**：如果某个已有标签的定义能覆盖这个主题，必须使用该标签。
4. **创建新标签**：只有检索到的已有标签都不合适时，才可以创建新标签，并且要逐个说明不合适的理由。新标签必须包含：
   - 中英文名和同义词；
   - 定义，写明包含什么、不包含什么；
   - 上级标签（可选），层级最多两层，例如“含能材料 > 起爆药”；
   - 创建它的文献及其片段，作为示例。
5. **记录**：每个标签都附上打标理由和校订稿片段，并记录词表版本和所用模型。

人工打上或确认过的标签会被锁定，自动打标和整理都不会覆盖它们。

#### 4.5.4 主要化合物

化合物名可以作为标签，但只限于本文合成、制备或研究的目标物。判断规则：这个化合物必须**在题名或摘要中作为本文的研究对象出现**。

| 可以 | 不可以 |
| --- | --- |
| 本文合成的产物；本文研究其性质的目标物 | 试剂、溶剂、催化剂（除非它们本身就是研究对象） |
| | 引言中引用的他人化合物 |
| | 仅用于对比的参照物 |

命名规则：
- 标签名使用化合物的正式名称或通用名称；
- 缩写和代号（例如 ICM-103）写入同义词；
- 文中的编号（例如“化合物 2”）不能作为标签名。

化合物标签占用标签总数的名额。合成系列化合物的文章，应该打化合物类别的标签，不应逐个列出化合物。

#### 4.5.5 标签类别（只用于浏览）

整理 Agent 可以给标签归类，例如领域、方法、文章性质、化合物，方便在词表中浏览。类别同样自然增长。它不约束打标，也不参与筛选。

#### 4.5.6 回溯（手动执行）

新标签创建之前已经打标的文献，不会自动获得这个新标签。由于采用领域级粒度，新标签会越来越少，回溯只在需要时手动执行：

- 每个标签记录它创建时的词表版本。按某个标签筛选时，如果它创建之后还没有回溯过，界面提示“在此之前建档的文献未对照该标签”。
- Owner 可以选择对一个或几个标签执行回溯：
  - 候选文献：在老文献的题名、摘要和已有标签中检索，这一步不调用模型；
  - 判断：Agent 只读这些短文本，一次调用可以同时判断多篇文献、多个标签；
  - 执行前显示候选数量。
- 回溯之后，如果某篇文献的标签数量超过上限，Agent 需要重新排序，并删去排在最后的标签。

#### 4.5.7 自动整理

每批文献建档完成后，整理 Agent 会自动扫描词表并直接执行以下操作，不需要人工审批：

| 操作 | 执行方式 |
| --- | --- |
| 合并同义或高度重叠的标签 | 被合并的标签变成同义词，原 ID 指向保留的标签；已打的标签由程序替换，不重新打标 |
| 补全上级标签（最多两层）、归类 | 不需要重新打标 |
| 修正定义 | 只对带有该标签的文献重新判断 |

每次整理，词表版本加一，并写入变更日志，记录操作、理由和受影响的文献数。Owner 可以随时查看并撤销任意一次操作。

整理与人工锁定的标签发生冲突时，保留人工标签，并在日志中记录。

整理和回溯只改变文献的描述版本，不会使单篇算子的结果失效。

#### 4.5.8 存放

词表属于文献库数据，随库一起保存和备份，可以导出为文件。代码仓库只保存词表格式和合成示例。

### 4.6 原始解析的保留范围

以下统计来自对比测试的实际产出（4 篇，49 页，MinerU CLI 输出）。

| 文件 | 内容 | 每页大小（pipeline / VLM） | 建议 |
| --- | --- | --- | --- |
| `content_list_v2.json` | 按页组织的区块，包含类型、标题层级、文字、表格 HTML，以及归一化到 0–1000 的坐标 | 约 13 / 17 KB | **保留**，作为对齐和校订的输入 |
| `.md` | Markdown 正文 | 约 4 KB | **保留** |
| Markdown 实际引用的图片 | 图、表、公式的截图 | 约 75–85 KB | **保留**。未被引用的图片不保留，本次测试中两种模式分别有 16 张和 20 张 |
| `middle.json` | 行级和 span 级坐标；pipeline 还带识别置信度 | 约 127 / 98 KB | 暂不保留。需要行级高亮时重新解析即可得到 |
| `content_list.json` | 第一版区块列表 | 约 7 KB | 不保留，由 v2 覆盖。实施时需要核对 v2 是否完整覆盖 v1 的字段，如图注、表格 HTML |
| `model.json` | 模型原始输出 | 约 25 / 10 KB | 不保留 |
| `_layout.pdf`、`_span.pdf` | 可视化调试文件 | 约 360 KB 每个 | 不保留 |
| `_origin.pdf` | 原始 PDF 的副本 | 约 220 KB | 不保留，原件已经单独保存。当前适配器也已设置 `return_original_file=false` |

按此建议，每页每种模式约保留 0.1 MB。两种模式合计，1 万页约 2 GB；如果全部保留，约 20 GB。

### 4.7 现有文献重新建档

Owner 决定：现有文献重新建档，从已有的解析 Markdown 开始。

需要注意一个限制：按 ADR 0010 和当前的归档适配，现有文献只保存了 VLM 的 Markdown 及其引用的图片，**没有区块列表和坐标**。因此现有文献的建档流程与新文献略有不同：

1. **VLM 一方**：直接使用已有的 Markdown，不重新运行 VLM。VLM 是两种模式中较慢的一种（约 8.5 秒/页），这样可以省下这部分时间。
2. **pipeline 一方**：新运行一次 pipeline（约 5.1 秒/页），得到带坐标的区块列表。
3. **对齐**：
   - 把 VLM 的 Markdown 按段落、标题、表格和公式切分成区块；
   - 按文本相似度，依顺序与 pipeline 的区块对齐；
   - 页码和区域取自 pipeline 一方。
4. **只在 VLM 中出现的区块**：页码按其前后区块推定，区域留空，定位粒度为“页”。这是如实记录定位精度，不代表可信度判断。
5. **之后的步骤**：仲裁、结构、元数据、参考文献、标签，都与新文献相同。

新入库的文献按 4.1 的完整流程，从两种模式各解析一次开始。

## 5. 就绪条件与文献状态

一篇文献要进入**就绪**状态，必须同时满足以下条件：

1. 每个部分的校订稿中，每个区块都有确定结果；
2. 正文部分的结构至少识别出正文和参考文献；
3. 必填元数据齐全：题名、作者、年份、出版形式和文章性质；
4. 已经打好标签，至少 1 个，且不超过上限。

文献状态只有三种：

| 状态 | 含义 | 能否被算子选中 |
| --- | --- | --- |
| 建档中 | 正在执行第 4 节的流程 | 不能 |
| 建档失败 | 某一步失败，例如仲裁结果没有通过硬校验，或必填元数据缺失。系统列出失败原因和待处理的项，进入人工处理队列 | 不能 |
| 就绪 | 满足以上全部条件 | 能 |

所有条件都是“满足或不满足”的判断，不使用经验阈值。

## 6. 版本

档案的变化分为两类，分别记录版本。

**内容版本**：每个部分各有一个，由该部分的校订稿和结构决定。以下情况会改变内容版本：
- 更换 PDF；
- 重新解析；
- 校订规则或对齐规则升级；
- 人工修订校订稿。

**描述版本**：整份档案一个，由元数据和标签决定。以下情况会改变描述版本：
- 手动回溯、词表自动整理；
- 元数据来源更新；
- 人工修改元数据或标签。

两类版本变化的影响不同：

| 变化 | 单篇算子结果 | 多篇算子结果 |
| --- | --- | --- |
| 某个部分的内容版本变化 | 只有读取了该部分的算子结果失效 | 如果快照中某成员被读取部分的版本变化，结果标记为过时 |
| 新增一个补充材料部分 | 只有声明读取补充材料的算子需要重跑 | 同上 |
| 描述版本变化 | 不失效 | 冻结的快照本身不变。只有按筛选条件重新生成快照后，成员才可能变化；如果算子声明使用元数据字段，结果标记为过时 |

## 7. 算子

### 7.1 单篇算子

单篇算子需要声明以下内容：

| 声明项 | 示例 |
| --- | --- |
| 范围 | 文章性质为研究论文，且带有“起爆药”标签 |
| 读取的部分与章节角色 | 正文的“实验”章节，加上补充材料 |
| 输出类型与规范 | 一组字段，或一段文字 |
| 版本 | — |

**复用规则**：结果绑定以下几项。这几项都不变时，直接复用已有结果：
- 被读取部分的内容版本；
- 算子版本；
- 规范；
- 模型配置。

**结果状态**有四种：

| 状态 | 含义 |
| --- | --- |
| 已提取 | 找到并提取了所需内容 |
| 原文未报告 | 读完了所需部分，但其中没有相关内容 |
| 无该部分 | 文献缺少算子声明要读的部分，例如没有补充材料 |
| 读取不完整 | 没有读完所需部分 |

“原文未报告”和“无该部分”要严格区分，后者不能当作前者。这与 ADR 0034 中覆盖与空结果的区分一致。

每个提取值都必须指向校订稿中的具体片段，并通过片段对应到 PDF 的页码区域。

### 7.2 快照

- **快照**由一组文献组成，并冻结每篇文献的各部分内容版本和描述版本。
- 快照可以由筛选条件生成，筛选条件包括元数据和标签。
- 同一条件在不同时间执行，会得到不同的快照。两个快照之间可以比较差异：新增、移除了哪些文献，哪些文献的内容版本有更新。

### 7.3 多篇算子

多篇算子分两步执行：

1. **逐篇读取**：对快照中的每篇文献运行声明好的单篇算子。这一步的结果按 7.1 的规则复用。
2. **汇总**：只基于第 1 步的单篇结果进行汇总。需要核实时，可以按片段回读校订稿。

**输出**有两种形式：
- **带引用的 Markdown 报告**：每个论断都标出来源文献和片段；
- **结构化表格**：每个单元格都能指回原文，可以导出。

**更新规则**：结果绑定快照。快照中的成员增减，或成员被读取部分的内容版本变化后，结果标记为“已过时”，由人决定何时基于新快照重新生成。

可以直接合并的输出（例如计数、拼接记录表）可以做增量更新。

### 7.4 总结

总结是一个普通的单篇算子：
- 读取正文部分；
- 可以默认对所有文献运行；
- 供人浏览和检索使用；
- 不参与建档，也不影响文献是否就绪；
- 其他算子不以总结作为输入。

| 决定 | 关系 | 需要的动作 |
| --- | --- | --- |
| ADR 0003：MinerU 由运维方管理 | 不变 | 需要确认运维方的服务能否按请求选择 pipeline 或 VLM，否则要部署两个实例（Q2） |

## 9. 问题与答复

| 问题 | 状态 | 结论 |
| --- | --- | --- |
| Q1 是否先验证 | 已定 | 先测试验证，由 Owner 另行安排人员执行（第 10 节） |
| Q2 MinerU 服务能否按请求选择模式 | 基本可行，有两点待确认 | MinerU 的请求本身带 `backend` 字段，可以逐个请求指定，见 `profile.ts`。待确认：一是运维方的服务已下载并能加载 pipeline 所需的模型（版面、OCR、公式）；二是当前适配器固定使用 `vlm-engine`，归档校验也只接受 `vlm`，需要扩展为两种模式 |
| Q3 仲裁模型与预算 | 不在本提案范围 | 由 Owner 另行安排 |
| Q4 原始解析的保留范围 | 有建议，待确认 | 只保留区块列表 v2、Markdown 和被引用的图片，见 4.6 |
| Q5 现有文献 | 已定 | 重新建档，从已有的解析 Markdown 开始，见 4.7 |
| Q6 标签词表规则 | 已定 | 自然增长、领域级粒度、总数上限（初值 6）、按重要性排序、不设维度；主要化合物可以作为标签；回溯手动执行；整理全自动执行，可撤销。见 4.5 |

还有一个待决定的问题：现有文献重新建档期间，已有的总结和算子结果是否继续可读，以及它们在重新建档完成后怎样处理。

## 10. 验证路径

测试验证由 Owner 另行安排人员执行，以下步骤供执行者参考。每一步都可以单独停止，前一步的结果决定后一步是否值得做。

| 步骤 | 内容 | 授权 |
| --- | --- | --- |
| 0 | 基准集：在对比测试的 4 篇、49 页上，人工标注关键数值、单位、化学式，以及段落是否完整 | 需要 Owner 投入时间 |
| 1 | 只读原型：用现有的 pipeline 与 VLM 产出做对齐和比较，统计一致、写法差异、实质分歧和单边区块各占多少比例，不调用模型 | 只读，可以直接做 |
| 2 | 对照基准集，计算“两边一致”的区块中仍有错误的比例，以及分歧区块中各方的正确率 | 只读 |
| 3 | 仲裁小样本：对分歧区块调用视觉模型，统计仲裁正确率、硬校验失败率和单页成本 | 需要授权调用模型 |
| 4 | 编写 ADR（修订 0008/0026、0010、0034）和实施计划 | Owner 确认方向 |

## 11. 风险

| 风险 | 缓解 |
| --- | --- |
| GPU 时间约增加一倍。按测试估算，两种模式合计约 13.6 秒/页；1000 篇、每篇 10 页，约 37 GPU 小时 | 新入库文献先建档，现有文献按需补建；VLM 的结果可以复用 |
| 区块对齐失败导致仲裁量过大 | 第 1 步先统计；对齐失败集中的版面类型单独处理，或引入第三份来源 |
| 硬校验失败的文献过多，人工处理队列堆积 | 第 3 步统计失败率；按失败原因改进规则 |
| 两份识别在同一处都出错，无法发现 | 用基准集衡量；对高可信要求的数据集做人工抽检 |
| 校订规则改变引起大面积重跑 | 内容版本按部分计算，只有文字确实改变的部分才会触发下游重跑 |

## 附录：已考虑的校订方案

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| 只用 VLM，加规则检查 | 对比测试 README 的建议 | 成本低，但 `%` 和 `℃` 这类错误很难用规则全部发现。没有第二份来源，就无法对照 |
| Agent 整篇重写 | 对照 PDF，让 Agent 输出整篇整理稿 | 重写后的错误读起来通顺，不易发现；成本高；长文受输出长度限制；会丢失定位；改动范围无法审查 |
| Owner 原案：MinerU 解析，视觉 Agent 手写一份，再由 Agent 对比汇总 | 两份独立来源相互对照 | 保留了“两份对照”这一核心思路。但 MinerU VLM 本身就是“看图手写”，而且在本地运行；让 Agent 通读对比，容易漏掉单个字符的差异；汇总相当于第三次整篇重写 |
| **采用**：两份 MinerU 识别 + 程序比对 + 只仲裁分歧 | 见 4.1 | 采用 |
