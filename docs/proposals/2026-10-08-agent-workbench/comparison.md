## 1. v0 的实际观察

以 Chromium 的 1440×900 窗口打开默认 A 布局：

| 观察项 | 结果 | 对使用的影响 |
| --- | --- | --- |
| Browser 现场标题 | 顶部约 y=796 | 首屏只能看到区域开头，难以理解当前页面操作 |
| 待协助面板 | 顶部约 y=357 | 桌面可见，但“一篇文章”的目标表达不够具体 |
| 辅助文字 | 30 个可见 p/small/td/button 元素小于 12px | 状态和辅助信息的长期可读性需要改善 |
| 390px 窄屏待协助面板 | 顶部约 y=1836 | 用户需要较多滚动才能处理问题 |
| v0 的 B 布局 | Browser 标题可上移到 y=357 | v0 已有可用的顺序变体，问题不能简单归结为缺少 Browser 入口 |

v0 的四个入口、显式任务范围、结果保留、合成内容标识和轻量离线实现值得保留。

## 2. Opus 的反对意见与共同方向

Opus 同意问题主要在首屏信息权重，而不在配色；但反对把“Browser 放到最上面”直接当作最终答案。它认为**首先应该前置需要人处理的事项**。Browser 只是某些任务当前使用的方式，不能盖过公开来源、API、解析和分析。

Opus 建议：

- 顶部采用可收起的待协助条，明确任务、文章、卡住的步骤、原因和一个主操作。
- 主体以活动任务列表为中心，同时呈现当前目标、阶段、进度和下一操作；只为需要 Browser 的任务提供缩略图。
- 四张大统计卡改成简洁状态条，最近产出降低优先级；动态辅助理解执行，不成为日志墙。
- 任务详情承载阶段记录、文章与产物；Browser 观看与接管进入较大的独立视图，返回保留上下文。
- 辅助文字至少 12px，主体约 13–15px；墨绿强调主操作，琥珀色强调待协助，状态同时提供文字。
- 不做多路实时 Browser 画面墙或自动轮播，也不新增复杂集群监控。

Codex 接受“待介入优先、任务统领、Browser 隶属具体执行”的方向。相较于只把 Browser 卡片移到上方，这更符合用户希望控制和观察 Agent 工作的目的；同时保留便捷进入当前会话的路径。

## 3. 这次应对着页面比较什么

| 维度 | 原版 v0 | 对比版的设计目标 |
| --- | --- | --- |
| 首页内容 | 统计、主任务卡、Browser 卡片和右侧动态 | 待协助事项优先，活动任务承担主要信息 |
| 目标识别 | 待协助提示较概括 | 直接看到文章、任务和当前原因 |
| 控制路径 | 从任务或会话进入操作 | 每项任务的下一操作更直接，介入对象更明确 |
| Browser 的地位 | 独立区域，容易成为视觉主角 | 属于具体任务与文章，其他执行方式同样可见 |
| 美化方式 | 暖白墨绿，较多卡片与小号辅助文字 | 延续色彩，通过密度、字号、对齐和状态层级改进 |
| 文献库 | 已有搜索、筛选和详情示意 | 保留阅读与结果检查能力，控制首期功能广度 |

最终选择可以组合两版优点，不要求整版替换。下一轮优先确认首页信息顺序和任务进入路径，再调整字体、间距和具体组件。

## 4. 验证与限制

两版都是可点击的设计原型。模拟提交、接管、指导、取消与文件获取只改变页面内存，不产生真实材料、任务或配置。Agent 接入协议、任务生命周期和后端对象图仍由提案继续讨论。

Opus 版的初步 Chromium 渲染检查在 1440×900 和 390px 下未发现页面报错或外部网络请求；桌面待介入标题位于约 y=115，具体文章位于约 y=184，首屏可见。实际浏览显示，它的信息更紧凑、待介入对象更明确；v0 的独立 Browser 观看区域及视觉层次也有保留价值。上述判断是评审意见，不是已确认产品决定。

Codex 保留临时目录中的 Claude 原始 HTML，仅在提案副本中补上离线 CSP、取消后禁止继续发送指导及过期反馈、交还后重新观察提示、PDF 文章身份未验证标记，并将“共享同一文献库”改为固定原则、纠正 Browser 模型标签。这些修正不改变 Opus 的主要布局。

较完整的交互遍历执行到断连场景时，测试脚本尝试点击已经 `aria-disabled` 的按钮，被 Playwright 正确阻止并超时；该轮不能计为完整通过。接管、会话间指导草稿隔离、交还和示例下载已在此前步骤执行。用户随后要求本次收口，未继续执行剩余交互与对比容器遍历。本轮不运行生产 Full，也不把样例交互当成生产验收。
