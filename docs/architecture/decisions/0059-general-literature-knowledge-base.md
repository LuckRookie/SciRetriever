# ADR 0059：通用的文献知识库：人和 Agent 并列，蓝图按五件事组织

类型：决策（ADR）
负责：产品定位与服务对象；需求按目的组织的写法；用户整理的模块归属
状态：Proposed（2026-11-10，待 Owner 接受）

- Date: 2026-11-10
- 依据：Owner 2026-11-10 的要求，原话如下：

  > 本项目的核心是领域通用数据库，同时对收集到的数据进行加工，做成Agents的知识测。Agents可以从本项目中获取知识、以及保留之前知识加工之后的内容（反复利用）。

  > 本质上我们的项目有两个服务对象：人、Agents。同时不只是Agents需要知识总结，人也需要，人要学习、要写综述、做研究此时都可以借助文献

  > 随意你要分清楚，什么是目的，什么是手段。我们的这一句话肯定是要指引我们的方向的，不要被其他内容给约束了。

  > 第一节说法也没错，我们这个确实可以作为科研Agents系统中的组件，但是我们现在又不只是科研Agents系统中的组件。

  > 人本身也在创造知识，PDF就是人写好的创造知识的工具，包括到后面，如果把产品嵌入到科研工作流中，那其实Agents也会创造知识对吧。咱们目标是给人和Agents用的知识库，加文献，是因为文献是目前可稳定获取的、可解析的知识。

  > 我们不一定要自己做，外部有很多人类的知识库产品，比如说obsidian、notion等。写作也不是非要在咱们这里写。

  > 我觉得，之前都过于陷入到了手段里面了，没有按照真正的目的来去做。

## 背景

2026-09-25 的 ADR 0026 把产品定为科研 Agent 系统的组件，人是正式使用者。此后面向人的能力陆续加入：以文献库为中心的 Web、阅读器、批注、翻译、从外部文献管理工具导入。产品定位没有随之修改。

2026-11-10 对蓝图的审视得到三组事实：

- **需求偏向做法。** 原需求 R1–R13 约 1.6 万字，其中发现、元数据和全文获取三条占 49.5%，总结与提取两条占 9%。来源选择规则、配置界面的分层、浏览器操作的时间和次数上限都写在需求里。
- **决定偏向做法。** 现有 51 份 ADR 中，定方向的 7 份，划边界的 9 份，规定做法的 35 份。服务于全文获取的 18 份，服务于知识加工的 3 份，其中最关键的 ADR 0044 尚未接受。
- **核心链路没有成立。** 实际文献库有 35,227 篇书目，其中有全文的 926 篇，完成建档的 3 篇。

ADR 0004 早已规定需求只写使用者的问题和结果，但没有执行。

## 决定

### 1. 产品是什么

SciRetriever 是通用的文献知识库，让人和 Agent 都能从任何领域的海量文献中得到自己需要的可靠知识，用于学习、写作和研究。

它有两种用法，共用同一个文献库：

- 研究者把它当作自己的文献库，在其中收集、整理、阅读和总结文献；
- 它也可以作为科研 Agent 系统中的文献材料与知识服务组件。

产品不只为其中一种用法设计。

### 2. 人和 Agent 并列

1. 人和 Agent 是并列的服务对象。每一项知识能力都要同时回答两个问题：人怎样用，Agent 怎样用。
2. 人使用 Web，Agent 使用命令行和 MCP。三者共用一个库和一套业务含义，这一点沿用 ADR 0033 与 ADR 0038。
3. 人和 Agent 都能发起加工，并取用同一份结果。
4. “科研 Agent 是主要的程序使用者”只描述机器入口，不表示人是次要对象。

### 3. 蓝图按五件事组织

产品要交付五件事：

| 简称 | 交付什么                                               |
| ---- | ------------------------------------------------------ |
| 收   | 把一个领域的文献成规模地收进库，并拿到全文             |
| 读   | 人和 Agent 都能读到每篇文献的全文                      |
| 理   | 人能把它当作自己的文献库来整理                         |
| 炼   | 按人或 Agent 提出的需要，把成批文献加工成知识          |
| 用   | 找到并取走需要的知识，人用于学习和写作，Agent 用于研究 |

“可靠”不是第六件事，它是贯穿五件事的品质：全文是真的，知识能回到原文核对，覆盖了多少、缺多少说得清。

蓝图各层按以下规则书写：

1. **区分目的和手段。** 检验方法：假设一件事的成本为零、速度足够快，它是否仍然重要。不再重要的就是手段。保存和复用加工成果是手段，因为加工有成本才需要它。
2. **需求只写三件事**：为谁服务，要让他们得到什么，怎样算做到。做法写进 ADR 和技术文档。这是对 ADR 0004 的重申。
3. **总设计先写五件事各由哪些模块负责**，再写各模块。
4. **一项做法的验收写在规定这项做法的 ADR 或技术文档里**，不写进需求的验收表。

### 4. 用户整理是一个独立的模块

1. 在原有八个模块之外，新增“用户整理”模块。它负责使用者对文献的组织和标注：分组、保存的筛选条件、批注和笔记。
2. 这些内容是使用者自己的数据，不是文献事实。它们不改变文献的身份、书目信息和材料；文献事实仍由“文献与材料”负责。
3. Agent 在同等授权下可以读取这些数据。
4. 标签的归属不变，仍按 [ADR 0037](0037-literature-archive-and-proofread-text.md) 与 [ADR 0053](0053-scope-terms-led-by-tags.md)。
5. 原有八个模块的名称、编号和责任不变。

### 5. 知识来源不以文献为界

这一节是方向，当前不设计、不验收。

1. 文献进入产品，是因为它是目前可以稳定获取和解析的知识。
2. 人和 Agent 也创造知识，例如笔记、总结和研究过程中的产出。后续它们应当能进入知识库并参与加工，落脚点是“用户整理”模块。
3. 写作和笔记工具不在产品内自建，由外部的知识库工具承担。产品负责与它们的导入和导出衔接。
4. 当前的核心是两件事：获取已有的知识（目前是文献的 PDF），以及对知识的加工和处理。

## 后果

- 产品需求已按第 3 节重写。原需求里的做法，凡是只写在需求里的，已先补进技术文档再删除。
- [总设计](../design.md)增加“五件事落在哪些模块”一节和第九个模块。原有八个模块对应的技术文档 01–08 和代码结构不改名。
- “用户整理”需要一篇自己的技术文档，把现在散落在各处的分组、筛选和批注内容归拢。由后续计划安排。
- ADR 0044 在提请接受之前，须按第 2 节第 3 条修订：人和 Agent 都能发起加工。
- 第 5 节不产生当前工作。导入系统（ADR 0058）和知识加工的输入准入在后续设计时不得写死“只接受文献”。
- 两个问题留待另行决定：
  - 全文文本是否分级，即是否每篇文献都要经过模型校订。这是“海量”与“可靠”之间的取舍。
  - 建档规则里偏向单一学科的内容怎样处理，例如标签规则中的“主要化合物”。

## 考虑过但没有采用的方案

| 方案                                          | 没有采用的原因                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 维持“科研 Agent 组件”的定位，人的能力作为附加 | 人的阅读、整理和学习已经是正式需求。定位不改，知识加工会继续只为 Agent 设计                |
| 按五件事重新划分全部模块                      | 八个模块的责任和数据归属大体合理。重新划分要给八千多行技术文档和代码结构全部改名，收益很小 |
| 把用户整理并入“文献与材料”                    | 两类数据的规则不同：使用者的数据属于个人、随时可改；文献事实要有来源，并且保守地收敛       |
| 在产品内自建写作和笔记工具                    | 外部已有成熟的产品，写作不必在本产品内完成                                                 |
