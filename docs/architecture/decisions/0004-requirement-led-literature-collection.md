# ADR 0004：产品需求与派生设计的责任边界

- Status: Accepted
- Date: 2026-07-29
- Supersedes: 旧文档中把 Work、状态机、CLI、解析器协议和其它技术机制写成产品需求的表述
- Superseded by: none
- Related: [产品需求](../requirements.md)、[设计文档](../design.md)、[技术文档](../technical.md)

## 背景

旧需求文档混入了数据模型、状态、命令、配置、解析器协议和实现验收，使技术方案反过来定义了用户问题。这样既掩盖了真正需求，也会把尚未讨论的设计提前固化成产品合同。

Owner 已重新确认产品需求：用户指定领域条件，系统从多家供应商搜索文献元数据，使用元数据获取文献资产，解析文献并获得轻结构化文本，最终形成文献数据库。

## 决策

1. [产品需求](../requirements.md)只定义用户问题、输入、核心业务流程、产品结果、质量要求和用户可观察的验收标准。
2. 数据模型、算法、模块、状态、协议、数据库技术与物理 schema、存储引擎、并发、部署、CLI、供应商接入和解析器选择都属于派生设计，不得写成核心产品需求。文献数据库本身仍是[产品需求](../requirements.md)定义的产品结果。
3. [设计文档](../design.md)负责从需求逐项推导系统架构、模块命名、逻辑对象、数据流、所有权和关键取舍。每项核心设计必须能够说明它解决了什么需求压力。
4. ADR 只记录已经由 owner 接受、会长期约束后续设计的重要选择。尚未讨论或仍可自由调整的细节不得以 `Accepted` ADR 固化。
5. [技术文档](../technical.md)负责把设计文档映射到代码目录、依赖、端口、持久化、外部访问、配置和运行技术；README、源码和测试负责说明当前实现。
6. 当前项目处于 pre-v1，不为被删除的需求表述、旧设计章节或旧内部模型保留文档兼容层。历史材料可以归档，但不参与当前权威解释。

## 后果

- 阅读产品需求时不需要先理解 Work、状态机、MinerU 或 CLI。
- Work/WorkVersion、不可变资产和 parser adapter 可以继续作为设计，但必须以解决多来源重复、版本、追溯和解析等需求压力为理由。
- 新设计先更新设计文档或形成讨论结论；只有需要长期锁定的关键选择才新增或修改 ADR。
- 当前代码行为不能因为已经实现就自动升级为产品需求。

## 需要新 ADR 的变化

以下变化需要新的 owner 决策：

- 改变需求、设计文档、技术文档、ADR 和当前实现之间的权威顺序；
- 把特定实现机制提升为产品不可替代的组成部分；
- 在存在受支持数据或公开契约后引入兼容、迁移或弃用政策。
