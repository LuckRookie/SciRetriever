# ADR 0002：多来源文献身份与增量处理

- Status: Accepted
- Date: 2026-07-23
- Revised: 2026-07-29
- Supersedes: none
- Superseded by: none
- Related: [产品需求](../requirements.md)、[系统设计](../system-design.md)、[ADR 0001](0001-sciretriever-scope-and-boundary.md)

## 背景

一次领域收集会从多家供应商获得重复、不完整或相互冲突的元数据。同一学术工作还可能具有预印本、作者接受稿和正式发表版。资产和解析文本必须对应到正确的文献版本，批量运行也必须能够保留部分成功并在以后继续补全。

这些问题需要稳定的内部身份和增量处理设计，但不意味着“以 Work 为中心”是产品需求。产品目标仍是大批量文献收集及其文献数据库结果。

## 决策

1. 系统内部使用 `Work` 表示同一学术工作的稳定聚合身份，使用 `WorkVersion` 表示可以独立拥有书目元数据、资产和解析结果的实际版本。
2. `Work` 和 `WorkVersion` 是内部一致性机制，不是用户必须理解的产品中心，也不改变[产品需求](../requirements.md)定义的工作流。
3. 供应商返回记录作为来源 observation 保存。系统另外提供面向查询和展示的统一元数据视图，不能用一个供应商值无声覆盖其它来源事实。
4. 跨来源身份收敛采用保守、确定且可审计的规则。明确相同才自动合并，明确冲突时保持分离，证据不足时不得使用不可复现的猜测静默合并。
5. 文献资产和轻结构化文本归属于具体 `WorkVersion`。相同文件字节可以复用，但版本、资产、来源和解析结果之间的关系必须分别保留。
6. 元数据、资产和解析结果分别提交。后续阶段只消费已经提交的数据库事实和资产，局部失败不撤销其它文献或前面阶段的有效结果。
7. 每篇文献当前可以执行什么操作，由数据库中已有的元数据、资产和解析结果判断，不由另一套批处理任务状态定义。
8. 产品按 owner 已确认的单机环境设计，不要求跨机器协调或分布式任务所有权。同一主机内采用何种进程模型、互斥、lease、heartbeat、中断恢复和调度方式，由后续系统设计决定。
9. 已经提交的元数据、资产和解析结果在运行中断后仍然有效；后续运行根据这些事实补充缺失内容。具体中断与调度机制留给系统设计。

## 后果

- 一个供应商记录不等于一篇新文献，也不天然等于一个书目版本。
- 资产获取和文献解析可以独立补全，不要求每次重新执行元数据搜索。
- 批次、失败和尝试记录只用于调度、诊断和审计，不能成为文献身份或可用程度的第二真相源。
- 具体身份匹配字段、版本关系算法、统一元数据投影规则、批次选择方式和物理 schema 留给系统设计与技术架构讨论，本 ADR 不提前固定。

## 需要新 ADR 的变化

以下变化需要新的 owner 决策：

- 取消 Work/WorkVersion 两层内部身份；
- 让 provider 记录直接成为数据库主身份；
- 让批处理任务状态取代已持久化文献事实；
- 引入跨机器协调或分布式 worker 系统。
