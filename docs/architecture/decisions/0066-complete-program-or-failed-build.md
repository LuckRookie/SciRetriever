# ADR 0066：构建交付完整的程序，缺少部件即失败

类型：决策（ADR）
负责：安装与构建的完整性：主线功能需要的本机部件有哪些、由谁取得、取不到时怎么办；启动时的把关；本机部件与外部服务的界线
状态：Proposed（2026-11-25，Owner 已决定第 1 节的原则与第 2 节里“Xvfb 等浏览器相关的部件也随程序到位”；第 3 节各部件的取得办法、第 4 节的启动把关与第 5 节的过渡顺序待 Owner 审阅；MinerU 见“还没有决定的事”）

  > 我认为应该构筑我们的程序的时候自动把所有相关的包都一起打包。不需要提示，要么就直接失败，要么就给安装好，包括Xvfb等浏览器相关的包。minerU我也在考虑可以作为可选包，因为minerU比较大，我们虽然接受外部服务，但是我们也可以安装到自己的程序里面

## 背景

2026-11-25，第一位外部使用者按 README 从源码安装：`pnpm install`，`pnpm build`，启动服务。他导入了 323 个 PDF，每一篇的标题都是文件名，作者、期刊、年份都是空的。

原因是程序读 PDF 的文档信息、XMP 与首页文字靠 MuPDF 的 `mutool`，而它要另外执行 `pnpm vendor:mupdf` 编译。这一步没有做时：

- 构建照样成功；
- 服务照样启动；
- 环境检查命令 `doctor` 不检查 MuPDF；
- 导入时读不出线索不算错误，文献以文件名入库并标为书目待补，页面上没有任何说明。

当天写的上手指南还把这一步写成“只导入和阅读 PDF 可以先不做”。

这不是一句文档写错的问题。当时的安装只取得 JavaScript 依赖并编译本项目的代码。主线功能还需要的本机部件有：MuPDF；检查 PDF 与取文字的工具（`pdfinfo`、`pdftotext`）；隔离与加锁用的 `prlimit`、`flock`；受控浏览器要用的 `Xvfb` 与 CloakBrowser。这些都靠使用者自己另外准备，缺了哪一样程序都不说。项目里有一个把 Node 与 MuPDF 一起打进去的便携包，缺 MuPDF 时拒绝打包，但它没有发布过，使用者拿不到。

## 决定

### 1. 构建的产物是完整的程序

- 主线功能需要的本机部件，由构建负责取得并放到程序能找到的地方。
- 取不到任何一样，构建就失败，并写明缺什么、为什么取不到。
- 不产出缺部件的程序，也不用提示、警告或文档里的“可以先不做”来代替。
- 主线功能指：导入文献、阅读、获取 PDF（含受控浏览器这一级）、生成全文在本机这一侧的工作。

### 2. 部件分三类

**随程序到位的本机部件。** 构建取得，使用者不必另外安装：

- MuPDF（读 PDF 的线索，渲染校订用的页面图）；
- 检查 PDF 与取文字的工具（现在是 `pdfinfo`、`pdftotext`）；
- `Xvfb`；
- 受控浏览器的 runtime：CloakBrowser 的 wrapper 与固定版本的 binary；
- 发布包里的 Node。

**基础系统自带的命令。** `flock`、`prlimit` 属于每个受支持的 Linux 都有的基础工具，不打包；构建检查它们，缺了就失败。

**外部服务。** 解析服务、模型服务、元数据与 PDF 的来源不是程序的部件，由使用者配置。没有配置时，对应的功能说明需要先配置什么；这不算程序不完整。

### 3. 取得部件的办法

每一样都遵守：

- 版本固定，取得后核对摘要或签名；
- 不需要 root；
- 包含在同一条构建命令里，没有需要使用者另外记住的步骤；
- 许可允许随包分发的，放进发布包；不允许或尚未确认的，由安装步骤从它的官方来源取得，取不到同样失败。

### 4. 启动与检查

- 服务启动时核对第 2 节的本机部件与基础命令。缺任何一样就拒绝启动，列出缺的部件与取得的办法。
- `doctor` 检查同一份清单，结论与启动时一致。
- 主线功能没有“缺部件也能跑”的降级运行。

### 5. 过渡

某个部件的“缺了就失败”，与它的自动取得同时生效。在构建还不能自动取得某个部件之前，不先加上对它的强制检查，以免没有 root 的使用者从“能装、少一项功能”变成“装不上”。

### 6. 文档

安装文档不把影响主线功能的步骤写成可选。安装步骤以构建命令为准；文档只说明构建需要的前提（联网、编译器）与失败时怎么办。

## 还没有验证的前提

- `Xvfb` 能不能在没有 root 的情况下随程序到位（随包带上它与所需的库，或用别的办法提供显示）。没有验证过。
- `pdfinfo`、`pdftotext` 是随包带上，还是改由已经随程序到位的 MuPDF 完成同样的检查，从而去掉这一项依赖。没有比较过两者的结果是否一致。
- CloakBrowser binary 的分发权利。运行清单现在写的是“operator-supplied; verify distribution rights separately”。在确认之前，发布包不带它，由安装步骤从官方来源取得。
- 发布包在别的机器上能否直接运行。MuPDF 的构建现在要求 glibc 2.38 或更新，其他部件的要求没有量过。

## 还没有决定的事

- **MinerU 作为可选包。** Owner 的考虑是：MinerU 体量大，可以做成可选的、装进本程序的包，同时保留接外部服务的方式。这会改变 [ADR 0003](0003-operator-managed-mineru-service.md) 第 2 条（MinerU 服务由 operator 独立部署和管理）。尚未决定，决定时另写 ADR。
- 是否另外提供容器镜像。它不能代替第 1 节：已知的使用者在共用服务器上，没有 root，也未必能用容器。

## 后果

- 从源码构建需要联网和编译器，时间变长；构建失败的情形变多，但每一种都说明原因。
- 发布包变大，并承担随包分发的许可义务（MuPDF 为 AGPL，须带协议文本与源码清单）。
- 没有 root 的使用者也能装出完整的程序。
- 测试环境与使用者的环境一致：持续集成跑的是同一条构建命令。
- [安装指南](../../guides/installation.md)、运行清单（`release/manifests/runtime-support.json`）与 `doctor` 的检查项随实现更新。

## 考虑过但没有采用的方案

- **只改文档，把步骤写清楚。** 事故之前就是这样：步骤在安装指南里，使用者没有读到，上手指南还写错了。靠文档保证不了装全。
- **缺部件时照常启动，只给提示。** 使用者看到的仍然是一个能打开、能导入的程序，提示容易被忽略；这次的 323 篇就是在没有任何报错的情况下入库的。
- **只发布容器镜像。** 见“还没有决定的事”。
