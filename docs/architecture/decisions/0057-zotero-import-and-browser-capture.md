# ADR 0057：从 Zotero 导入，以及在浏览网页时收藏文献

类型：决策（ADR）
负责：从 Zotero 导入书目、分类、PDF、标签与批注；用户在自己的浏览器里浏览文献时一键收藏
状态：Accepted（2026-11-09，Owner 确认：“接受”）。部分被取代：第 1、2、6、7 节，第 3 节的“Zotero 编号”，以及“后果”中的建议顺序，见 [ADR 0058](0058-import-system-and-agent-access.md)；第 3 节“独立 PDF 不导入”、第 5 节“读不到标识就不保存”与由扩展解读页面标签，见 [ADR 0063](0063-unified-intake.md)

- Date: 2026-11-09
- 依据：Owner 2026-11-06 至 11-09 的要求，原话如下：

  > 现在咱们还有一个问题：就是用户如何导入他们的文献，我们最先要适配的就是zotero的导入工作。

  > 你问是不是在同一个电脑上，我觉得要考虑在与不在两种情况都要考虑

  > 我们肯定也要支持从zotero中导入pdf的。同时除了zotero之外我们还需要考虑如果让用户在自己浏览网页版的文献的时候，能够直接导入数据。就跟zotero的浏览器插件一样。

- 部分取代：
  - [ADR 0035](0035-authenticated-remote-web-access.md)“没有第二种认证模式”与“跨站请求拒绝”：浏览器扩展改用配对令牌，只能调用收藏接口（第 6 节）。
  - [ADR 0046](0046-reading-marks.md)“不在本决定内”中的“与 Zotero 等外部工具同步”：允许从 Zotero 单向导入批注（第 4 节）；同步仍不做。
- 与[产品需求](../requirements.md) R7 的修订同时生效：Zotero 导入不再只是书目交换；系统保存 Zotero 的库与条目编号，用于再次导入。
- Related：[ADR 0014](0014-capability-scoped-providers-and-local-credentials.md) 凭据；[ADR 0029](0029-unverified-pdf-acquisition.md) PDF 验收；[ADR 0032](0032-library-centered-web-workspace.md)、[ADR 0026](0026-agent-knowledge-and-human-collaboration.md) 不兼容 Zotero 插件；[ADR 0033](0033-machine-interfaces-cover-web-capabilities.md) 三端能力；[ADR 0052](0052-intake-batches-and-explicit-scope.md) 入库批次；[ADR 0056](0056-outbound-proxy-by-requester.md) 出网代理

## 背景

现在用户带着已有文献进来只有两条路：

- **导入书目**：导入 BibTeX/BibLaTeX、RIS、CSL JSON 文件。PDF、Zotero 分类和批注都带不进来。Zotero 导出 BibTeX/RIS 时会把它的标签写进关键词字段，导入后这些标签全部被当成了作者关键词。
- **上传 PDF**：一次只能传一篇，而且必须先选定一篇已在库的文献。

大多数用户的文献在 Zotero 里。Zotero 的数据分三部分：

- **条目**：书目字段，加上可嵌套的分类（一篇可以同时在多个分类里）、标签（手动或自动）和笔记。
- **附件**：附件文件可以存在 Zotero 的 `storage/<附件编号>/` 目录里，也可以只链接到别处的文件。一个条目可以挂多个 PDF。
- **批注**：PDF 上的批注作为附件的子项保存在 Zotero 数据库里，不写进 PDF 文件。

Zotero 对外有两个读取接口，返回的条目格式相同：

- **本地 API**：在 Zotero 7 设置里开启后，可以从本机读取 `localhost:23119/api/`。条目附件会给出本机文件路径。Zotero 不允许网页访问这个接口。
- **网络 API**：`api.zotero.org` 需要 API key。条目与批注只有用户开启了 Zotero 同步才有；附件文件只有存在 Zotero 官方存储的才能下载，用 WebDAV 同步的不能下载。

SciRetriever 的服务可能就在用户的电脑上，也可能在另一台服务器上，两种情况都要支持。

在浏览器里收藏文献时，用户用的是自己的网络和登录状态，常常能打开服务器打不开的全文。

## 决定

### 1. Zotero 导入：同机走本地 API，不同机走网络 API

| 情况                         | 读条目与批注                                                   | 取 PDF                                                                                    |
| ---------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 服务和 Zotero 在同一台电脑上 | 本地 API；Zotero 需保持打开，并开启本地 API                    | 按本地 API 给出的路径直接读文件，存储的和链接的附件都可以                                 |
| 不在同一台电脑上             | 网络 API；用户填只读 API key，可选个人库或有权访问的群组库     | 存在 Zotero 官方存储的，服务端下载；其余由用户在网页上选择 Zotero 的 `storage` 文件夹上传 |
| 都不可用时的兜底             | 上传 Zotero RDF 导出文件，书目、分类、标签都在；不含批注与编号 | 导出时勾选“导出文件”，连同文件夹一起上传                                                  |

- 两个 API 用同一套解析代码。书目字段尽量取 Zotero 自己转换出的 CSL JSON，经现有的 CSL JSON 导入规则落库，不另写一套类型映射。实现时要核实本地 API 也提供 CSL JSON。
- 不直接读 `zotero.sqlite`：Zotero 运行时会锁住这个文件，它的表结构也会随版本变化。
- 选择 `storage` 文件夹后，浏览器按 `storage/<附件编号>/` 把文件对应到附件，只上传库里还缺主 PDF 的那些。链接附件不在 `storage` 里，首版列入报告，入库后可以用“获取 PDF”补。
- 网络 API 是一个外部来源：
  - key 存进 `credentials.toml`；
  - 遵守 Zotero 的 `Backoff` 与 `Retry-After` 响应头；
  - 按 ADR 0056 在“文献来源”组里单独列一项，可以选择是否经代理。
- 本地 API 是本机服务，始终直连。

### 2. 导入分三步：选择、预览、导入

1. **选择**：选库，再从分类树里勾选要导入的分类（可选整库）。
2. **预览**：不写库，列出：
   - 新增多少篇、已在库多少篇、与已在库文献冲突多少篇；
   - 能带进来多少个 PDF，其中多少个要上传；
   - 多少条批注能导入、多少条不能导入及原因；
   - 不导入的内容：笔记、独立 PDF、非 PDF 附件。
3. **导入**：形成一个入库批次（ADR 0052 的新方式“Zotero 导入”），并作为后台任务执行，可以中断后继续。书目先入库，PDF 和批注随后补上。报告按第 2 步的分类写明实际结果。

CLI 与 MCP 提供同样的三步。同机时可以直接给出 `storage` 目录路径，代替网页上传。

### 3. 每类内容怎样落库

- **书目**：作为一条用户来源记录保存，与导入书目同等：优先于供应商来源，供应商只补缺失字段。再次导入时内容没变就记为 matched，不重复建来源记录。
- **身份**：先用 DOI、arXiv 号等标识匹配已有文献。Zotero 的 Extra 字段里的 DOI、arXiv、PMID 也要解析出来。没有标识的条目按现有书目导入规则处理。
- **Zotero 编号**：保存 Zotero 的库编号，以及条目、附件、批注的编号。再次导入同一个库时按编号对应，不靠标识去重，所以没有 DOI 的条目也不会重复入库。
- **分类**：导成文件夹，放在一个以库名命名的根文件夹下，保持原有层级；一篇在多个分类里，就进多个文件夹。再次导入只补新增，不删除用户在本系统里的整理。
- **标签**：
  - 自动标签多为出版社给的关键词，作为这条来源记录的作者关键词；
  - 手动标签是用户自己的分类，导成根文件夹下的“标签”子文件夹，预览里可以取消；
  - 建档时生成的受控词表标签不受影响。
- **PDF**：
  - 取 Zotero 指定的首选附件作为主 PDF；同一条目的其他 PDF（如补充材料）首版不导入，只计数。
  - 按 ADR 0029 验收：文件有效即可，标为“文章身份未验证”。
  - 文献已有主 PDF 时不替换。文件不同就记为冲突，在报告里列出。
- **批注**：只有当本系统的主 PDF 与 Zotero 批注所在的附件逐字节相同（sha256 一致）时才导入，否则锚点会错位。
  - 高亮、下划线导成高亮，保留原文；区域批注导成框选。
  - 坐标：Zotero 用 PDF 页面单位、原点在左下；导入时换成原点在左上，按页面尺寸换算。
  - 颜色：Zotero 的 8 种颜色就近归到本系统的 5 种。
  - Zotero 批注的评论导成该批注的笔记。超过 20,000 字符的不导入，在报告里列出。
  - 便签、文字框、手绘没有对应的种类，不导入，只计数。
- **不导入**（首版）：
  - Zotero 笔记：本系统没有整篇笔记；
  - 没有父条目的独立 PDF：缺书目无法入库，用户可以先在 Zotero 里用“获取 PDF 元数据”补出条目；
  - 网页快照等非 PDF 附件；
  - 相关条目关系、回收站里的条目。

### 4. 只从 Zotero 单向导入

- 不写回 Zotero，也不做双向同步。
- “再次导入”就是对同一个库重跑第 2 节的流程：已导入的按编号对应，书目有变化的形成新的来源记录，新增的条目补进来。在 Zotero 里删除的条目不会同步删除。
- 网络 API 有版本号，以后可以只取变化的条目；定时同步不在本决定内。

### 5. 浏览网页时收藏：自己的浏览器扩展

用户在出版社或预印本网站看到一篇文献，点扩展按钮就能收进文献库。

- **扩展只在用户点击时读当前页。** 先读页面里的标识与书目标签（`citation_*`、Dublin Core、`prism.*`，以及网址里的 DOI 或 arXiv 号），然后到服务端查询：
  - 已在库：显示状态，以及是否已有 PDF；
  - 不在库：显示读到的标题和作者，用户可以选择放进哪个文件夹，再点保存。
- **书目**：页面上读到的字段作为一条来源记录保存（来源名 `web-capture`），并照常用标识向元数据来源补全缺失字段。读不到 DOI 或 arXiv 号时，扩展请用户手动填写，否则不保存。
- **PDF**：扩展用用户自己浏览器的网络和登录状态下载 PDF，再把文件传给服务端。下载地址取页面的 `citation_pdf_url`；用户当前就在 PDF 页面时，用这个页面的地址。
  - Cookie 与登录信息不离开用户的浏览器。
  - 访问 PDF 所在网站的权限由扩展在第一次用到时逐站请求。
  - 文件验收、已有主 PDF 时的处理同第 3 节。
- **入库批次**：每台设备每天合成一个批次，例如“网页收藏 2026-11-09”，可以改名。
- **不复用 Zotero 的翻译器，也不兼容 Zotero Connector 协议**（与 ADR 0032 一致）。首版只用上面的通用页面标签；通用标签读不到书目的网站，以后再按站点补规则。
- **形态**：首版是 Chromium 系浏览器（Chrome、Edge）的扩展，代码放在仓库新的 `apps/` 子目录。服务端提供安装包，用户以开发者模式加载。上架商店和 Firefox 版另议。

在服务端运行的受控浏览器里浏览并收藏，已经可以通过现有的浏览器观看与介入做到，用的是服务器的网络出口。它不替代本节的扩展。

### 6. 扩展与服务端的连接：配对令牌

- 用户在设置页生成一次性配对码，再在扩展里填写服务地址和配对码。配对成功后，扩展得到一个长期令牌。
- 服务端只保存令牌的加盐派生值。设置页列出已配对的设备和最近使用时间，可以随时撤销。
- 令牌只能调用收藏用的接口：按标识查询文献状态、列出文件夹、保存书目、上传 PDF。它不能读取或修改其他数据，也不能登录 Web 工作台。
- 这些接口按令牌认证，不校验浏览器的 Origin；其他接口照 ADR 0035 不变。
- 与 ADR 0035 一样，HTTP 直连不加密传输内容。

### 7. 设置与界面

- 设置页新增“Zotero”分区，包含：
  - 本机 Zotero：地址，默认 `127.0.0.1:23119`，带“测试连接”；
  - 网络 API：用户编号与 key，带“测试连接”。
- 设置页新增“浏览器扩展”分区：下载安装包、生成配对码、已配对设备列表。
- 入库页新增“从 Zotero 导入”标签页，按第 2 节三步进行。入库记录里显示 Zotero 导入批次和网页收藏批次。

## 后果

- catalog 要升一版表结构，用来保存 Zotero 编号与本系统对象的对应关系，以及扩展的配对令牌。
- 需求 R7 要修订：Zotero 导入成为正式能力；系统需要长期保存外部工具的记录编号。
- 第 1 节的兜底和第 5 节的扩展各需要一个新的解析器或子项目，可以晚于 Zotero 的两个 API 交付。建议顺序：
  1. Zotero 本地 API 与网络 API：书目、分类、PDF；
  2. 浏览器扩展；
  3. 批注导入与 RDF 兜底。
- 用户自己提供的 PDF 来源变多了，“文章身份未验证”的文件也会变多。身份检验仍按 ADR 0029 留给解析阶段。
- 规格写进[文献与材料技术文档](../technical/03-literature-materials.md)、[页面规格](../web/page-specs.md)的入库与设置部分，以及[配置说明](../../guides/configuration.md)。
