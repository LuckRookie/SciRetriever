## 背景

“把文献放进文献库”现在有五个入口，各有各的规则：

| 入口                         | 接口             | 先预览   | 没有标识的条目   | 批次             |
| ---------------------------- | ---------------- | -------- | ---------------- | ---------------- |
| 网页“导入”：导出文件加文件夹 | 导入会话         | 有       | 接受             | 每次一个         |
| Agent 导入                   | 导入会话加 skill | 有       | 接受             | 每次一个         |
| 扩展收藏                     | 单独的收藏接口   | 没有     | 拒绝             | 每台设备每天一个 |
| 网页“上传 PDF”               | 单独的上传接口   | 没有     | 必须先有这篇文献 | 不形成批次       |
| 主题发现、引用扩展           | 发现任务         | 确认范围 | 不涉及           | 每次一个         |

另外：

- Zotero 的完整导入（分组、按条目同步、批注）只设计了“桌面上的 Agent 读 Zotero 接口”一条路，而且还没有实现。人只能先手工导出 BibTeX，分组、标签和批注都带不进来。
- 手里只有一个 PDF、库里还没有这篇文献时，没有办法把它放进来。
- 计划 20 的实现审查（2026-11-13）发现的五个较重的问题里，三个出在“Agent 加上传脚本搬运文件”这条路上。
- 导入之后没有下文：文件标为“文章身份未验证”就停在那里，与初稿（ADR 0060）和全文取得情况都没有接上。
- 一次入库不能撤回。

这些入口做的是同一件事。本决定把它们收成一套。

## 决定

### 1. 四个词

- **条目**：一篇要入库的资料。
- **来源**：条目原来所在的地方，例如一个 Zotero 库、一份导出文件、一个网页、本机的一个文件夹、一个文献信息来源。
- **载体**：把条目和文件送到文献库的程序。一共三种：扩展、网页、接口。
- **入库批次**：一次入库。它从开始送条目时就存在，结束时带着一份报告。界面上不再另有“导入会话”这个词。

### 2. 一种条目

- 一个条目可以带这些内容：
  - 书目，可以不完整；
  - 标识，例如 DOI、arXiv 号；
  - 文件，其中一个是全文；
  - 所属的分组，有层级；
  - 标签；
  - 批注；
  - 它在来源里的编号。
- **条目至少要有标识、标题、文件三者之一。** 所以有三种常见的形状：
  - 只有书目，例如一条没有附件的导出记录；
  - 书目加文件；
  - 只有文件，例如拖进来的一个 PDF。
- 只有文件的条目，由文献库认出它是哪一篇，办法见第 11 节。认不出的标为“书目待补”，照样入库。
- 没有标识的资料可以入库（需求收1“信息不完整的文献可以先进库”）。网页上读不到标识时，有标题就可以收藏。

### 3. 一个过程

所有载体送来的条目都走同一个过程，结果都是一个入库批次：

1. **交清单**：载体把来源的原始数据交来。只有文件的条目，文件本身就是原始数据，先放在暂存区。
2. **预览**：文献库解读数据并给出估计，不写库：
   - 新增、已在库、冲突、可能重复（第 8 节）、不接纳，各多少条；
   - 要补多少个文件；
   - 多少条批注能导入，多少条不能及原因；
   - 不导入的内容及数量。
3. **确认**：写库。确认立即返回，入库在后台进行，进度随时可读。确认时重新判定，以报告为准。
4. **补全文**：见第 4 节。
5. **报告**：按预览的分类写明实际结果，并写明这一批的全文取得情况。

- 批次的状态：收集中、待确认、入库中、完成、已取消、已撤回。
- **两种确认方式**：
  - 整批确认：默认。人在网页上确认；Agent 在用户说过可以直接导入时自己确认。
  - 逐条确认：条目交来就入库。只用于扩展的单篇收藏：使用者点“收藏”就是确认。这样的批次每台设备每天一个，当天保持开放。
- 扩展弹窗里的“已在库”和“不在库”，就是只有一条的清单的预览。
- 中断后继续、重复交同一份数据不重复入库、过期自动取消或结束，照 ADR 0058 第 4 节。

### 4. 全文从三处来，进同一条通道

- 条目的全文可以由载体送来，也可以由文献库自己获取。
  - **载体送来**：上传。文献库列出还缺哪些文件，载体照清单逐个交；已有主 PDF 的只核对，不替换。
  - **文献库获取**：现有的“获取 PDF”，范围就是这个批次。
- 两种方式进同一条文件通道，用同一套验收（ADR 0029），计入同一份全文取得情况。
- 文件上传不设大小上限，也不设时长上限。
- 为一篇已在库的文献补 PDF，同样走这条通道，原来 16 MiB 的上限取消。
- **入库之后接着做什么，写在批次页上**：对这一批获取全文、解析并形成初稿（ADR 0060）。这些操作会联网或花费，照需求规2 由使用者发起，入库本身不自动触发。

### 5. 来源只决定怎样读懂数据

- 每种原始格式一个适配器，放在服务端，把原始数据转成条目。适配器不联网、不写库（ADR 0058 第 3 节不变）。
- 载体不解读格式。扩展读到的网页书目标签原样交给服务端，由适配器解读。按站点补规则时只改服务端，使用者不必重装扩展。
- 首批适配器：
  - Zotero 接口的数据；
  - BibTeX、BibLaTeX、RIS、CSL JSON；
  - 网页的书目标签；
  - 文件本身。
- 以后按需要增加，只加适配器：EndNote、Zotero RDF、标识列表等。

### 6. 三种载体

| 载体 | 给谁         | 送什么                                            |
| ---- | ------------ | ------------------------------------------------- |
| 扩展 | 人，主要方式 | 正在看的网页；Zotero 里的库和分组，连同文件和批注 |
| 网页 | 人           | 本机的文件：PDF、文件夹、导出文件                 |
| 接口 | Agent 和脚本 | 任何条目                                          |

- **扩展**：
  - 收藏当前网页：一条条目，逐条确认。
  - 从 Zotero 导入：使用者在扩展里选库和分组，扩展读 Zotero 的本地接口，把数据交给文献库，然后打开网页上的这个批次。文件由扩展在后台上传，可以中断后继续。
  - **扩展只负责取，网页负责看和确认。** 除了单篇收藏的结果，扩展不显示预览、进度和报告。
  - 扩展怎样读到 Zotero 的文件，以计划 20 的探测为准：能直接读就直接读；不能时，请使用者选一次 Zotero 的数据文件夹。
- **网页**：入库页的一个放置区，接受 PDF、文件夹和导出文件，自动识别是什么。导出文件和同一次放进来的文件按导出里写的路径配对；单独的 PDF 是只有文件的条目。
- **接口**：一组 HTTP 接口。CLI 和 MCP 的书目导入是它的包装。skill 只讲怎样用这组接口。
- **人完成任何一种入库都不需要 Agent。** Agent 可以代使用者入库（需求收3），用的是同一组接口。
- 没有本地接口的文献管理工具（EndNote 等）走导出文件，由网页送来。
- 主题发现和引用扩展也是入库：来源是文献信息来源，载体是文献库自己。它们的做法不变，只在入库页、批次和报告的用语上与本决定一致。

### 7. 一个接口，一种用途

- 入库只有一组接口。单独的收藏接口不再存在。
- 设备连接的用途里，“收藏”和“导入”合成“入库”。“读取”“操作”不变。
- 凭令牌只能看到和操作本设备发起的批次。网页登录的使用者能看到和操作全部批次。
- 接口的路径与字段归技术文档。

### 8. 再次入库与重复

- 来源有自己的库编号时，按条目在来源里的编号对应（ADR 0058 第 5 节不变）。经扩展从 Zotero 导入总是带库编号，所以再导一次就是同步。
- 来源没有库编号时（导出文件、单独的文件、网页）：
  - 有标识的，按标识对应。
  - 文件按内容的 sha256 对应：同一个文件不重复入库。
  - **没有标识的，按标题、第一作者和年份判断是否可能与已在库的文献重复。** 可能重复的不自动合并，也不自动新增：预览里单独列出，由使用者逐条决定并入已有的还是新增。没有人决定时不入库，写进报告，以后可以在批次页上处理。

### 9. 撤回

- 一个批次可以撤回。撤回移除这一批新增的、之后没有被动过的内容：文献、文件、分组、批注。
- 下列内容不移除，在撤回的报告里列出：
  - 入库之前已经在库的；
  - 之后被其他批次命中的；
  - 之后被使用者整理、批注或加工过的。
- 撤回之前写明将移除多少、保留多少。撤回只能由网页登录的使用者发起，凭令牌不能撤回。
- 撤回之后，这些文献不再出现在文献库、查询和加工的范围里。具体做法归技术文档。

### 10. 入库页

- 入库页按“文献从哪里来”排列：
  - **从检索**：主题发现、引用扩展；
  - **从文件**：放置区；
  - **从 Zotero**：需要扩展；没有连接扩展时，写明怎样安装和连接；
  - **从网页**：说明在文献页面上点扩展。
- 下面是入库记录：全部批次，一种行，不论由谁发起。原来的“导入会话”列表并入其中，“上传 PDF”标签页并入“从文件”。
- 每个批次一页：预览、确认、进度、报告、接着做什么、撤回。
- 扩展的弹窗有两项：收藏这一页，从 Zotero 导入。

### 11. 认出是哪一篇，再补全书目

条目带来的书目不完整时，文献库分两步补：先认出它是哪一篇，再向文献信息来源取书目。条目自己带来的内容是线索，用来认出它；完整的书目取自文献信息来源。

- **线索因载体而异，认的办法只有一套，放在服务端。**
  - 文件：文件自带的信息（标题、DOI）、文件名、首页的文字。
  - 网页：页面里的书目标签（`citation_*`、Dublin Core、PRISM、schema.org 的结构化数据）、网址里的 DOI 或 arXiv 号、页面的标题。
  - 使用者正在看的页面本身就是 PDF 时，扩展把文件交来，按文件处理。
- **按下面的顺序认，前一步成功就不做后一步：**
  1. **找标识。** 取线索里的 DOI 或 arXiv 号。文件只看文件信息、文件名和首页；首页上有几个不同的标识时不取，因为分不清哪个是它自己的。
  2. **用标识取书目，并核对。** 取回的标题要能在线索里找到（文件的首页文字，或页面的标题）。对不上的，当作没有标识。
  3. **用标题找。** 没有标识时，取线索里的标题：网页用标题标签，文件用首页最醒目的一行。向文献信息来源按标题查。标题一致，并且作者或年份也能在线索里找到的，才采纳。只是标题相近的，作为“可能是这一篇”列在预览里，由使用者选。
  4. **没有认出。** 以线索里的标题入库，没有标题时用文件名，标为“书目待补”。
- **什么时候认：**
  - 网页带着书目标签，本身就有书目，收藏时不必等查询；补全照现在的做法，保存之后进行。
  - 只有文件的条目在预览阶段认，显示进度。这是使用者发起的入库的一部分；预览仍然不写库。
- **“书目待补”以后怎样补：**
  - 使用者自己填；
  - 这篇文献解析之后，用解析出的标题和作者再认一次，不另外花费；
  - 由知识加工读出书目，不在本决定内。
- 这一节只用程序和文献信息来源，不调用模型。
- 认出来的结果只决定书目。文件仍照 ADR 0029 标为“文章身份未验证”，解析时的身份核验不变。
- 网页读到的字段照 ADR 0057 第 5 节保存为一条来源记录；文献信息来源只补它没有的字段。
- 首版不做：按站点写的读取规则、在检索结果页上一次收多篇、按 ISBN 查图书。页面没有书目标签时，按上面第 3、4 步处理。

## 还没有验证的前提

- 扩展能读 Zotero 的本地接口，并能读到文件。计划 20 的探测扩展已交给 Owner，结果还没有回来。
- 第 11 节的办法在真实文件上能认出多少：有多少 PDF 的首页读得到标识，核对标题能否挡住被引文献的标识，按标题查会认错多少。没有 DOI 的文献（例如许多中文期刊论文）和扫描件预计认不出。
- “可能重复”的判断会误报多少、漏报多少。
- 存储能否干净地撤回一批内容。
- 扩展在后台连续上传几千个文件是否稳定。

每一项在重排后的计划里各有一道验证，验证不通过时回到本决定修改。

## 后果

- 计划 20 按本决定重排。已有实现的去留：
  - 留下：导入会话的状态机与暂存、设备连接、文件通道、外部编号对应、书目格式的适配器、扩展的外壳与连接；
  - 要改：收藏接口并入、页面书目标签的解读移到服务端、确认改为后台进行、批次的归属、入库页；
  - 要新做：扩展的 Zotero 导入、只有文件的条目、可能重复的判断、撤回；
  - 不再是主路：skill 里的上传脚本。它作为 Agent 的可选辅助是留是去，在计划里定。
- 实现审查发现的缺陷里，上传被 5 秒请求超时掐断这一条与本决定无关，必须先修。
- 需求收3 在接受时补三句：手里的文件可以直接入库，不要求先有书目；人不借助 Agent 就能完成导入；一次带入可以撤回。
- 规格写进[文献与材料技术文档](../technical/03-literature-materials.md)、[产品接口技术文档](../technical/01-product-interface.md)、[页面规格](../web/page-specs.md)的入库、设置与扩展弹窗部分。
- HTTP 版 MCP：Owner 2026-11-14 交由总设计师处置（“如果有用就留着，没用就改造或者弃用都可以”）。总设计师决定保留：实现审查没有发现问题，它让桌面上的 Agent 不装任何东西就能查文献、读全文。它随入库一起上线；“操作”用途照 ADR 0058 不默认勾选。Agent 的授权怎样设计，留到考虑知识加工时一并审视。
- 不在本决定内：Agent 的授权；扩展用使用者的浏览器成批下载全文；定时同步；写回外部工具；Firefox 版扩展。

## 考虑过但没有采用的方案

| 方案                                   | 没有采用的原因                                                                                |
| -------------------------------------- | --------------------------------------------------------------------------------------------- |
| 维持现状，逐个修缺陷                   | 五个入口各有规则的局面不变；人仍然没有完整的 Zotero 导入                                      |
| 以桌面上的 Agent 作为人的导入方式      | 搬运是确定的活，不该由模型临场完成；试跑和审查发现的问题多出在这条路上；没有 Agent 的人用不了 |
| 在 Zotero 里装一个本项目的插件         | 每种文献管理工具都要各写一个，并跟随它们的版本维护；扩展已经在使用者的电脑上，一个就够        |
| 另做一个桌面小程序负责搬运             | 使用者要多装一样东西；它能做的，扩展和网页都能做                                              |
| 只有文件的条目由载体先读出标识再交清单 | 每种载体都要各自实现一遍读取，结果会不一致；文件迟早要上传，先交来由服务端统一读更简单        |
| 没有标识的可能重复条目自动新增         | 重复的文献会污染文献库，事后难以清理；不入库的条目还在报告里，可以随时补进来                  |
