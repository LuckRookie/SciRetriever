# ADR 0065：文献库按千万篇设计，耗时不随总篇数增长

类型：决策（ADR）

## 背景

2026-11-21 的正式库有 18.8 万篇，其中 929 篇有 PDF；catalog 4.8 GB，约每篇 25 KB。一个引用扩展任务同时以每秒约 2.7 篇写入。此时全库计数约 7 s，运行中任务的详情约 19 s，搜索索引每次刷新约 11 s 且一直追不上写入，Web 上的其他请求排在这些请求后面。

这些耗时都来自同一类做法：每次操作都要扫过全库、整个结果集或整个任务，或者把全库的数据放进内存。万篇时看不出来（计划 25 的万篇检查中三次读取为 373 / 155 / 119 ms），到二十万篇加上持续写入就卡了，到百万、千万篇会完全不可用。只把当前的数字压下去，下一个数量级又会出现同样的问题。

## 决定

### 1. 设计规模

- 书目按一千万篇设计；有全文的文献按一百万篇设计。
- 常规性能检查在一百万篇书目（其中十万篇有全文）的合成库上运行；压力检查在一千万篇书目（其中一百万篇有全文）上运行，在大改动和收尾时进行。
- 当前的库有多大，不作为任何设计的依据。

### 2. 人与 Agent 的分工

- 千万篇的量由 Agent、命令行与批量任务处理：它们按条件取出待处理的一批，逐篇读取、写入，从断点续跑。这条路径按第 1 节的规模设计。
- 人的界面只面对有边界的**工作集**：一次搜索的结果、一个集合、一个任务的产出、最近读过的、待审核的一批，以及“收进来的文献”。面对全库时，界面只提供搜索、写入时维护的几项总数和进入各个工作集的入口，不提供全库的浏览列表。
- **收进来的文献**与**只被发现的文献**：文献仍然存在同一个库里，去重、引用关系与补全照旧（[ADR 0013](0013-decoupled-discovery-and-database-maintenance.md)、[ADR 0064](0064-citation-expansion-bounded-by-depth.md)）。人或 Agent 对一篇文献做过明确的选用（导入、浏览时收藏、加标签、放进集合、打开阅读、提供或要求全文、发起加工），它就是收进来的文献；只经由发现进入、尚未被选用的，是只被发现的文献。这个区分在写入时维护；人的文献列表默认只显示收进来的文献，只被发现的文献通过搜索、任务的产出和引用关系找到。

### 3. 规模规则

以下 N 指库的总篇数。

1. **单篇、任务与工作集内的操作只与本次的量有关。** 打开一篇、查看任务、搜索，以及在工作集里浏览、筛选、计数、翻页，耗时只取决于本次要显示的量、工作集的大小或自上次以来的变化量；与 N 的关系不超过对数级（例如一次索引查找）。
2. **常驻内存不随 N 增长。** 服务进程不把全库的数据或其投影放在内存里；缓存要有与 N 无关的上限。
3. **后台维护与变化量成正比。** 状态、计数器、搜索索引等派生数据在写入时或按写入时记下的变更维护。全库扫描只作为显式的维护操作（例如重建、校验），它可以中断、可以继续，不挡前台请求。
4. **代价与结果数成正比的准确数，可以截断，但必须如实。** 超过一万篇的工作集或搜索结果，其总数、分面和相关度排序可以只算到一个上限，或在后台补算；界面写明是截断的数，不把它当准确数。上限按扫描的命中数算，不按结果数算：筛选再严，一次请求扫过的命中也不超过上限。
5. **结构变化不停服。** schema 变化只加表、加列、加索引，数据在后台按批回填，回填期间旧路径照常工作；不能这样做的变化登记为例外，写明停服时间的估计，并经 Owner 同意。
6. **长任务的进度在库里。** 运行时间长、规模大的任务（例如多层引用扩展）把待处理的队列与已完成的记录存在库里，中断后从断点继续，内存不随任务规模增长。

### 4. 检验

- 每条规则都由测试证明，而不只靠审查：同一操作在一万篇与一百万篇的合成库上耗时相近；边写边读时短请求仍达到目标耗时；进程内存在两种规模下相近。
- 各操作的目标耗时写在[查询技术篇 2.4](../technical/06-retrieval-context.md#24-规模与目标耗时)与[阅读体验](../web/reading-experience.md)的验收表中，本 ADR 不写具体数字。
- 违反规则的现有做法是缺陷，在计划 26 中逐项处理；新的违反在审查与性能检查中拦下。

### 5. 存储

- 继续使用 SQLite。它可以容纳千万行与数百 GB；已查明的卡顿都来自读写方式，而不是 SQLite 本身。
- 数据访问保持在现有的存储接口之后，不让上层直接依赖 SQLite 的特有行为，以便将来更换。
- 出现下列任一情况时重新评估：每篇所占空间降不下来，使一千万篇的库大到备份与迁移不可接受；SQLite 只允许一个写入者，使入库吞吐达不到目标。

### 6. 各处的做法

以下按第 2、3 节定下现有各处的做法（Owner 2026-11-21：“照建议定”）。

1. **文献状态**：写入文献时在同一事务里维护它的状态与“是否收进来”，存在库里并建索引，供 Agent 按状态取出待处理的一批，也供人的列表默认只显示收进来的文献；进程内不再保留整库的状态。影响状态推算的设置（标签上限、建档方式）改变时，状态在后台按批重算，界面显示“正在更新”。
2. **计数、分面与列表总数**：
   - 全库的几项总数（全部、收进来的、只被发现的、有 PDF、各状态）由写入时维护的计数器给出，准确且立即可得。
   - 工作集与搜索结果不超过 10,000 篇、且扫描已完成时，计数与分面照常准确计算；超过时最多数到 10,000，显示“1 万以上”，并提供“算出准确数”，在后台计算，完成后补上。
   - 列表翻页不再每页重算总数。
3. **翻页与排序**：工作集不超过 10,000 篇时，所有排序与筛选照常提供。超过时只提供有索引支撑、按游标翻页的排序：入库时间（收进来的文献按收进来的时间），最近读过的按打开时间，搜索结果按相关度；其他排序提示先缩小范围。不为全库建标题、出版年等排序索引。
4. **搜索**：写入时把变更记进库里，索引刷新只处理这些变更。按相关度排序时只对最新的一批命中打分，这批的条数有与 N 无关的上限，从中取前 1,000 条。命中不超过这个上限时结果是精确的；超过时回执与界面写明“在最近写入索引的若干条命中里按相关度显示前 1,000 条”。任何查询的耗时都不随命中数无限增长。
   - **窗口**：在整个文献库里搜索时，窗口按筛选之前的原始命中划定，即最近写入索引的 C 条命中；筛选、计数、分面与排序都在同一个窗口里做。
   - **工作集**：成员不超过 10,000 篇的工作集里搜索，符合的文献、计数与分面是精确的：从命中一侧或成员一侧中估算成本较低的一侧扫完。相关度排序在预算内能排完时覆盖全部结果；排不完时只对其中一部分（按工作集的顺序取）打分，其余按工作集的顺序接在后面，回执与界面写明，其他排序照常提供。预算按索引里记下的文档长度估算，不读正文；idf 被钳到下限的词不计词频，结果与原生 `bm25()` 一致。超过 10,000 篇的工作集（包括大的“收进来的文献”与批次）与整个文献库一样分窗，窗口开在估算成本较低的一侧：按原始命中，或按成员收进来的时间（最近收进的若干篇）。按成员分窗时，按收进时间排序是准确结果的前缀，可与相关度一起提供。续查游标记下所走的一侧，两次请求之间范围变化也不换边。
   - **如实**：窗口外还有命中时，计数写“至少 n 条”，没有结果时写“这 C 条命中里没有，更早的还没查”；回执带机器可读的“扫描未完”标志，Agent 不得把窗口内的零当成全库的零。
   - **续查**：“在更早的命中里继续找”按下一个窗口再查一次，仍是有界的短请求，人与 Agent 共用。扫描未完时只提供相关度排序，其他排序提示先缩小范围。需要穷尽处理的 Agent 按状态分批取，相关度搜索不保证穷尽。
5. **读请求**：短请求（翻页、打开一篇、读 PDF、状态）与长请求（统计、导出、批量）分道执行，长请求不挡短请求。短请求超过 5 s 记为缺陷。长请求分段执行，不长时间持有读事务，使 WAL 能够收缩；承诺同一快照的长请求（导出、显式校验）可以在长请求的道上持有一个读事务直到结束。
6. **打开 PDF**：按段下载，第一页先显示；完整的 SHA-256 校验在后台进行，校验不通过时页面换成“文件与记录不一致”并停止显示。PDF 字节按内容地址使用浏览器缓存。
7. **入库吞吐**：本机处理每秒至少 100 篇书目（一千万篇约 28 小时）。按批写入，每批数百篇一个事务；身份匹配使用索引查找。
8. **迁移**：按第 3 节第 5 条只加表、加列、加索引，后台回填。变更记录由库里的触发器写入，任何写入者（包括旧版本的进程）的写入都被记下；旧版本打开带有新增表的库时照常工作，不因此拒绝打开。
9. **引用扩展的进度**：每查完一篇文献，在写入其结果的同一事务里记下“已查”并更新待查队列；中断后最多重查一篇。运行一开始就登记为进行中，结果随每一段写入，结束时只改运行的状态，不在最后一次写入全部结果。
10. **来源冷却**：来源给出 `Retry-After` 时按它等待；没有时依次等待 1、5、15、60 分钟，最多重试 6 次；之后在本任务内停用该来源，并在任务详情里写明。冷却期间其他来源照常进行；冷却状态与第 9 条的进度一起保存。
11. **任务详情**：任务的合计与重放到的位置存成 home 下可删、可重建的旁路文件，并核对任务、库与 schema 的身份；进程重启后首读加载它，只读之后新增的记录。文件缺失或核对不通过时整读一次重建，不影响正确性。合计不在写入任务事件的事务里维护。
12. **写入让行**：
    - 写许可在进程之间排队，等待者对持有者可见，CLI、服务与后台回填共用同一个机制。
    - 持有者每写完一段检查是否有等待者，有就让出，单段持有写许可的时间有上限。
    - 前台持续写入时，后台回填仍保有至少五分之一的写入时间，不会无限期推迟。

## 后果

- 文献库首页从全库列表改为工作集的入口；页面规格要改写，先出设计稿。
- 计数、分面、列表总数与相关度排序在超过一万篇的工作集上可能显示截断的数；页面规格与查询合同要写明口径。
- 文献状态、“是否收进来”、计数器与搜索索引的变更记录要存进库里，需要加表加列；第一次按第 3 节第 5 条的方式上线前，可能仍有一次停服迁移。
- 需要一个合成库生成器，直接生成百万、千万篇的数据；性能检查的运行时间与磁盘占用会明显增加，压力检查不在每次改动时运行。
- [需求](../requirements.md)的收4 随本决定改写（2026-11-21）。
