# ADR 0065：文献库按千万篇设计，耗时不随总篇数增长

类型：决策（ADR）
负责：文献库的设计规模；所有读写路径必须遵守的规模规则及其检验办法；存储的选择与重新评估的条件；现有各处（状态、计数、排序、搜索、读请求、PDF、入库、迁移、引用扩展进度、来源冷却）按规则的做法
状态：Proposed（2026-11-21，Owner 已同意规模目标、规则、存储与第 5 节各处做法的建议，待审定本文）

- Date: 2026-11-21

  > 立意的时候不要只想着20w，之后我们会有更多的数据呢？别忘了我们数据库是要为了大批量的文献数据所设计的，以后说不定会有很多，百万千万都不一定。所以这部分的优化一定要设计好。

## 背景

2026-11-21 的正式库有 18.8 万篇，其中 929 篇有 PDF；catalog 4.8 GB，约每篇 25 KB。一个引用扩展任务同时以每秒约 2.7 篇写入。此时全库计数约 7 s，运行中任务的详情约 19 s，搜索索引每次刷新约 11 s 且一直追不上写入，Web 上的其他请求排在这些请求后面。

这些耗时都来自同一类做法：每次操作都要扫过全库、整个结果集或整个任务，或者把全库的数据放进内存。万篇时看不出来（计划 25 的万篇检查中三次读取为 373 / 155 / 119 ms），到二十万篇加上持续写入就卡了，到百万、千万篇会完全不可用。只把当前的数字压下去，下一个数量级又会出现同样的问题。

## 决定

### 1. 设计规模

- 书目按一千万篇设计；有全文的文献按一百万篇设计。
- 常规性能检查在一百万篇书目（其中十万篇有全文）的合成库上运行；压力检查在一千万篇书目（其中一百万篇有全文）上运行，在大改动和收尾时进行。
- 当前的库有多大，不作为任何设计的依据。

### 2. 规模规则

以下 N 指库的总篇数。

1. **交互操作只与本次的量有关。** 浏览、筛选、计数、搜索、打开一篇、查看任务等交互操作，耗时只取决于本次要显示的量或自上次以来的变化量；与 N 的关系不超过对数级（例如一次索引查找）。
2. **常驻内存不随 N 增长。** 服务进程不把全库的数据或其投影放在内存里；缓存要有与 N 无关的上限。
3. **后台维护与变化量成正比。** 状态、计数器、搜索索引等派生数据在写入时或按写入时记下的变更维护。全库扫描只作为显式的维护操作（例如重建、校验），它可以中断、可以继续，不挡前台请求。
4. **代价与结果数成正比的准确数，可以截断，但必须如实。** 任意筛选或搜索下的总数、分面和相关度排序，在结果很多时可以只算到一个上限，或在后台补算；界面写明是截断的数，不把它当准确数。
5. **结构变化不停服。** schema 变化只加表、加列、加索引，数据在后台按批回填，回填期间旧路径照常工作；不能这样做的变化登记为例外，写明停服时间的估计，并经 Owner 同意。
6. **长任务的进度在库里。** 运行时间长、规模大的任务（例如多层引用扩展）把待处理的队列与已完成的记录存在库里，中断后从断点继续，内存不随任务规模增长。

### 3. 检验

- 每条规则都由测试证明，而不只靠审查：同一操作在一万篇与一百万篇的合成库上耗时相近；边写边读时短请求仍达到目标耗时；进程内存在两种规模下相近。
- 各操作的目标耗时写在[查询技术篇 2.4](../technical/06-retrieval-context.md#24-规模与目标耗时)与[阅读体验](../web/reading-experience.md)的验收表中，本 ADR 不写具体数字。
- 违反规则的现有做法是缺陷，在计划 26 中逐项处理；新的违反在审查与性能检查中拦下。

### 4. 存储

- 继续使用 SQLite。它可以容纳千万行与数百 GB；已查明的卡顿都来自读写方式，而不是 SQLite 本身。
- 数据访问保持在现有的存储接口之后，不让上层直接依赖 SQLite 的特有行为，以便将来更换。
- 出现下列任一情况时重新评估：每篇所占空间降不下来，使一千万篇的库大到备份与迁移不可接受；SQLite 只允许一个写入者，使入库吞吐达不到目标。

### 5. 各处的做法

以下按第 2 节的规则定下现有各处的做法（Owner 2026-11-21：“照建议定”）。

1. **文献状态**：写入文献时在同一事务里维护它的状态，存在库里并建索引；进程内不再保留整库的状态。影响状态推算的设置（标签上限、建档方式）改变时，状态在后台按批重算，界面显示“正在更新”。
2. **计数、分面与列表总数**：
   - 全库与快捷筛选（各状态、有 PDF、最近打开）的计数由写入时维护的计数器给出，准确且立即可得。
   - 任意筛选或搜索下的计数与分面最多数到 10,000；超过时显示“1 万以上”，并提供“算出准确数”，在后台计算，完成后补上。
   - 列表翻页不再每页重算总数。
3. **翻页与排序**：入库时间、最近打开、出版年、标题、相关度五种排序都有索引支撑，按游标翻到任何一页的耗时都与总篇数无关；标题排序使用存储的规范化标题。其他排序（例如按全文指标）只在结果不超过 10,000 条时提供，超过时界面提示先缩小范围。
4. **搜索**：写入时把变更记进库里，索引刷新只处理这些变更。按相关度排序时只取前 1,000 条，界面写明“按相关度显示前 1,000 条”。
5. **读请求**：短请求（翻页、打开一篇、读 PDF、状态）与长请求（统计、导出、批量）分道执行，长请求不挡短请求。短请求超过 5 s 记为缺陷。长请求分段执行，不长时间持有读事务，使 WAL 能够收缩。
6. **打开 PDF**：按段下载，第一页先显示；完整的 SHA-256 校验在后台进行，校验不通过时页面换成“文件与记录不一致”并停止显示。PDF 字节按内容地址使用浏览器缓存。
7. **入库吞吐**：本机处理每秒至少 100 篇书目（一千万篇约 28 小时）。按批写入，每批数百篇一个事务；身份匹配使用索引查找。
8. **迁移**：按第 2 节第 5 条只加表、加列、加索引，后台回填。变更记录由库里的触发器写入，任何写入者（包括旧版本的进程）的写入都被记下；旧版本打开带有新增表的库时照常工作，不因此拒绝打开。
9. **引用扩展的进度**：每查完一篇文献，在写入其结果的同一事务里记下“已查”并更新待查队列；中断后最多重查一篇。
10. **来源冷却**：来源给出 `Retry-After` 时按它等待；没有时依次等待 1、5、15、60 分钟，最多重试 6 次；之后在本任务内停用该来源，并在任务详情里写明。冷却期间其他来源照常进行；冷却状态与第 9 条的进度一起保存。

## 后果

- 计数、分面、列表总数与相关度排序在结果很多时可能显示截断的数；页面规格与查询合同要写明口径。
- 文献状态、计数器与搜索索引的变更记录要存进库里，需要加表加列；第一次按第 2 节第 5 条的方式上线前，可能仍有一次停服迁移。
- 需要一个合成库生成器，直接生成百万、千万篇的数据；性能检查的运行时间与磁盘占用会明显增加，压力检查不在每次改动时运行。
- [需求](../requirements.md)的收4 随本决定改写（2026-11-21）。
