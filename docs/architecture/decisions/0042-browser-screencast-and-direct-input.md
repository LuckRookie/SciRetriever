# ADR 0042：浏览器观看改用页面投屏，取得控制权后直接输入

类型：决策（ADR）

## 背景

现行观看画面就是 Agent 每次观察时截的那张 JPEG：

- Agent 推理、等待、下载期间，服务端不刷新画面；
- 一次完整观察约 0.25 秒，另有 750 ms 的刷新间隔；
- 前端收到新观察后，再单独拉一次图。

人点击画面时，要先接管，再按观察 revision 校验，页面一变就拒绝；执行之后还要整页重新观察，才出新图。实际表现是：画面滞后，点击常被拒绝，只支持点击、滚动和三个按键。迁移方案（`docs/archive/2026-09-07-typescript-browser-workbench-reference/`）原本选的是投屏加 WebSocket，落地时退化成了观察截图。

2026-10-27 在 sandbox 用 CloakBrowser（按产品参数启动）和合成测试页做了实测，报告在本机 `sandbox/reports/2026-10-27-browser-screencast*/`：

- **本机回环**：每秒 60 帧，画面延迟中位 30 ms，点击到看见反应 58 ms。
- **Owner 实际网络**：经端口转发，往返 4.5 ms。约每秒 20 帧，画面延迟中位 108 ms，点击 160 ms，滚轮、键入、拖动在 150–190 ms 之间。
- **隔帧推送**（`everyNthFrame` 为 2）：会丢掉单次变化，静止页点击后最长 4 秒看不到反应。
- **对 Agent 的影响**：投屏不拖慢 Agent 的观察与点击。最后一个观看者离开后，约 24 ms 停止编码。
- **刷新与新标签页**：刷新和页内跳转时投屏不断；新标签页要重新订阅。
- **密码遮挡**：现行截图的遮挡方式是临时往页面里插入覆盖层，会在投屏里间歇闪现，1430 帧中有 470 帧可见。

## 决定

### 1. 观看与 Agent 观察分开

- 人看到的画面来自 Chromium 页面投屏，每一帧都推，不隔帧。
- Agent 的观察照旧，在自己的决策点截图、读页面；投屏不进入模型输入。
- 两者不再共用同一张图。

### 2. 投屏的传输

- 投屏帧逐帧确认。转发端只保留最新一张待发帧，慢网时丢弃旧帧，不排队。
- 帧只经已认证的观看连接发送，不落盘，不做录像或回放；ADR 0026 关于长期截图与录像的未决项不变。
- 有人观看时才开投屏，最后一个观看者离开即停止编码。
- Agent 切换到新标签页或弹窗时，在新页上重新订阅。
- 分辨率、画质、在途帧数和慢网时怎样自适应，属于实现参数，由技术文档维护。

### 3. 取得控制权与直接输入

1. **第一次操作**：人在画面上第一次按下鼠标或按键，即申请控制权并暂停 Agent。
   - 申请照旧经服务端，验证任务、文章、会话与控制 epoch。
   - 这次输入带上它所在投屏帧的文档身份。服务端只核对这个文档身份：没有换成别的文档时，派发这次输入；已经换了，则不派发，画面照常更新。
   - 不再按观察 revision 校验，因为观察 revision 随 Agent 的每次观察变化，与人看到的画面并不对应。
2. **取得控制权后**：鼠标移动、按下与抬起、拖动、滚轮、键盘与文本插入（输入法）都直接转发给页面，坐标按当前投屏帧换算，不再逐次校验。
3. **交还以后**：交还后 Agent 重新观察，不继续旧的缓存动作；ADR 0032 第 5 节第 3 条不变。

### 4. 敏感输入

- 投屏画面与真实页面一致，不另做遮挡：观看者就是正在操作的人本人，密码框在页面上本来也只显示圆点。
- Agent 的观察截图仍按 ADR 0030 遮挡敏感输入，但改为截好后在图上涂抹，不再改动页面 DOM，以免遮挡层出现在投屏里。

## 未采用的方案

| 方案                               | 原因                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 保留观察截图，只缩短刷新间隔       | Agent 推理期间仍然没有画面；每次截图连带整页观察，约 0.25 秒，帧率上不去                                |
| 投屏隔帧推送以省带宽               | 实测会丢掉单次变化，点击后长时间看不到反应                                                              |
| 每次人工输入都按观察 revision 校验 | 观察 revision 与人看到的画面不对应，正常操作也会被拒绝，这正是“点不上”的原因；取得控制权后 Agent 已暂停 |
| 投屏帧里也遮挡密码框               | 观看者就是控制者本人；要遮挡，就得对每帧做页面检测，或往 DOM 插覆盖层，后者已证明会闪现                 |

## 后果

- 观看画面持续更新；点击、拖动、键盘输入直接生效。
- 现有的 `/api/frame` 拉图与 750 ms 刷新由投屏取代后删除，不保留两套。
- 成本：有动画的页面，投屏编码在软件渲染下约多占 2.4 个 CPU 核；没人观看时不产生成本。
- 残余风险如实承认：
  - 控制期间，人的输入不再逐次校验；页面在两次输入之间变化时，后一次输入按人看到的最新画面作用；
  - 慢网下只能靠降分辨率和画质保持响应，2 Mbps 级别的网络仍会明显滞后；
  - 实测只覆盖合成测试页与一条真实网络，出版社页面在实施验收中验证。
- 实现规则归 [Browser 控制](../technical/08-browser-control.md)；实施与验收见计划 17 的 04 块。
