# SciRetriever 产品需求

- 文档效力：产品需求真相源
- Owner 确认：2026-08-10
- 产品设计：[设计文档](design.md)
- 当前实现：项目 [README](../../README.md)、源码与测试

本文只说明 SciRetriever 要解决的问题、用户工作流、产品结果和验收标准。数据模型、模块划分、算法、供应商协议、存储方式和运行机制属于设计，不在本文规定。

## 1. 产品目标

SciRetriever 要解决的是**面向指定领域的大批量文献收集问题**。

研究者通常需要从多个文献来源反复检索、下载和整理大量文献。不同来源覆盖范围不同，返回的元数据可能重复或不完整，全文获取方式也不一致。手工完成这些工作成本高、难以重复，并且很难持续维护已经收集的结果。

SciRetriever 接收用户给出的领域条件或种子文献，通过主题检索或引用关系迭代收集文献，完成多来源元数据汇总、文献下载、内容解析和语言模型总结，最终形成一个可以持续积累、查询并与主流文献管理工具交换数据的文献数据库。

这套文献数据库本身就是持续维护的产品结果，不是一次运行结束后附带留下的副产品。每次收集、处理、查询或交换都必须以用户当前意图和数据库中已经存在的结果为基础；需要改变数据库的操作复用有效内容、补充仍然缺失的内容，并把新确认的信息继续纳入同一数据库。

## 2. 用户与使用场景

主要用户是需要建立专题文献数据库的研究者或文献整理人员。典型场景包括：

- 为一个研究方向批量收集相关文献；
- 从一批种子文献出发，沿引用关系继续发现相关文献；
- 定期补充某个领域新发表的文献；
- 从多个来源提高文献覆盖率；
- 批量获得文献全文和可直接阅读、导出及程序处理的轻结构化文档；
- 在文献数据库中查询、检查和继续处理已经收集的文献；
- 在文献数据库与 Zotero 等主流文献管理工具之间导入和导出书目信息。

## 3. 用户输入与产品输出

### 3.1 用户输入

用户可以通过两种方式发起文献收集：

1. 指定一次领域发现所针对的条件，例如主题描述、关键词、时间范围、文献类型或其它文献筛选条件；
2. 指定一篇或一组种子文献，并要求系统通过文献之间的引用关系迭代发现更多相关文献。

需求只规定用户能够表达目标领域或引用扩展目标，不规定具体查询语法、迭代方式或供应商能力。

### 3.2 产品输出

产品输出是一个文献数据库。数据库至少能够关联保存以下四类信息：

1. **文献元数据**：用于识别、描述和检索文献的信息；通过文献来源检索获得的信息还包括提供它的来源；
2. **文献资产**：已获得的全文或相关文件，以及资产类型、来源和可用性信息；
3. **轻结构化文档**：由语言模型根据文献资产的中间解析内容总结形成、具有固定最小结构并允许补充其它章节的 Markdown 文档；同一内容还以有序结构化章节保存，供程序读取，并能够追溯到原始资产；
4. **文献关联信息**：文献由哪次有边界的外部发现、哪些条件或引用关系获得，以及已经确认的文献引用关系。

数据库是持续积累的产品结果，不是一次运行后即丢弃的临时结果集合。所有已经接纳并需要长期保留的收集和处理结果都必须能够在这套数据库中共同查询和继续补充，不能因输入方式或处理工具不同而形成彼此隔离的结果。用户还必须能够通过主流文献交换格式导入和导出书目信息，使数据库能够与 Zotero 等常用文献管理工具协作。

## 4. 核心工作流

外部发现和内容补全是围绕同一文献数据库的两类独立操作，不是一条每次都必须从搜索运行到语言模型总结的固定流水线。

```text
外部发现：领域条件或种子文献 + 当前文献数据库
  -> 执行一次有边界的多来源主题搜索或引用扩展
  -> 元数据身份命中、去重并逐条写回数据库
  -> 保存发现条件、来源结果和发现原因

数据库补全：用户选择的数据库范围 + 当前文献数据库
  -> 在本次操作期间冻结实际目标
  -> 补齐主 PDF，或者从当前第一个缺失步骤补齐最终内容
  -> PDF 基本检查 -> 解析 -> 语言模型先确定最终元数据、再总结正文
       ├─ 明确没有实际内容 -> 丢弃内部 PDF 和对应中间结果，尝试其它候选
       └─ 具有实际内容 -> 接纳最终元数据和总结型轻结构化文档
  -> 各阶段确认结果继续写回同一数据库
  -> 向用户报告本次选择、完成、缺失、失败和未完成情况

其它操作：手动接纳 PDF、查询、书目导入导出
  -> 读取或更新同一文献数据库
```

八项核心产品能力是：

1. 按主题领域收集文献；
2. 按引用关系迭代收集文献；
3. 从多个来源汇总和整理文献元数据；
4. 获取文献全文及相关资产；
5. 解析文献资产并获得语言模型可用的中间内容；
6. 使用语言模型判断内容并形成最终元数据、关键词和总结型轻结构化文档；
7. 持续建立、查询和补充文献数据库；
8. 通过主流文献格式导入和导出书目信息。

## 5. 功能需求

### R1. 发起文献收集

- 用户必须能够提交一组领域条件，批量收集与目标领域相关的文献。
- 用户必须能够提交一篇或一组种子文献，通过引用关系迭代收集相关文献。
- 每次访问外部来源的主题搜索或引用扩展必须具有明确输入和停止边界，并保存本次发现条件、来源结果摘要、实际发现的文献和发现原因；普通本地数据库查询不需要形成这种外部发现记录。
- 外部发现和 PDF/内容补全必须能够分别发起。一次发现只负责把满足最低身份条件的元数据结果接纳到数据库并保存发现原因，不自动下载 PDF、解析或启动语言模型总结。
- 引用扩展获得的相关文献必须先按普通元数据规则进入数据库，再与来源文献建立引用关系；供应商记录 ID 或无法可靠识别目标的原始文本不能直接成为数据库中的文献关系。
- 供应商一次返回的大量引用关系不得无条件把全部目标创建为文献或触发递归；只有进入用户指定方向、深度和数量边界的目标才继续取得元数据并按普通规则入库，未进入当前范围的供应商关系可以留待后续扩展。
- 同一发现条件可以再次执行以补充新文献；PDF 或内容缺失通过独立数据库补全操作处理，不要求恢复或依附上一次发现运行。
- 系统必须保留文献由何种收集方式、哪些条件或哪些引用关系发现，使用户能够理解文献进入数据库的原因。

### R2. 多来源元数据搜索

- 系统必须能够在一次领域发现中查询多个已配置的文献元数据供应商；每个供应商分别运行到结果耗尽或达到该供应商的本次原始扫描上限。过滤、身份准入和去重前返回的每条原始结果都消耗该上限，不能仅按最终接纳数量限制搜索。
- Metadata 与 Acquisition Source 必须分别支持版本维护的默认安全选择和用户指定的精确选择。未固定列表时使用当前版本可离线确定的默认集合；固定列表时严格保留用户的集合与顺序并允许为空。默认集合不得通过启动时联网探测、凭据是否存在或临时服务状态推导；凭据存在不能暗中启用 Search 或 Download。Metadata 只配置一个正整数逐 Source 原始扫描上限，默认 500，独立应用到每个参与的 Source；它不是所有来源共享的总量或 HTTP 请求次数。
- 对已经正式接入且具有领域元数据检索能力的供应商，用户必须能够选择启用并在同一次领域发现中共同查询；供应商只覆盖特定出版社、学科或索引范围时，由该供应商返回自己的结果，不要求用户先根据出版社逐篇路由元数据搜索。
- 系统必须保留各供应商成功返回的结果；单个供应商失败不得使其它成功结果失效。
- 系统必须把不同来源中代表同一文献的结果收敛到同一文献记录，同时保留来源差异和来源信息。
- 系统必须允许元数据不完整的文献先进入数据库，并在后续明确发现或补充操作中继续完善。
- 元数据发现阶段只要求非空标题或 DOI 至少存在一个，不负责证明文献与目标领域语义相关。产品不要求在这一阶段使用语言模型、搜索分数、关键词命中、摘要分类或连续低收益规则过滤或提前停止；后续最终关键词和数据库查询用于帮助用户判断与分类。
- 一篇文献具有可用实际内容但偏离最初搜索主题时，仍然是有效文献，不能因此被解释为没有实际内容或自动删除。
- 一次领域发现完成后，不得仅因为某篇文献已经被发现，就自动对它再执行一轮全部供应商的逐篇精确补查；新的外部补充由用户后续明确发起。
- 系统必须按文献中的署名顺序保存结构化作者信息，并在来源明确提供时保留姓名组成、ORCID、署名单位及其 ROR。缺失信息不得根据姓名或单位名称猜测；当前产品不要求建立跨文献的全局作者身份或作者消歧系统。
- 对需要 API key、token 或其它认证材料的供应商，用户必须能够安全配置或移除凭据、查看哪些供应商已配置或缺失必要凭据，并显式执行最小只读连通性测试。凭据和测试结果不属于文献数据库；本地字段存在、认证成功和具体内容授权必须能够区分。
- 普通运行配置必须固定为同一用户级文件；用户从不同工作目录运行时必须得到同一配置，可以通过统一配置入口管理，也可以直接编辑该文件。普通配置与凭据必须继续分离；系统不得要求用户理解环境变量或当前目录优先级，也不得从多个旧位置猜测并自动迁移配置。
- 统一配置入口必须把模型连接、模型选择和任务使用分成三层。`Provider` 只保存本地名称、API 协议、Base URL 与 exact-origin API key 作用域；`Model` 以唯一 `provider/model` 身份保存思考程度、是否可读取图片以及是否使用流式响应；`Analyze` 与 `Browser` 只选择 Model 和管理各自业务参数，不重复配置 Provider、key、远端 model、reasoning 或 stream，也不得因一次选择而修改 Model 或另一个任务。思考程度必须包含 `default/none/minimal/low/medium/high/xhigh/max`；`default` 必须省略 wire 字段，显式值不得静默降级或映射。`stream` 必须默认 `true`，并由 `openai-responses`、`openai-chat-completions` 与 `anthropic-messages` 三种协议共同继承；用户可以在具体 Model 将其关闭。流式响应必须在 Agents 私有边界内从有界 SSE 重建为一个完整结果，不把事件流暴露给消费模块；任一模式失败后不得自动切换模式补发请求。context/output、structured output、tool decision、图片格式/数量/大小等调用合同必须由消费模块拥有并通过显式 probe 验证，不能要求用户把这些内部技术值录入 Model。Browser 只允许选择图片 Model；底层 Acquisition 普通配置可以继续把该选择保存在 `[download]`。模型 Provider key 必须由 `Models` 管理；Metadata/Acquisition Provider 的普通设置、key 和 test 必须归属于 `Search`/`Download` 中的具体 Source 对象；MinerU endpoint、上传授权和 token 必须由 `Parse → Setup` 连续管理。不得建立职责重叠的全局 key 页面，secret 只进入独立凭据文件。新增远程 Provider/Model 时必须在同一流程隐藏输入 key，并自动执行一次有界只读模型目录请求；只有目录失败或无可用结果时才回退手工输入。首页、状态查看和普通命令不得隐式发起该请求，目录结果不得持久化或被当成 capability 证明。配置不得建立 Model Profile、Preset、Entry 或任务级 reasoning/stream override；保存前必须展示不含 secret 的配置摘要。
- 配置测试必须继续归属于 `config`，并按 `Provider / Model / Search / Download / Parse / Analyze / Browser` 的 owner 语义组织；交互 TUI 与结构化 CLI 必须调用同一套不含 Storage 的 Probe 服务。配置测试只验证当前最小 readiness，不创建或修改文献业务事实。人类结果必须紧凑地优先显示测试对象、本次安全请求 method/endpoint、实际 Model、结果、失败原因和下一步，不得只显示内部错误码；能够安全确认的 HTTP status、Network 类别和 Provider 结构化错误类别可以进入当次结果，但 Key、header、query、响应正文、供应商任意 message 和原始异常不得进入。证据只能说明“Model 或 endpoint 不存在”时不得擅自断言一定是 Model 名错误。Provider 目录不能替代具体 Model 调用，Download 没有安全且与具体文献无关的外部 probe 时必须明确报告 unavailable，不能借用 Metadata probe、下载任意 PDF 或声称文章 entitlement 已验证；真正的 Search、PDF 获取、Parse/Analyze 能力分别由 `discover topic`、`complete pdf`、`complete content` 的正式业务路径验证。

### R3. 文献资产获取

- 系统必须能够使用已收集的元数据信息寻找并下载对应文献资产。
- 自动获取必须根据文献的稳定标识符、来源明确提供的资产线索、供应商专属定位或安全解析后的实际落地站点选择适用来源，不能仅依据不统一的出版社名称、元数据来自哪家聚合供应商或单独 DOI 前缀盲目调用出版社 API。能够提供元数据和能够提供原文是两项独立能力，同一家供应商可以同时具有两者。
- Sci-Hub Source 必须默认关闭。用户显式启用后可以直接使用随版本维护的内置有序镜像列表，也可以用自己的有序 HTTPS 列表完整覆盖；恢复内置列表必须删除而不是复制 custom override。系统不得自动发现或并发轰炸镜像，也不得为该 Source 增加 Key、Cookie、session、代理、selector、脚本或访问控制绕过配置。内置列表可随版本维护，但不得改写用户的 custom override。
- 当最后的受控浏览器路线进入站点验证页时，系统必须把它作为普通网页状态纳入与文章页相同的 Observation、动作执行、捕获和清理合同，并允许已经核实的必要验证资源在当前固定 Profile、当前文章流程和同一供应商串行许可内正常加载。系统必须把“Challenge page observed”“Challenge cleared”“Challenge unresolved”“本地 Network 策略阻断资源”和“普通访问被拒绝”分别反馈。Challenge 清除后仍须继续执行文章授权、正文归属和 PDF 验收，不能把验证页通过等同于当前文章已经获得全文访问权。
- 用户必须在受控浏览器作业开始前固定选择 Rules 或 Agent controller。Rules 可以使用通用 PDF 发现和供应商确定性规则且不调用模型；Agent 从第一份统一 Browser Observation 起决定下一项封闭动作且不先运行确定性点击流程。两种 controller 在正常未命中、timeout、Challenge 或失败时都不能自动切换或互相 fallback。模型不能取得浏览器、Cookie、登录材料、任意 URL、selector、脚本、持久 memory 或事实写入能力，也不能绕过供应商串行限速、Network 安全边界、单次资源上限或统一 PDF 验收；Challenge 不产生专属 target、动作、controller、预算或交互状态机。
- 用户必须能够明确选择一篇具体文献并提供本地 PDF。系统复制而不是移动用户文件，对内部副本执行与自动获取相同的基本 PDF 检查，并且绝不修改或删除用户原文件。
- 手动提供的有效 PDF 通过正常资产关系进入数据库，但不属于自动获取来源顺序；无效文件作为用户输入错误拒绝。已有当前主 PDF 时默认拒绝手动接纳，不能静默替换。
- 一篇文献可以具有多个资产或多个可能来源，系统必须明确资产与文献的关系。
- 下载阶段只对 PDF 做必要的文件检查：实际字节非空；根据字节而不是扩展名、文件名、HTTP `Content-Type` 或下载事件确认其为 PDF；标准 PDF reader 能够打开；页面树可读取且至少有一页；获取路径与目标文献的元数据信息相符。需要密码但没有可用密码、因而无法读取的加密 PDF 不能通过检查；轻微不规范但仍能正常打开和读取页面的 PDF 可以通过。
- 下载阶段不得设置固定最小字节数、最小页数或正文字符数，也不判断 PDF 是否具有正文、摘要、目录、封面或足够的学术内容。
- PDF 是否包含可供分析的实际文献内容，在解析后的语言模型分析阶段判断。若判断没有实际内容，系统必须丢弃该 PDF 及其解析结果，不把它们或该候选的信息保存在文献数据库中，并可继续尝试其它来源。
- 未被内容判断为无效的已获得资产必须在后续重跑中保持可用，不因重复收集而被无声破坏。
- 对一次主 PDF 获取，产品业务结果只区分“已经获得”与“没有获得”；没有获得时不要求长期保存网络、来源或候选级原因。数据库或文件系统无法安全提交属于系统失败，不能伪装成“没有获得”。
- 当系统已经正常遍历某篇具体文献在当前元数据和已配置自动能力下的全部 PDF 获取路径、仍没有获得主 PDF 时，数据库必须把它标记为需要用户人工提供 PDF。全库自动补全默认不再反复选择这种文献；新增可用于获取的元数据、成功接纳主 PDF 或用户明确要求重新尝试时，必须解除该标记。
- 用户中断、网络或 API 临时错误、权限或配置错误、数据库或文件系统错误，以及尚未完成全部自动路径时，不能把文献标记为需要人工提供 PDF。这些情况只属于本次操作没有完成。

### R4. 文献解析

- 系统必须能够解析已获得的受支持文献资产，并形成可供语言模型继续处理的中间内容。
- 中间内容必须提供形成最终轻结构化文档所需的完整可读文本和基本 Markdown 结构；当 Markdown 实际引用图片等资源时必须保留对应资源，但当前语言模型不要求使用图片。中间内容本身不是用户可独立使用的轻结构化文档。
- 中间内容必须能够追溯到所使用的文献资产和解析器。
- 单篇文献解析失败不得阻止同批其它文献继续处理。

### R5. 语言模型内容判断与总结

- 系统必须能够使用语言模型分析解析器产生的中间内容，并在一次逻辑分析中形成一份最终文献结果。普通文献的内容分析必须按顺序使用两次核心模型请求：第一阶段判断实际内容并确定最终元数据，第二阶段只在第一阶段成功后开始，并以已确定的最终元数据为上下文总结文献内容。超长文献可以在阶段内部有界分段，但不能改变这个先后关系，对外仍只有一份最终结果。
- 语言模型必须先判断解析内容是否包含属于当前目标文献、足以说明该文献实际研究、论证、综述、讨论或报告了什么的内容。只有封面、目录、标题与元数据、摘要、访问提示、错误页、下载说明，或者内容明确属于另一篇文献时，应判定为不可用。一页 PDF 不自动无效；完整短文、通信、评论、更正或技术说明仍可具有实际内容。
- 只有结构有效且明确的无实际内容决定才能触发清理。PDF 可能具有正文，但解析结果乱码、截断、只剩资源引用或不足以判断时，属于解析或语言模型分析失败，必须保留 PDF；缺字段、拒答、未知结构、输入不对齐或模型调用失败同样不能解释成内容无效。
- 内容有效时，第一阶段必须先提出最终文献元数据，其中包括全文总结关键词和原文摘要。最终元数据应保留已有可靠来源值；用户导入记录中的非空书目信息按用户明确提供的值优先保留，除全文关键词重新形成和已经允许的名称规范化外，只使用 PDF 明确提供的信息补齐缺失项。能够确定为同一出版社时可以统一名称变体；供应商身份和用户导入来源仍作为来源信息保留，不成为文献自身元数据。第二阶段必须同时接收同一解析中间内容和已经通过结构验证的最终元数据，再形成正文总结章节和按原文顺序排列的参考文献文本。第二阶段不得重新生成另一份元数据、关键词或摘要，最终元数据与关键词也不得以平行分类、标签或第二份分析结果重复保存。
- 轻结构化文档必须保存为可直接读取和导出的 Markdown，并同时具有与 Markdown 同源的有序结构化章节供程序读取；它是文献总结，不承诺替代原始 PDF 或解析器中间结果中的完整原文。
- Markdown 必须按顺序具有 `# 元数据`、`# 摘要`、`# 研究背景与目标`、`# 研究方法`、`# 数据`、`# 结论与局限性`、`# 参考文献` 七个一级标题。固定标题不得删除、改名或重排；可以在摘要之后、参考文献之前增加必要的其它正文一级标题，固定或额外正文一级标题下可以增加二级标题。元数据、摘要和参考文献下不增加二级标题，参考文献始终位于最后。
- `# 元数据` 必须使用固定的 Title、Authors、DOI、Other Identifiers、Publication Date、Year、Document Type、Language、Venue、Publisher、Volume、Issue、Pages、Keywords 填空项，不得增删、改名或重排。摘要单独进入 `# 摘要`；URL、开放获取、许可证、引用计数、供应商、状态和 provenance 不进入元数据块。
- 固定结构中没有可用内容时，最终 Markdown 必须统一显示精确字符串“未提供”，不能使用多种自然语言、`N/A`、`null`、`None` 或空字符串表达同一缺失事实。额外正文标题没有内容时不创建。
- 标题、原文摘要、纳入文档的原始数据、数值、单位、公式和参考文献文本必须忠于原文；背景、目标、方法、数据解释、结论与局限可以由语言模型跨原文章节整理总结。原文没有明确提供的信息必须明确缺失，不得编造。
- 最终关键词使用一个扁平列表，突出文献的核心领域、问题、方法、对象、材料、理论或贡献，不强制每个维度都有值；只作为测试、对照、背景或次要案例出现的术语不能机械成为关键词。供应商声明关键词仍作为来源事实保留，与最终关键词区分。
- 轻结构化文档必须包含语言模型实际识别到的参考文献文本，并以有序列表表达，一项对应一条原文；标题或标识符缺失的参考文献仍须保留已有文本。没有可识别参考文献时保留固定标题并显示“未提供”，但该缺失标记不属于参考文献。语言模型可以按需从这些原文中提取 DOI、标题、作者和年份等临时检索线索，但线索不能作为被引文献的权威元数据，目标文献仍须通过元数据来源获得并按统一身份规则接纳。
- 最终元数据、结构化章节、参考文献文本和规范 Markdown 必须能够共同追溯到同一解析中间内容、原始文献资产和本次逻辑语言模型分析。第一阶段产生的待验收元数据不能脱离最终内容单独发布；任一阶段失败都不得留下部分最终结果。单篇文献分析失败不得阻止同批其它文献继续处理，也不得破坏已经获得的元数据、资产或已成功接纳的轻结构化文档。
- 用户必须能够在文献数据库中查询、直接导出并以结构化形式继续使用已经成功接纳的轻结构化文档。

### R6. 文献数据库

- 主题收集、引用扩展、书目导入、内容处理、查询和导出必须使用同一套持续积累的文献数据库，不能各自形成彼此隔离的文献结果集合。
- 文献数据库允许长期存在完成度不同的文献。用户必须能够不重新执行外部发现，直接针对整个数据库、一次历史发现、一次导入、查询结果或明确选择的文献补齐缺失主 PDF 或最终内容。
- 用户必须能够在数据库中查找和检查已经收集的文献。
- 本地文献查询只读取已经接纳的数据库事实，不得隐式访问元数据供应商、创建外部发现运行或修改文献数据库；不同供应商对同一具体文献的来源记录不能制造重复查询结果，同一文献的不同明确版本仍须作为不同具体文献供用户区分。
- 每篇文献必须能够看到当前拥有的元数据（包括有序作者署名和已明确获得的作者标识及单位）、资产、轻结构化文档和引用关系。
- 用户打开一篇具体文献时，必须在同一一致读取中看到该文献的当前元数据及来源、版本上下文、当前主 PDF、当前解析与轻结构化内容、下一缺失步骤、是否需要人工 PDF 以及本地已确认引用数量；大型文件字节和可能无界增长的引用边可以通过独立读取获得。
- 已经确认的引用关系必须能够追溯到元数据供应商明确返回的结构化关系，或供应商、PDF 中的具体一条参考文献原文；多个来源支持同一关系时不得制造平行引用关系。
- 参考文献原文已经保存但尚未可靠解析到目标文献时，原文必须继续可用且不得建立错误关系或占位文献；后续运行可以再次尝试解析。
- 用户必须能够区分各类信息当前是否已经获得、哪些内容仍然缺失，以及哪些缺少主 PDF 的具体文献已经正常耗尽自动获取能力并需要人工提供文件。本次操作中的普通处理失败由该次操作的报告说明；日志只提供实时进度和诊断，不能替代报告，也不要求成为数据库中的长期文献事实。
- 数据库必须支持持续追加和补全，而不是要求每次重新建立全部结果。
- 再次运行收集或处理时，系统必须以数据库中已经确认的结果为基础复用已有内容，并从仍然缺失的部分继续。

### R7. 书目信息导入与导出

- 用户必须能够把 Zotero 等主流文献管理工具中的书目信息导入文献数据库。
- 用户必须能够把文献数据库中的书目信息导出到 Zotero 等主流文献管理工具能够使用的格式。
- 文献经过元数据信息收集并形成可用的统一书目信息后即可导出，不得把全文获取、解析或语言模型总结完成作为书目导出的前置条件。
- 产品必须覆盖主流文献交换格式；具体格式范围由后续产品设计明确。
- 导入的文献必须能够与通过主题或引用关系收集的文献共同查询和继续补充，不形成彼此隔离的结果集合。
- 每条带来新来源事实并通过接纳的导入记录必须作为该文献的一项独立来源事实保留；其中非空书目信息优先于供应商来源，供应商只能补齐导入记录缺失的字段。重复导入相同信息只形成 matched，不得持续制造重复文献或重复来源事实。
- 已经具有最终轻结构化文档的文献接纳新导入信息时，不得拆开覆盖与当前内容对齐的最终元数据；新来源事实进入下一次完整内容分析的输入，只有新的最终元数据和轻结构化文档整体接纳后才替换当前结果。
- 产品不要求长期保存原始书目文件、文件路径、外部工具对象、外部工具记录 ID、导入批次历史或其它导入导出过程来源细节；数据库只需保留“该元数据由用户通过书目导入明确提供”这一最小来源事实。

### R8. 大批量处理

- 产品必须面向一批文献运行，而不是只支持逐篇手工处理。
- 每次批量补全开始时必须在当前操作期间冻结实际目标；运行期间后来进入数据库或范围的文献不动态加入本次操作。不同目标可以有界并行，每个目标都必须从当前第一个缺失步骤继续并保留已经确认的前序事实；具体阶段如何在批量目标之间协调由 Accepted 设计在不改变冻结范围、局部成功和报告边界的前提下决定。
- 普通发现、查询或全库范围按同一文献的明确版本组去重，默认只要求至少一个版本达到目标。系统优先复用完成度更高的版本；完成度相同时优先正式发表版、作者接受稿、预印本和其它版本。
- 只有某个版本已经稳定缺少主 PDF，或者被明确判断没有实际内容且其余候选也已耗尽时，才尝试同一文献的下一版本。网络或存储系统错误、解析失败、语言模型失败、取消和无法判断不能证明版本不可用，也不能触发跨版本回退。用户明确选择具体版本时不回退到其它版本。
- 批量运行必须保留已经成功完成的文献，局部失败不能回滚整批有效结果。
- 中断或失败后，用户必须能够再次运行相同流程；系统必须根据数据库中仍然有效的结果继续补充缺失内容，而不要求重建已经完成的外部调用现场，也不制造无意义重复。
- 每次元数据发现、数据库补全、手动 PDF、书目导入和导出等用户发起的处理操作都必须向用户给出操作特有的本次运行报告。PDF 获取、Parsing 和 Analysis 作为数据库补全阶段时，其完成、明确无内容、缺失和失败必须在同一补全报告中可区分，不要求为内部阶段再套一层报告；纯查询结果本身就是读取输出。报告至少应说明本次实际选择、完成、稳定缺失、普通失败、未开始或受控中断的大致情况，以判断是否需要继续处理。
- 运行报告必须独立于逐条日志形成；日志只提供实时进度和诊断，不能被解析成报告或业务状态。二者都只描述本次操作，不要求长期保存为批次历史，也不参与下次目标选择。正常结束、普通失败和用户受控中断应尽可能返回已经形成的报告；断电、进程被强制终止等无法执行收尾逻辑的情况不保证产生最终报告，已经提交的数据库事实仍然有效。

## 6. 产品质量要求

### 6.1 覆盖与部分成功

多来源和两种收集方式的目的在于提高覆盖率。任何单一来源、文献获取、解析或语言模型总结失败时，系统都应尽可能保留其它已经获得的有效结果，并明确指出尚未完成的部分。

### 6.2 一致性

同一文献不应仅因来自不同来源、不同收集方式或书目信息导入而在数据库中无控制地重复出现。系统也不得在证据不足时把不同文献错误合并，或把无法可靠识别目标的参考文献文本直接连接到某篇文献。重复执行相同收集或重复导入相同数据不应持续制造重复记录、重复资产或平行引用关系。

### 6.3 可追溯性

用户必须能够判断：

- 文献由哪次外部发现、哪些领域条件、种子文献或直接引用原因获得；
- 元数据来自哪些供应商；
- 资产从何处获得；
- 轻结构化文档依据哪个资产、解析中间内容和语言模型形成；
- 已确认引用关系依据哪项供应商结构化关系或哪条来源参考文献原文形成；
- 本次操作中哪些文献未能获取、解析或完成语言模型总结，以及它们在本次运行中的失败边界；
- 哪些文献已经正常耗尽当前自动 PDF 获取能力、因而需要用户人工提供文件。

数据库中的长期可追溯性只针对实际接纳的结果、外部发现原因和会影响后续选择的当前事实；普通运行失败进入本次报告，逐候选过程和批量统计只服务本次运行，日志仅提供非权威实时诊断。被判断为没有实际内容而丢弃的 PDF 不形成资产、来源、解析结果或候选级失败记录；自动获取耗尽只说明需要人工 PDF，不保存候选、来源或失败原因。

### 6.4 数据完整性

已经写入数据库的有效元数据、资产关系和轻结构化文档不得因另一个来源失败、运行中断、重复运行或重复导入而被无声破坏。

### 6.5 可扩展接入

增加或替换元数据来源、文献获取方式、解析能力、语言模型服务或书目信息交换格式时，不应要求重新定义产品工作流或文献数据库的基本含义。

## 7. 范围边界

当前核心产品范围包括通用文献元数据、文献资产、总结型轻结构化文档、文献引用关系以及书目信息导入导出。同一文献的不同明确版本需要作为同一文献的版本组织，但产品不要求建立引用关系之外的通用文献关系图谱；更正、撤稿和其它供应商关系只有在未来形成明确用户需求时才进入产品数据边界。

产品需要处理通用文献信息和产品明确规定的总结型通用文本结构，但不要求从文献中抽取反应、分子、路线、产率、材料性质等特定领域知识，也不要求提供基于这些领域数据的预测、规划或分析系统。

以下内容不由需求文档决定：

- 内部数据模型、文献标识和版本表示方式；
- 使用何种数据库、文件存储、消息机制或并发模型；
- 供应商调用协议、请求额度和限速策略；
- 使用何种文献获取工具、解析器、语言模型或客户端；
- CLI、GUI、Web API 等具体交互形式；
- 内部阶段名称、状态枚举、表结构和模块名称。

这些内容只有在能够更好地满足本需求时，才由设计文档和技术文档作出选择。

## 8. 产品验收

满足以下场景时，核心需求才算成立：

| 场景 | 必须观察到的结果 |
|---|---|
| 领域收集 | 用户给出领域条件后，全部本次已配置来源分别执行有界搜索；原始结果在过滤与去重前消耗各自扫描上限，满足标题或 DOI 最低条件的结果进入数据库；单个来源失败不撤销成功结果，也不对每条发现结果自动发起逐篇全源补查或在元数据阶段执行语义相关性过滤 |
| 引用迭代收集 | 用户给出种子文献后，系统能够通过引用关系继续发现相关文献，并保留文献被发现的关系；供应商一次返回大量关系时只在用户边界内物化目标，不自动无界递归 |
| 发现与内容处理分离 | 一次外部发现具有独立输入、逐来源结果、发现对象和原因；发现结束不会自动启动 PDF、Parsing 或 Analysis，也不创建领域占位集合 |
| 参考文献解析 | 参考文献原文可以独立保留；只有目标文献经过元数据接纳并获得本地身份后才建立引用关系，关系保留其具体来源支持，无法可靠解析时不创建占位文献或错误关系 |
| 多来源搜索 | 至少两个供应商返回结果时，成功结果都被保留，重复文献不会简单按供应商复制成多篇 |
| Source 默认与扫描边界 | 空 Source 配置使用当前版本声明的 Metadata/Acquisition Auto 集合且不联网判定集合；切到 Custom 后只按用户保存的精确顺序运行并允许空列表；Key 的存在不改变选择；Metadata 的单一 limit 分别约束每个 Source 的过滤前原始 item |
| 部分来源失败 | 一个供应商失败时，其它供应商的有效文献仍进入数据库，并能看到失败信息 |
| Provider 凭据与连通性 | 用户可以通过受控入口或直接编辑同一用户级凭据文件配置和移除 Provider 密钥；能够在不显示密钥的情况下查看必需、可选、已配置、部分配置、缺失或不需要凭据的状态，并显式执行遵守统一访问政策的最小只读测试；测试不创建文献、运行或数据库事实，也不把认证成功冒充具体全文授权 |
| 用户级运行配置 | 所有正常命令和配置状态只读取同一用户级普通配置文件；裸配置入口管理并可首次创建该文件，用户也可直接编辑；工作目录和旧配置环境变量不改变配置身份，普通配置与 secret 继续分文件保存 |
| Models 与任务配置 | Models 可以保存多个 Provider 与唯一 `provider/model` Model；Provider 只拥有 API/endpoint/exact-origin key，Model 只拥有 reasoning/image/stream，Analyze/Browser 直接选择 Model，调用 capability/limits 由各模块派生且不形成任务级 override；`xhigh/max` 可保存，default 省略且显式值原样发送；stream 默认开启、三协议精确继承、可按 Model 关闭且失败不自动切换模式；Browser 只列出图片 Model；新增远程 Provider/Model 时同流程隐藏输入 key 并自动执行有界模型目录读取，只有失败或空结果才出现 Manual；首页/status 纯本地，配置与输出不显示 secret，也不存在 Service/Model Profile/Preset/Entry 兼容层 |
| 文献下载 | 系统能够从元数据继续获得实际字节非空、标准 PDF reader 可打开、页面树可读取且至少一页、获取路径与目标文献相符的 PDF；扩展名、文件名、HTTP 类型或下载事件不能替代字节检查，不可读取的加密文件不能通过 |
| 原文来源路由 | 聚合元数据来源与出版社内容能力保持解耦；系统优先使用明确资产线索和稳定标识，再按安全解析后的实际站点选择适用的公开、授权 API 或 Browser route，不因 Scopus 等聚合来源返回记录就错误调用同机构内容 API，也不对每篇文献盲目尝试全部出版社 |
| Sci-Hub 可选来源 | Source 默认关闭；显式启用且没有 custom override 时使用当前版本内置有序镜像，custom 列表完整覆盖内置列表并在升级时保持不变；Reset 恢复跟随内置列表，禁用保留 custom；请求按序而非并发执行且继续经过统一 Network/PDF 验收，不配置凭据、会话、代理或绕过能力 |
| 受控 Browser | 最后一级使用一个固定长期设备身份、一个共享 Browser process/context 和逐供应商串行 lane；用户在作业开始前选择只运行确定性规则或只运行 Browser Agent，两种方式不按失败相互切换；Challenge 与普通网页使用同一观察和封闭动作，资源阻断、页面未解决、普通拒绝和 PDF 捕获能够区分，任何动作都不能绕过 Network、供应商限速或 PDF 验收 |
| 自动 PDF 获取耗尽 | 只有当前全部自动路径正常结束仍未获得 PDF 时，具体文献才显示需要人工提供 PDF，并从全库自动重试范围排除；新增元数据、成功主 PDF 或明确重试会解除标记，网络、权限、配置、存储错误和用户中断不会误标 |
| 手动 PDF 接纳 | 用户明确选择具体文献后可以复制接纳本地有效 PDF；内部副本通过相同基本检查和正常资产关系发布，用户原文件不被移动、修改或删除，已有主 PDF 不被静默替换 |
| 文献解析 | 已获得的受支持资产能够生成语言模型可用、可追溯到原始资产的中间内容 |
| 内容判断与总结 | 语言模型先判断属于当前文献的实际内容并确定最终元数据，再以该元数据和同一解析结果为上下文总结正文；程序形成符合固定一级标题、统一“未提供”缺失值和有序参考文献格式、可直接导出并可结构化读取的总结型 Markdown；只有明确无实际内容的 PDF 及对应结果被丢弃，无法判断或解析失败时保留 PDF |
| 书目导入 | 用户能够导入主流文献管理工具的书目信息；每条带来新事实的接纳记录作为用户来源 observation 参与统一元数据，非空导入值不被供应商覆盖，重复 matched 不制造重复事实，并可与数据库已有文献共同查询和补充 |
| 书目导出 | 已经完成元数据信息收集并形成可用统一书目信息的文献，无需等待全文处理即可导出为 Zotero 等主流文献管理工具可继续使用的格式 |
| 批量局部失败 | 某些文献获取、解析或语言模型总结失败时，其它文献继续完成，已完成结果不丢失 |
| 数据库补全 | 用户可以按全库、历史发现、导入、查询结果或明确文献发起缺失 PDF/内容补全；本次实际目标只在当前操作中冻结，每个目标从当前第一个缺失步骤继续，不要求保存批次历史 |
| 多版本补全 | 普通逻辑文献范围默认只补齐一个可用版本，先复用完成度更高的版本并按既定版本顺序选择；只有稳定缺失才尝试下一版本，系统、解析或模型失败不触发跨版本回退 |
| 重复运行 | 再次执行相同收集或处理时，系统重新读取文献数据库，复用仍然有效的结果并补充缺失内容，不依赖恢复上一次外部调用现场，也不产生无意义重复 |
| 运行报告与日志 | 元数据发现、数据库补全、手动 PDF 和书目交换在正常结束、普通失败或受控中断时以操作特有报告说明本次选择与完成情况；补全报告区分 PDF 获取、Parsing 和 Analysis 结果，日志只提供独立实时反馈；二者都不进入数据库，硬崩溃可以没有最终报告但不损坏已提交事实 |
| 数据库使用 | 用户能够查询一篇文献并同时了解其元数据、资产、轻结构化文档、引用关系和是否需要人工 PDF 的可用情况，且轻结构化文档能够直接导出并按章节供程序读取 |
